# Centrifugo scale and stream positioning compared with Messenger

Checked against Centrifugo's official documentation and engineering posts on 2026-09-27. Centrifugo is a reference, not a component of this project. Conclusions about Messenger are based on the current source and are marked as such.

## What Centrifugo actually does

- Centrifugo uses Redis Pub/Sub to send a channel publication to each node with interested subscribers, then the node writes to its local clients. Its Redis broker can keep bounded channel history for recovery. The stream has an epoch and increasing offset. Recovery succeeds only if the epoch matches and the missing interval is still present; otherwise the application reloads authoritative state. Positioning periodically detects possible loss even while a client stays connected. [Engines](https://centrifugal.dev/docs/server/engines), [history and recovery](https://centrifugal.dev/docs/server/history_and_recovery).
- Redis sharded Pub/Sub spreads **different channels** across slots. Centrifugo PRO adds partitions and can group subscriptions by Redis node to limit connection count, batch resubscriptions, and follow slot moves. This does not divide a single hot channel's publication across several Redis primaries. [Scalability options](https://centrifugal.dev/docs/pro/scalability), [Centrifugo's Redis Pub/Sub engineering post](https://centrifugal.dev/blog/2026/06/29/scaling-redis-pub-sub), [Redis sharded Pub/Sub](https://redis.io/docs/latest/develop/pubsub/).
- Centrifugo PRO's `shared_position_sync` lets subscribers of the same channel on one node share recent broker position reads. Its `singleflight` coalesces simultaneous identical history or position reads, including reconnect bursts. Neither is a promise that position checks are free. [Scalability options](https://centrifugal.dev/docs/pro/scalability).
- The Centrifugo messenger tutorial's 100,000-member experiment **published to personal channels**. It split broadcasts into batches, parallelized them across Centrifugo nodes, and used multiple Redis instances. The tutorial says a shared group channel would be cheaper to publish to if the product can use one. Its latency numbers come from its own test setup, mostly with one online recipient, and cannot establish Messenger's capacity. [100,000-member tutorial](https://centrifugal.dev/docs/tutorial/scale).
- Centrifugo sends periodic ping/pong to detect broken client connections. Online presence is optional extra state, and its docs warn that presence and join/leave events add load. Its observability separates connection count, subscriptions, broker messages, recovery results, and ping/pong timing. [Transport ping/pong](https://centrifugal.dev/docs/transports/overview), [presence](https://centrifugal.dev/docs/server/presence), [observability](https://centrifugal.dev/docs/server/observability).

## What Messenger does now

- One Redis Pub/Sub connection per locally active Redis primary carries all of that node's room subscriptions. Every active room still has a listener goroutine and a 256-event buffer. The group room is published once per saved message, then each interested WS node loops over its local recipients. This is the right shape for a large group when live subscriptions are limited to the open chat. [Redis subscription hub](../ws/internal/redisroom/subscriptions.go), [room listener](../ws/internal/room/room_subscription.go), [local fanout](../ws/internal/room/room_fanout.go).
- A single hot group still occupies one Redis hash slot. More WS nodes spread socket writes, while the Redis owner must send one copy to each interested WS node. Client writes remain proportional to connected recipients times message rate. This is an inference from the [room channel key](../ws/internal/redisroom/client.go), [slot routing](../ws/internal/redisroom/subscription_topology.go), and [fanout](../ws/internal/room/room_fanout.go); it is not a load-test result.
- The [position checker](../ws/internal/room/room_position.go) now uses at most 16 concurrent checks, starts with jitter, and skips rooms that received a live publication within the interval. Each quiet room check still uses a Redis `GET` and, when an epoch exists, `XREVRANGE` ([Redis client](../ws/internal/redisroom/client.go)). Sweep duration and oldest room position age are exposed as [metrics](../ws/internal/monitoring/metrics.go). At high room counts, the configured interval is still not a bound on missed-final-event detection until those metrics are measured under load.
- A [synthetic sweep benchmark](../ws/internal/room/room_position_bench_test.go) on an Apple M3 Pro measured 10,000 quiet rooms in about 0.8 seconds with 1 ms simulated `Tail` latency and 7.2 seconds with 10 ms latency. The benchmark models scheduling and fixed read latency; it does not measure Redis Cluster throughput, network contention, or live fanout. At 10,000 rooms and 16 workers, an average read near 40–50 ms would put a sweep near the 30-second target. The checker now waits after an overlong sweep instead of immediately starting another one; this avoids continuous retry pressure, but also lengthens the detection interval while Redis is slow. [Recovery and timing tests](../ws/internal/room/room_position_test.go) cover the missed-final-event and unavailable-history paths.
- Each live publication now carries the preceding retained Stream ID, captured atomically with the append and publish ([publisher](../api/messenger-outbox-publisher/src/main/kotlin/com/andrewtinyakov/messenger/infrastructure/redis/RoomEventPublisher.kt)). The [live handler](../ws/internal/room/room_position.go) compares it with the local last ID and replays a bounded gap before accepting the new position. If recovery cannot prove completeness, it asks the client for SQL catch-up. This addresses a missed intermediate Pub/Sub event even when a later event arrives; it still needs integration and load measurements. Centrifugo uses an explicit increasing offset for positioned streams. [History and positioning](https://centrifugal.dev/docs/server/history_and_recovery).
- [Socket ping/pong](../ws/internal/socket/connection.go) currently closes dead connections, and [metrics](../ws/internal/monitoring/metrics.go) expose a per-node active-connection gauge and active-room count. There is no distributed per-user online-presence registry. That is sufficient for connection capacity monitoring; adding Redis heartbeats for every user would be separate product work, not a repair for stream gaps.

## Recommended changes

1. Measure the new predecessor check under load. If Redis reads or live processing become expensive, consider an explicit per-room offset. Do not infer continuity from a larger Stream ID alone.
2. Measure quiet-room sweep duration and oldest check age. If the 16-worker scan exceeds the target period, use pipelined position reads grouped by Redis primary. Add a Redis failure counter if diagnosis requires distinguishing Redis errors from other stale-room causes. Keep one check per **room per node**, not per connected client. Any strict freshness guarantee needs the measured oldest age to remain below its bound.
3. Keep group-room fanout for the present permission semantics. Measure a hot group at realistic online counts and message rates: Redis primary CPU, Pub/Sub reader lag, room buffer overflow, per-node outbound bytes and queue lag, slow-client closes, and recovery amplification. If Redis input or local fanout becomes the limit, first reduce per-message overhead and batch writes where protocol permits. More Redis primaries help across rooms, not within one room. More WS nodes help socket writes but increase interested-node broker copies.
4. Treat socket heartbeat, stream positioning, and product presence as distinct. The first two are needed for reliable live service. Add a cross-node presence index only if the product needs to answer who is online; avoid broadcasting every join/leave to 100,000 viewers. Sum existing per-node connection gauges for fleet capacity and add ping/pong or close-reason metrics for diagnosis.

The 100,000-member SQL limit says nothing about 100,000 simultaneous viewers. Centrifugo's published benchmarks and tutorial provide useful workload designs, but Messenger needs its own load and failure tests before claiming that scale. [Centrifugo's million-connection test](https://centrifugal.dev/blog/2020/02/10/million-connections-with-centrifugo), [100,000-member tutorial](https://centrifugal.dev/docs/tutorial/scale).
