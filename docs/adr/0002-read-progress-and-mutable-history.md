# Account read progress and mutable history

The client requires 700 ms of continuous foreground visibility, then coalesces progress to at most one request per second per selected chat. New arrivals preserve existing dwell timers. These timestamps record server acceptance of a cumulative prefix, including batching delay; they do not measure the exact instant each message was seen.

Human reads use a cumulative account-level frontier, separate from device recovery ACKs. Immutable timestamp ranges record the first accepted crossing of each new prefix, with one range per eligible UTC message-creation day. This avoids expanding a large prefix into per-message receipts, handles creation times that are not ordered by sequence, and permits bounded creation-based cleanup. The API expires details exactly 168 hours after message creation; daily bucket cleanup has up to one day of physical grace plus scheduler backlog. Short advances inspect at most 256 indexed sequences and write intervals only for eligible creation days present. Larger advances write at most eight ranges without scanning the skipped prefix. Retention and batching reduce storage without promising constant space for arbitrary traffic. See the [research](../research/presence-read-receipts-and-history.md).

Edits keep creation sequences and use independent message versions. Each edit, deletion for everyone and shared clear takes the next chat sequence, which the change log records ([ADR 0005](0005-chat-sequences-and-replica-reads.md)). Deletion for everyone physically removes bounded selected rows at commit, or denies an accepted history prefix immediately and persists bounded purge work. Sequences remain monotonic with intentional holes. A retained bodyless change log records upserts, removals and cleared prefixes. Clients below its floor reconcile their bounded retained identities against authoritative viewer-specific snapshots. A missing target never requires a permanent tombstone row.

History pages certify their examined interval at a captured chat sequence watermark, mutation sequence and member sequence. Empty pages can advance recovery across deleted or hidden content. Only certified coverage can advance across absent rows; one live frame cannot prove coverage of an earlier gap. Human reads remain independent. Keyset history queries jump over merged personal exclusions by indexed endpoints, with a bounded span budget and explicit continuation when work remains.

Personal clear stores one account cutoff, and selected personal deletion merges sequence exclusions above that cutoff. Self chat deletion also records a sidebar hide cutoff without removing membership. A later saved sequence resurfaces the chat. Everyone clear preserves the active identity; everyone chat deletion closes it, and a later direct pair starts a new identity. Either direct participant can delete either author's messages for everyone. Group authors can delete their own messages, the creator can moderate all messages, and only the creator can clear or delete the whole group for everyone.

The deletion module hides scope rights, snapshot capture, idempotency, visibility and purge scheduling behind one use-case interface. Its SQL adapter shares the chat lock with sends and mutations. Request results remain bodyless and retained after purge so delayed command retries cannot recreate content. Reply writes validate current same-chat viewer visibility; reads hydrate unavailable targets without retained quote bodies. See the [scoped deletion research](../research/scoped-deletion-and-message-interactions.md).

Shared read invalidations use one SQL deduplication row per chat and two-second bucket. Account-room invalidations now follow every committed account read advance independently; see [ADR 0003](0003-viewport-sidebar-hints.md). A nonblocking transaction advisory claim keeps independent readers from waiting on another reader's uncommitted notification row. Losing the claim coalesces only the invalidation, while each reader still commits its own durable progress and timestamps. A winner rollback can leave that bucket without a notification; the selected chat's next state check repairs it, at the latest after one minute. The unique SQL key still enforces the emission limit across API replicas. Hash collisions can coalesce unrelated hints but cannot change progress or authorization. PostgreSQL releases transaction advisory locks automatically; see its [advisory lock functions](https://www.postgresql.org/docs/17/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS).
