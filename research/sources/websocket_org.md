# WebSocket.org scale, Kubernetes, and security guides

Reviewed [WebSockets at Scale](https://websocket.org/guides/websockets-at-scale/), its related [Kubernetes ingress guide](https://websocket.org/guides/infrastructure/kubernetes/), and [security guide](https://websocket.org/guides/security/). The guides are useful checklists. Their code and capacity figures need independent validation before use.

## Architecture points worth keeping

- Separate three scaling questions: how many sockets a gateway can hold, how publications reach the correct gateway nodes, and how clients recover state after a disconnect. Horizontal gateways plus a Pub/Sub backplane address fanout; they do not themselves give durable messages or restore missed state. Redis confirms that its Pub/Sub delivery is [at most once](https://redis.io/docs/latest/develop/pubsub/). A messenger needs durable application storage and a replay or snapshot path.
- A load balancer selects a backend for each *new* WebSocket connection. The open connection already stays on that backend, so cookie or IP affinity is useful only for reconnects or for other HTTP requests that must find state on the same node. It cannot preserve a connection after backend failure. With an L7 NGINX proxy, the proxy maintains a client-side connection and an upstream connection, then tunnels bytes after the 101 response. [NGINX WebSocket proxying](https://nginx.org/en/docs/http/websocket.html). This is a good diagram and experiment for the article.
- Routing choices need workload data. Round robin balances connection count initially but can leave hot users or rooms concentrated on one node. Least-connections cannot detect traffic differences. A single hot broadcast room still creates work on every node hosting listeners, regardless of the new-connection balancing algorithm. Measure connections, publications, delivered fanout, bytes, queue depth, and p99 latency per node before choosing a routing rule. [Scale guide](https://websocket.org/guides/websockets-at-scale/).
- The guide's sticky-session advice is best treated as a temporary simplification when reconnect state only exists in local memory. Moving session and message state to shared storage lets any healthy node accept a reconnect. Affinity does not place every member of the same chat room together: hashing the client IP or cookie places *clients*, and a client can belong to many rooms. [Scale guide](https://websocket.org/guides/websockets-at-scale/), [Kubernetes Service affinity](https://kubernetes.io/docs/concepts/services-networking/service/).
- Record node and cluster active connections, upgrade failures, unexpected disconnects, reconnect attempts, subscriptions, inbound and outbound messages and bytes, slow-client buffers, CPU, memory, broker load, and delivery latency. Connection count alone misses hot fanout and slow consumers. The guide's 70–80% capacity trigger is a rule of thumb; establish a tested limit for the project's payload and traffic mix. Its claim of 500,000 idle sockets on a 16 GB server and 2–10 KB per connection is not a portable capacity estimate. [Scale guide](https://websocket.org/guides/websockets-at-scale/).
- Fallback to SSE or long polling may help where the upgrade fails. It changes the request and load pattern, so benchmark it separately. SSE is server-to-client; client writes still need HTTP. The example fallback client is illustrative, lacks jitter in reconnect delays, and does not show state recovery. [Scale guide](https://websocket.org/guides/websockets-at-scale/).

## Kubernetes lessons and caveats

- Ingress read timeout must fit the heartbeat strategy. NGINX says it closes a quiet proxied WebSocket after 60 seconds by default; periodic ping frames can reset that timeout. Choose an idle timeout and heartbeat interval together rather than copying the guide's one-hour timeout without a reason. [NGINX WebSocket proxying](https://nginx.org/en/docs/http/websocket.html), [ingress-nginx annotations](https://kubernetes.github.io/ingress-nginx/user-guide/nginx-configuration/annotations/).
- Use readiness to stop new connections during drain, handle termination in the gateway, and allow enough grace time to close sockets or give clients time to reconnect with jitter. Kubernetes marks terminating endpoints unready and sends SIGTERM within a grace period; a `preStop: sleep 15` alone is not an application drain protocol. [Kubernetes pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/). Load tests should include a rolling deployment and a pod crash, not only steady traffic.
- HPA can use connection count as a custom metric alongside CPU and memory, but scaling out adds only *new* connection capacity; it does not move existing sockets. Scaling in removes a pod and forces its clients to reconnect. Kubernetes HPA requires a custom metrics API for per-pod custom metrics. [Kubernetes HPA](https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale-walkthrough/), [Kubernetes guide](https://websocket.org/guides/infrastructure/kubernetes/).
- The Kubernetes guide enables both ingress cookie affinity and Kubernetes Service `ClientIP` affinity in its sample. These are different mechanisms; ingress-nginx may route directly to endpoints, bypassing Service proxy affinity. Test the actual traffic path before combining them. [ingress-nginx behavior](https://kubernetes.github.io/ingress-nginx/user-guide/miscellaneous/), [Kubernetes Service affinity](https://kubernetes.io/docs/concepts/services-networking/service/).

## Security lessons and caveats

- Use WSS, authenticate each connection, authorize each subscribe/publish action, cap total and per-user connections, bound incoming message size and outgoing queues, rate-limit handshakes and messages, and close or revalidate sessions after logout, expiry, or account revocation. A valid handshake does not grant indefinite access to every room. [Security guide](https://websocket.org/guides/security/), [OWASP WebSocket security](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html).
- Browser cookies accompany WebSocket handshakes, so check an explicit Origin allowlist to prevent cross-site WebSocket hijacking. Origin is a browser security signal, not authentication: non-browser clients can forge it. CORS headers are not a substitute for handshake Origin validation. [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html), [MDN server guide](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API/Writing_WebSocket_servers).
- The security page puts a JWT from `localStorage` into the URL query. That can leak through proxy/access logs, and the page's client-side `Custom Header` approach is not available through the standard browser `WebSocket(url, protocols)` constructor. Prefer a short-lived connection ticket or a controlled cookie plus Origin checks, redact credentials in logs, and specify refresh/revocation. [Security guide](https://websocket.org/guides/security/), [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html), [MDN constructor](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/WebSocket).
- Do not copy the security snippets verbatim. The guide edits `ws._receiver._maxPayload`, a private field, while `ws` exposes a supported `maxPayload` server option. Its `verifyClient` examples use an API the `ws` maintainers discourage. Its `X-Forwarded-For` IP limit assumes the header came from a trusted proxy; otherwise a client can choose its own apparent IP. [Security guide](https://websocket.org/guides/security/), [ws API](https://github.com/websockets/ws/blob/master/doc/ws.md?plain=1), [ws server examples](https://github.com/websockets/ws/blob/master/README.md?plain=1).

## Project implications

Build a small chat/notification gateway with measurable, staged failure experiments: one node, multiple nodes with channel-aware Pub/Sub, broker interruption, hot room, slow consumer, rolling restart, and burst reconnect. Add an SSE-only notification path to compare cost when bidirectional messaging is unnecessary. Expose per-node metrics and show where durability and authorization live. The scale guide's Pub/Sub sample is a sketch, not production code: it accepts arbitrary client-chosen subscribe and publish channels, lacks authorization and persistence, and references an undefined `removeClient` method. [Scale guide](https://websocket.org/guides/websockets-at-scale/).
