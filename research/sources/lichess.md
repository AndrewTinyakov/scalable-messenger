# Lichess: separate WebSocket server

The requested ["Starting from scratch" post](https://lichess.org/@/thibault/blog/starting-from-scratch/NITT84rC) currently returns a Lichess 404. Its [discussion page](https://lichess.org/forum/community-blog-discussions/ublog-NITT84rC) remains online, but cannot verify the post's WebSocket wording. The notes below come from Lichess's own maintained repositories. Treat them as evidence about the current implementation, not a quotation or historical summary of the missing post.

## What the implementation shows

- Lichess's [main server README](https://github.com/lichess-org/lila) and [WebSocket server README](https://github.com/lichess-org/lila-ws) describe `lila <-> Redis <-> lila-ws <-> WebSocket <-> client`. The latter also warns that it trusts `X-Forwarded-For` and must sit behind a reverse proxy.
- The socket server is **not generic**. Its [router](https://github.com/lichess-org/lila-ws/blob/master/src/main/scala/Router.scala) has separate game, study, tournament, lobby and other endpoints. [Authentication](https://github.com/lichess-org/lila-ws/blob/master/src/main/scala/Auth.scala) checks sessions and tokens with MongoDB. [LilaHandler](https://github.com/lichess-org/lila-ws/blob/master/src/main/scala/LilaHandler.scala) translates application events into local client and room delivery. Separation of processes does not mean that future feature changes can never require a socket server deployment.
- [Redis communication](https://github.com/lichess-org/lila-ws/blob/master/src/main/scala/Lila.scala) uses Pub/Sub channels for application traffic. [Bus](https://github.com/lichess-org/lila-ws/blob/master/src/main/scala/Bus.scala) is a local event bus for connected clients. [Users](https://github.com/lichess-org/lila-ws/blob/master/src/main/scala/Users.scala) maps each user to a set of local clients, so one user can have multiple connections. [RoomCrowd](https://github.com/lichess-org/lila-ws/blob/master/src/main/scala/RoomCrowd.scala) and [RoundCrowd](https://github.com/lichess-org/lila-ws/blob/master/src/main/scala/RoundCrowd.scala) track local presence and batch crowd updates.
- The [History](https://github.com/lichess-org/lila-ws/blob/master/src/main/scala/History.scala) class retains up to 20 versioned events per room or round in memory. On reconnect, it returns events only when it has a contiguous version range. This is a bounded recovery mechanism, not a durable message log. [Monitor](https://github.com/lichess-org/lila-ws/blob/master/src/main/scala/Monitor.scala) records current connections, origin and auth counts, room counts, Redis traffic and other metrics.
- [LilaHandler](https://github.com/lichess-org/lila-ws/blob/master/src/main/scala/LilaHandler.scala) handles a `LilaStop` event by marking the app offline. The [Redis bridge](https://github.com/lichess-org/lila-ws/blob/master/src/main/scala/Lila.scala) buffers certain critical messages in process memory during this interval, then flushes when the app is online. That buffer would disappear if the socket process died; it should not be presented as a durability guarantee.

## Benefits, costs and likely failure modes

The separate process lets Lichess change the main application without necessarily closing every WebSocket, and it can size connection handling separately. That is a useful teaching step. The cost is a new Redis communication path, application protocol coordination, proxy configuration, and a second deployment to monitor. Socket code still knows about chess features and MongoDB, which is a good counterexample to the idea of a universal, never redeployed gateway. These are inferences from the linked repositories.

Redis Pub/Sub is useful for low latency live fanout, but [Redis documents](https://redis.io/docs/latest/develop/pubsub/) at-most-once delivery: a disconnected subscriber misses published messages. The bounded in-memory history cannot recover events after its process restarts or the version gap exceeds its limit. For any message that must survive such failures, persist it in the application database or a durable log and let clients resync from that source. This recommendation is an inference from the code and Redis semantics.

## What to use in the pet project

Start with one API and one WebSocket service joined by Redis Pub/Sub. Demonstrate an API deployment while sockets remain connected, then a WebSocket deployment and reconnect. Add a local `user -> connections` map and room map. Measure live connections per node, publishes, fanout recipients and reconnect rate. Then deliberately kill Redis or a socket node and show why a durable chat message needs database history plus client cursor replay, while ephemeral presence can tolerate loss. Keep business logic in the API for this teaching version; Lichess's feature-aware gateway is a valid evolved design, not proof that all gateways should be feature-aware.
