# Routing and subscription authorization

Checked against official NGINX, AWS, and Centrifugo documentation on 2026-09-24. Design inferences below are marked as such.

## Routing facts

- A WebSocket starts as an HTTP upgrade. With an L7 reverse proxy, the proxy selects an upstream for that request, then keeps a tunnel to that upstream after the `101` response. AWS describes persistent connections on both sides of its Application Load Balancer. The accepted connection is already tied to its target; a session-affinity policy governs later requests or reconnects. [NGINX WebSocket proxying](https://nginx.org/en/docs/http/websocket.html), [AWS ALB listeners](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-listeners.html), [AWS ALB target-group stickiness](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-target-groups.html#sticky-sessions)
- L4 can route WebSockets without reading HTTP. For example, AWS Network Load Balancer uses a TCP flow hash and pins each TCP connection to one target for its lifetime. Different TCP connections from the same client can reach different targets. NGINX `stream` can use weighted round robin, `least_conn`, or `hash $remote_addr consistent`. L4 routing by user or room requires some separate mechanism that exposes that identity before choosing a target. [AWS load-balancing behavior](https://docs.aws.amazon.com/elasticloadbalancing/latest/userguide/how-elastic-load-balancing-works.html), [NGINX stream upstream](https://nginx.org/en/docs/stream/ngx_stream_upstream_module.html)
- L7 can choose by request information. NGINX HTTP upstreams support weighted round robin, `least_conn`, `ip_hash`, and `hash <key> consistent`; a key can contain variables. `ip_hash` uses the first three octets of an IPv4 address or all of an IPv6 address, so it is not user affinity. NGINX also documents cookie based sticky routing. The `sticky` directive was commercial only before NGINX 1.29.6; check the deployed version. [NGINX HTTP upstream](https://nginx.org/en/docs/http/ngx_http_upstream_module.html)
- NGINX says consistent hashing remaps relatively few keys when a backend is added or removed. It gives no fixed percentage. This changes target selection for future handshakes; it does not migrate open WebSockets. [NGINX HTTP upstream](https://nginx.org/en/docs/http/ngx_http_upstream_module.html), [AWS ALB listeners](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-listeners.html)
- Centrifugo's own multi-node examples use round robin with no sticky sessions. Its broker moves publications across nodes; even its SSE/HTTP-streaming `/emulation` commands can arrive at a different node from the stream. This depends on the shared cluster broker being configured, not on load-balancer affinity. [Centrifugo load balancing](https://centrifugal.dev/docs/server/load_balancing), [Centrifugo engines](https://centrifugal.dev/docs/server/engines)

## Design inferences from those facts

- If a client has one socket but can subscribe to boards A and B, a handshake can choose only one gateway. If A and B hash to different gateways, the client cannot be local to both. Board affinity works cleanly when the client opens a separate connection per board or joins only one board at a time. A personal channel plus arbitrary group channels brings back cross-node delivery. Room affinity is therefore a workload constraint, not a generic replacement for a backplane.
- Hashing a room ID from a URL such as `/ws/boards/42` is possible at L7 if the room is known before the upgrade. The gateway must still authorize it. A client supplied room ID is a routing hint, never proof of membership. Hashing by user instead gathers one user's devices, but does not gather every member of a group.
- `least_conn` balances connection counts at admission, not message rate or outbound bytes. A few hot rooms can overload a node with fewer connections. Each node still needs its own load metrics and a plan to drain or reconnect clients when a hot room moves.

## Centrifugo authorization facts

- Client subscriptions are denied by default. Centrifugo can allow a channel through a channel-specific subscription JWT issued by the application backend, a backend subscribe proxy, or a user-limited `#` channel. The connection JWT authenticates the user; a subscription JWT binds that user to a named channel. A supplied subscription token bypasses the subscribe proxy; user-limited channels also bypass it. [Centrifugo channel permissions](https://centrifugal.dev/docs/server/channel_permissions), [channel JWT authorization](https://centrifugal.dev/docs/server/channel_token_auth)
- The subscribe proxy calls the configured backend endpoint when a client tries to subscribe and waits for its accept or reject response before deciding. This is a synchronous decision *in the subscription request's causal path*, although the network call itself is ordinary HTTP or gRPC I/O. It avoids putting new room rules in the gateway binary, at the cost of a backend call on each relevant subscribe or resubscribe. [Centrifugo subscribe proxy](https://centrifugal.dev/docs/server/proxy)
- The backend can assign server-side subscriptions through a connection JWT `channels` claim, connect proxy result, or server API. An automatic personal channel can subscribe every authenticated connection for user 42 to `personal:#42`. Centrifugo's general `allow_subscribe_for_client` option lets every authenticated user subscribe to every channel in that namespace, so it is unsuitable for private group chats. [Centrifugo server-side subscriptions](https://centrifugal.dev/docs/server/server_subs), [channel permissions](https://centrifugal.dev/docs/server/channel_permissions)
- Subscription JWT expiry can force refresh and bound stale access. The subscribe proxy can check current membership at subscribe time. Neither mechanism alone instantly revokes a subscription that is already open; an application needing immediate revocation must also remove or disconnect existing subscribers through the server API or use a short expiry. This last sentence is a design inference from when Centrifugo performs its permission checks. [Centrifugo channel JWT authorization](https://centrifugal.dev/docs/server/channel_token_auth), [subscribe proxy](https://centrifugal.dev/docs/server/proxy), [server API](https://centrifugal.dev/docs/server/server_api)

The practical default for the messenger example is to spread WebSocket connections across gateways without room affinity, authorize group channels with backend issued subscription tokens or a subscribe proxy, and use a cross-node publish mechanism. Room-pinned boards are a separate experiment whose connection and membership rules make pinning possible.
