# Use RabbitMQ for send commands and Redis for live rooms

Status: accepted for the Messenger architecture example.

The WS node publishes send requests to partitioned RabbitMQ quorum queues and reports `queued` only after a publisher confirm. API workers validate and save them, then acknowledge the consumed commands. This makes `queued` a meaningful acceptance promise even if the sender goes offline before SQL commit, subject to the quorum queue's documented failure assumptions. SQL stores the message, request result, conversation sequence, and outbox event in one transaction. An outbox relay publishes saved events through Redis sharded Pub/Sub and keeps short Redis Stream history for recovery. SQL remains the authority for complete catch-up.

Redis Streams could also queue send requests with `XREADGROUP`, `XACK`, and pending-entry recovery. We chose RabbitMQ because a Redis primary can acknowledge `XADD` before its asynchronous replica receives the command; a failover could then erase the only server-side copy of a request that the sender believes is queued. Redis Streams have a different role after SQL commit: losing that short history falls back to SQL. This is a durability decision, not a claim that RabbitMQ has greater raw throughput. [RabbitMQ quorum queues](https://www.rabbitmq.com/docs/quorum-queues), [Redis replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/), [Redis consumer groups](https://redis.io/docs/latest/commands/xreadgroup/).

The extra broker and command hop add latency and operational work. Neither queueing nor Redis publication proves device application. The design uses a fixed set of command queues keyed by conversation ID, consumer prefetch, a bounded backlog that rejects new publishes when full, request-id deduplication, client application acknowledgements, and SQL catch-up. A single RabbitMQ queue or Redis Stream would concentrate work on one leader or shard. Worker scaling stops helping when SQL or one hot conversation becomes the bottleneck. [RabbitMQ queue scaling](https://www.rabbitmq.com/docs/queues), [queue limits](https://www.rabbitmq.com/docs/maxlength), [Redis Cluster](https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/).
