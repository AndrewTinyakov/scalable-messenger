# Gateway-owned presence benchmark, 26 November 2026

The candidate passed the 1,000-user realistic workload and failed the 8,000-user ramp. At 1,000 users it saved all 8,285 planned sends and passed all 2,618 presence snapshot checks. The polling build and the candidate used identical seeded plans for the workload comparisons. The gateway protocol and the traffic generated by the presence features differ between builds. ## What the driver checks

Each new socket must receive fresh statuses for up to three subjects after its first nonempty watch. A visible socket fails the check after five seconds or if it closes with a sample still pending. Hidden closings and samples removed by unwatch are counted as deferred. The driver allows one second for frames already in flight when an unwatch is sent. It counts watch commands, validated presence and online-count frames, and observed online/offline changes after a subject's first status. The wire has no flag that distinguishes a snapshot from a transition.

The driver splits `RATE_LIMITED` errors by whether the frame carries a request ID. Untagged errors can come from presence watches, sidebar watches, subscriptions or gateway command limits. The exact number attributable to presence was unavailable. The idle probe measures offline detection from initiating a normal close until a different socket sees the offline status.

Both runs first recorded traffic failures in the 4,500-user stage. The candidate peaked at 1,500 concurrent sockets across the two gateways. It left 105 dispatched sends pending and verified 74,639 durable outcomes with zero verification failures. The sharded recipient checks cover recipients in the sender's worker.

The candidate received 236,595 presence frames and 210,104 online-count frames. It observed 184,803 online/offline changes and sent 73,081 presence watches and 50,261 online-count watches. Of 23,792 sampled watches, 23,633 passed, 154 failed and five were deferred. The driver completed 5,585 reconnects. It received 14,839 untagged rate-limit errors and zero rate-limit errors with a request ID.

The driver recorded 718 presence frame validation failures. That counter covers both malformed frames and IDs outside the watch set and grace window. The rejected payloads were unavailable, so the split is unknown. The driver also recorded 19,603 local HTTP capacity faults. Failure observations can overlap for an action. The causes of the missing reads and saves remain unresolved, and the capacity limit remains unmeasured.

The gateways logged 576 failed `RecordLastSeen` attempts during ramp traffic. The API rejected each 1,000-entry, 37,000-byte request against its 8,192-byte gRPC limit. The corresponding SQL query counter stayed flat during the ramp. The snapshot checks cover live status. Durable last-seen persistence remained unverified. After this run, gateways send `RecordLastSeen` in batches of at most 150 entries, which a unit test keeps under the 8,192-byte limit; the ramp was not rerun with that fix. ## Quiet-watch probe

Two disposable accounts shared a group. The viewer watched the subject, and both sockets stayed active through a 60-second window. The old build used its selected-chat watch. The candidate used its user-ID watch. The subjects made no status changes during the window. Redis `MONITOR` covered the three primaries and counted client commands naming presence keys or channels. Lua subcommands, replication and unrelated gateway heartbeats were outside that count. API counters were sampled at the boundaries of the window.

| Probe | Polling build | Candidate after 45-second settle |
| --- | ---: | ---: |
| Presence frames in 60 seconds | 12 | 0 |
| Redis commands naming presence keys or channels | 16 | 2 |
| Presence authorization RPCs / SQL queries | 2 / 2 | 0 / 0 |
| Clean-close detection, three samples | 5.001, 4.981, 6.001 s | 2.153, 2.200, 2.201 s |

The 16 polling commands were `EVAL` calls against the online lease keys. The two candidate commands were a snapshot hash read and bucket sequence read within 0.06 ms of the window's start. No further presence Redis commands occurred during the settled window. The candidate probe immediately following the 1,000-user workload saw 977 `SUNSUBSCRIBE` commands for older bucket watches in the first 9.4 seconds. It also received zero frames and made zero presence authorization calls. Both probes cover one active device per subject and one authorized watcher.

## Commands

These were run from the repository root. `bench.env` and `networks.yaml` set isolated subnets, proxy limits and host ports 28081, 28082 and 29090. The setup command receives the API, WebSocket and origin explicitly. It uses the Compose project name to find PostgreSQL. Each run has its own credential manifest outside the repo.

```sh
export PATH="$HOME/.nvm/versions/node/v24.21.0/bin:$PATH"
work=/tmp/messenger-presence-2773b26
export COMPOSE_ENV_FILES="$PWD/.env,$work/bench.env"
api=http://127.0.0.1:28081/api
ws=ws://127.0.0.1:28082/ws
origin=https://presence.messenger.localhost

node tests/realistic-load/main.mjs plan --profile tests/realistic-load/profiles/users-1000.json \
  --seed 1118 --output "$work/1000-plan.json"
node tests/realistic-load/main.mjs plan --profile tests/realistic-load/profiles/stress-ramp.json \
  --seed 1118 --output "$work/stress-plan.json"
shasum -a 256 "$work/1000-plan.json" "$work/stress-plan.json"

docker compose --env-file .env --env-file "$work/bench.env" -f compose.yaml -f "$work/networks.yaml" \
  -p messenger-presence-bench up -d --no-build api-proxy ws-proxy messenger-command-processor \
  messenger-outbox-publisher monitoring-access postgres-exporter redis-exporter nginx-exporter-api nginx-exporter-ws
node tests/realistic-load/main.mjs setup --plan "$work/1000-plan.json" --manifest "$work/1000-sessions.json" \
  --compose-project messenger-presence-bench --api "$api" --ws "$ws" --origin "$origin" --auth-rate 16 --ticket-rate 25
node tests/realistic-load/main.mjs run --plan "$work/1000-plan.json" --manifest "$work/1000-sessions.json" \
  --report "$work/1000-report.json" --api "$api" --ws "$ws" --origin "$origin" \
  --auth-rate 16 --ticket-rate 25 --start-at 1795652534832

python3 "$work/collect-idle.py" messenger-bench http://127.0.0.1:8081/api ws://127.0.0.1:8082/ws \
  https://messenger.localhost legacy "$work/idle-legacy" > "$work/idle-legacy.json"
python3 "$work/collect-idle.py" messenger-presence-bench "$api" "$ws" "$origin" \
  current "$work/idle-candidate" > "$work/idle-candidate.json"
docker compose --env-file .env --env-file "$work/bench.env" -f compose.yaml -f "$work/networks.yaml" \
  -p messenger-presence-bench down

export MESSENGER_API_DB_POOL=10 MESSENGER_API_BOUNCER_POOL=20
docker compose --env-file .env --env-file "$work/bench.env" -f compose.yaml -f "$work/networks.yaml" \
  -p messenger-presence-ramp up -d --no-build api-proxy ws-proxy messenger-command-processor \
  messenger-outbox-publisher monitoring-access postgres-exporter redis-exporter nginx-exporter-api nginx-exporter-ws
node tests/realistic-load/main.mjs setup --plan "$work/stress-plan.json" --manifest "$work/stress-sessions.json" \
  --compose-project messenger-presence-ramp --api "$api" --ws "$ws" --origin "$origin" --auth-rate 50 --ticket-rate 150
node tests/realistic-load/main.mjs run --plan "$work/stress-plan.json" --manifest "$work/stress-sessions.json" \
  --report "$work/stress-report.json" --api "$api" --ws "$ws" --origin "$origin" \
  --auth-rate 50 --ticket-rate 150 --workers 2
```

Use a new wall-clock start time to repeat the fixed workload. The ramp coordinator synchronizes its workers and records their common start time. The local collectors used Prometheus's range API, `docker stats --no-stream`, the API's Micrometer counters and Redis `MONITOR`. PostgreSQL verification counted `send_requests` by terminal status where `created_at` was at or after the run start, before starting the idle probes. The raw logs and collector scripts are in `/tmp/messenger-presence-2773b26`. The checked-in JSON contains aggregates without credentials or client IDs.

```sh
fixed_start=$(cat "$work/1000-start-ms")
ramp_start=$(jq -r .startAt "$work/stress-report.json")
python3 "$work/collect-prometheus.py" http://127.0.0.1:29090 "$fixed_start" "$((fixed_start + 600000))" > "$work/1000-prom.json"
python3 "$work/collect-prometheus.py" http://127.0.0.1:29090 "$ramp_start" "$((ramp_start + 1440000))" > "$work/stress-prom.json"
python3 "$work/collect-idle.py" messenger-presence-ramp "$api" "$ws" "$origin" \
  current "$work/idle-candidate-settled" > "$work/idle-candidate-settled.json"
docker compose --env-file .env --env-file "$work/bench.env" -f compose.yaml -f "$work/networks.yaml" \
  -p messenger-presence-ramp down
```

The collectors ran before each corresponding Compose project stopped. The settled probe waited 45 seconds after ramp verification. Both candidate projects were taken down with their volumes retained. The pre-existing candidate dev project stayed up. The polling project stayed up and retained the probe's two disposable accounts and group.
