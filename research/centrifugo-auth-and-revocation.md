# Centrifugo authorization and group removal

Checked against the official Centrifugo documentation on 2026-09-27. Centrifugo is a reference design here; Messenger currently runs its own Go WebSocket service. Design conclusions are marked as inferences.

## Admission and ongoing access

- A connection JWT identifies the user. It can carry an expiry; a client must refresh it or lose the connection. A connect proxy is another way to authenticate. Centrifugo warns that very short connection token lifetimes create frequent backend refresh calls. [Client authentication](https://centrifugal.dev/docs/server/authentication), [proxy events](https://centrifugal.dev/docs/server/proxy).
- Subscriptions are denied by default. A client can gain access through a channel subscription JWT or a subscribe proxy that asks the backend at subscription time. The subscription JWT binds a user to a named channel. If the client supplies a token, Centrifugo **skips the subscribe proxy**; it also skips that proxy for user-limited channels. Do not depend on the proxy checking every group join if tokens or user-limited channels can grant access first. [Channel permissions](https://centrifugal.dev/docs/server/channel_permissions), [channel JWT authorization](https://centrifugal.dev/docs/server/channel_token_auth), [subscribe proxy](https://centrifugal.dev/docs/server/proxy).
- The subscribe proxy can call a backend over HTTP or unary gRPC and accept or reject before admitting the subscription. gRPC changes the transport and message format; the backend authorization decision remains in the subscription's request path. The docs do not promise that gRPC removes the database work or the request latency. [Proxy events and gRPC configuration](https://centrifugal.dev/docs/server/proxy).
- Channel JWT expiry bounds how long stale access can survive without refresh. It does not push a group removal to an already connected subscriber when the membership row changes. A `sub_refresh` proxy can recheck expiring subscriptions, but Centrifugo says its callback can be delayed by **up to one minute**. Expiry checks are therefore a backstop for revocation, not an immediate group-kick mechanism. [Channel JWT authorization](https://centrifugal.dev/docs/server/channel_token_auth), [sub refresh proxy](https://centrifugal.dev/docs/server/proxy).

## Active removal

- The server API has `unsubscribe(user, channel)` for all of a user's connections in a channel, with optional client or session targeting. It also has `disconnect(user)`. The normal server unsubscribe code is terminal for that subscription; the SDK does not automatically resubscribe. A fresh manual subscribe still needs an authorization check, so pair unsubscribe with a subscribe proxy or another grant that has been invalidated. [Server API](https://centrifugal.dev/docs/server/server_api), [client protocol codes](https://centrifugal.dev/docs/server/codes).
- The backend can create server-side subscriptions from connection JWT `channels`, a connect proxy result, or the server `subscribe` API. Centrifugo offers an automatic personal channel per authenticated user. Its SDK documentation recommends client-side subscriptions when possible because clients can control their lifecycle. [Server-side subscriptions](https://centrifugal.dev/docs/server/server_subs), [client SDK specification](https://centrifugal.dev/docs/transports/client_api).
- The server API can publish once to a group channel or broadcast to an array of personal channels. This supports both group-room fanout and per-user fanout; the former avoids one publication per member, while the latter lets the backend choose the recipient set when it saves a message. The comparison is an architectural inference, not a Centrifugo guarantee. [Server API publish and broadcast](https://centrifugal.dev/docs/server/server_api).

## What a group kick can promise

**Inference:** With a shared group channel, committing a membership removal in SQL and then calling `unsubscribe` are separate operations. A publication can reach the still-subscribed socket in between, or the unsubscribe call can fail. A durable revocation event, retries, and a periodic reconciliation loop can shrink and repair that window. They cannot make the SQL change and WebSocket unsubscribe atomic. To promise that a removed member receives no message saved *after* removal, choose recipients in the same transactional ordering as message saves and emit only to those recipients' personal channels. This increases fanout work with group size. If a brief revocation delay is acceptable, group rooms plus subscribe-time authorization and explicit unsubscribe are simpler.

**Inference:** A JWT-only group grant can let a kicked user resubscribe until its token expires. A live membership check on every subscribe prevents that, though it costs one backend call per subscribe or resubscribe. Short JWT lifetimes trade backend refresh load for a shorter stale-access window. [Channel permission decision order](https://centrifugal.dev/docs/server/channel_permissions), [subscription token expiry](https://centrifugal.dev/docs/server/channel_token_auth), [subscribe proxy](https://centrifugal.dev/docs/server/proxy).

## Message recovery remains separate

Centrifugo's bounded channel history can replay a short disconnect gap. Its `recovered: false` result means the client must reload from the application database. Centrifugo explicitly treats broker history as a cache, not durable chat history. Its positioning logic can also detect a missed publication while a socket remains connected. None of those features decides whether a removed user may still receive group publications; subscription authorization and revocation must handle that. [Stream history and recovery](https://centrifugal.dev/docs/server/history_and_recovery), [client protocol codes](https://centrifugal.dev/docs/server/codes).

## Group rooms versus personal rooms at large scale

Telegram's published group limit is 200,000 members; its channels can have unlimited subscribers. This describes product capacity, not Telegram's internal fanout design. [Telegram FAQ](https://telegram.org/faq).

For one message in a group of N members, Messenger's current `group:<chatId>` path saves one outbox row, runs one Redis stream/pubsub publication, and lets each WS node with subscribers fan out locally. The alternative `user:<id>` path would save N outbox rows and run N Redis stream/pubsub publications, including for offline members. Both paths ultimately send about one WebSocket frame to each connected recipient. The current outbox publisher handles rows one at a time, so it would require batching and sharding before N approaches Telegram's group limit. These are inferences from Messenger's code, not claims about Centrifugo.

The Go WS implementation now shares one Redis `PubSub` connection per locally active Redis primary and routes messages to each room. Every connected user still has a personal room and local room state, but Redis connection count no longer grows one-for-one with rooms. Per-room goroutines and position checks remain separate scaling costs to measure before claiming Centrifugo-like connection scale. [go-redis PubSub implementation](https://github.com/redis/go-redis/blob/v9.17.3/pubsub.go).

At N = 200,000, even one message per second means about 200,000 outbox rows and Redis publications per second with the current personal-room path; ten messages per second means about two million. Group-room publication remains one row and one broker publication per message, plus local fanout on interested WS nodes. The recipient count, number of online clients, and number of WS nodes are distinct costs.

Centrifugo's own messenger tutorial deliberately uses personal channels for a 100,000-member room and reports that it can work with batched broadcasts, partitioning, and multiple Redis instances. It also says a single group channel is easier and cheaper to publish to when the product can use it. Its latency measurements are for its implementation and hardware, not Messenger's. [Centrifugo large-room tutorial](https://centrifugal.dev/docs/tutorial/scale).

Removing a member from Messenger already blocks *newly processed sends* in the command processor, which checks SQL membership under the chat lock. The group-room issue is continued *receipt* of messages until the WS subscription is revoked. For large groups, an explicit removal event delivered to the affected user's personal channel can remove the group subscription quickly; a lost or delayed event still requires a fail-closed policy or reconciliation if a one-minute revocation bound is a hard guarantee. A client-side unsubscribe is only a UI hint, never the authorization mechanism.
