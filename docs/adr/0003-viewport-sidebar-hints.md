# Viewport sidebar hints and bounded summaries

The sidebar watches at most 100 chat rows per connection, independently of the selected-chat subscription and presence watch. One batched authorization request validates current membership and derives direct peers on the server. Grants expire after 30 seconds and renew before expiry. Presence observations expire independently and become unknown when stale or unavailable. Queued sidebar frames retain their grant and check it immediately before writing. Replacement, revocation or expiry discards frames still waiting at that check; an in-flight packet cannot be retracted.

A saved group message adds one bodyless `sidebar_activity` publication on `messenger:{activity:<chatId>}:live`. Gateways share one feed per locally watched group and forward only to connections watching that row. This avoids publishing message bodies or creating an outbox event for every group member. The extra publication follows the existing room script and is not atomic with it. A failure retries the outbox publication and can duplicate either hint or live event. Sidebar hints have no retained Stream, replay cursor or application ACK. Missed hints, overflow, disconnected feeds and rows outside the viewport reconcile through the existing periodic directory refresh while the network and API are available. The SQL message and its recovery guarantees remain unchanged.

Clients coalesce affected summary requests and add 500–2,000 ms jitter for sidebar activity, with at most 100 pending chat IDs and 10 concurrent requests. A hint sequence never advances device recovery or human read progress. Every committed account read advance now also creates a `reads_changed` event in that account's user room, independent of shared chat notification coalescing. This adds one account-room notification, rather than fanout to group members. Other devices can clear a group badge without joining its full-message room. Shared read invalidations retain the two-second SQL coalescing rule from ADR 0002.

Counts and previews inspect a maximum of 256 newest stored message candidates per returned chat. Own messages, global and personal clear cutoffs, hidden chats and personal exclusions filter that window after the index-backed LIMIT. `unreadCountCapped` means the unread candidate window saturated, so `unreadCount` is a lower bound, not a conventional exact count clamped at a fixed number. It can validly be `0` with the flag set. A null last-message summary does not prove that all older history is empty. These deliberate product limits keep read work independent of total history length without adding writes per group member.

Activity uses the database wall clock in the transaction that allocates chat sequences, with a per-chat monotonic maximum. Directory keysets order by activity and chat ID descending, falling back to membership join time for an empty chat. Pagination is live rather than a frozen snapshot: a concurrently active chat can move ahead of a cursor and is reconciled by refresh. Clients deduplicate chat identities across pages.
