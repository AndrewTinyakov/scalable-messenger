# Priyanshu Gupta: scaling a notification WebSocket service

Source: ["The best way to scale a WebSocket Server" (2024)](https://priyanshuguptaofficial.medium.com/scaling-websocket-server-e4323e031edf). Article accessible.

## Proposed design and useful parts

The article uses a notification service with multiple WebSocket gateways behind a load balancer. Each gateway owns two RabbitMQ queues: one bound to `public.#`, one to `private.#`. A producer publishes a notification by category, and each gateway that receives it sends it to matching local sockets. The example correctly highlights that one user may have several connections, including several devices across gateways; fanout must account for all of them. A dedicated notification service can persist a notification before live dispatch. [Article](https://priyanshuguptaofficial.medium.com/scaling-websocket-server-e4323e031edf), [RabbitMQ topic exchange rules](https://www.rabbitmq.com/docs/exchanges).

The `public.<topic>` and `private.<user-id>.<topic>` keys are useful as a *product-level naming example*. The WebSocket server still needs to authorize each subscription and distinguish user identity from connection identity. RabbitMQ wildcards match routing-key segments separated by dots, so IDs and topic names need an encoding rule if they can themselves contain dots. [RabbitMQ topic exchange rules](https://www.rabbitmq.com/docs/exchanges), [OWASP WebSocket security guidance](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html).

## Important limits and corrections

- `private.#` on **every** gateway causes **every** private event to be delivered to **every** gateway's private queue. Each gateway then filters local sockets. It solves correctness for users with devices on multiple nodes, but it does not efficiently route user-specific messages. For sparse private recipients, bind per user only on interested nodes, maintain a leased user-to-node directory, or use another targeted routing scheme. Those alternatives add binding churn, registry consistency, or both. [Article](https://priyanshuguptaofficial.medium.com/scaling-websocket-server-e4323e031edf), [RabbitMQ exchanges](https://www.rabbitmq.com/docs/exchanges).
- The article's “load balancer for initial routing only” is not how a normal WebSocket reverse proxy works. With Nginx, the client sends the opening HTTP handshake to Nginx; Nginx opens an upstream connection and, after HTTP 101, tunnels the traffic between client and selected backend. The proxy stays in the path for the lifetime of that connection. Direct client-to-backend traffic would require an explicit discovery or redirect design and reachable backend addresses, not a load-balancer setting. There are two transport legs, but Nginx's tunnel need not act as an application-level WebSocket endpoint. [Nginx WebSocket proxying](https://nginx.org/en/docs/http/websocket.html).
- A JWT in the query string is **not automatically safe** because a browser does not cache WebSocket URLs. OWASP warns that query-string tokens can appear in access logs and should be redacted. If used, keep them short lived and scoped; verify identity and authorization at connection and subscription time, and handle logout or token expiry on long-running sockets. TLS only protects transport, not logging or stolen tokens. [Article](https://priyanshuguptaofficial.medium.com/scaling-websocket-server-e4323e031edf), [OWASP WebSocket security guidance](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html).
- Persisting a notification and then publishing it are two separate operations. A crash between them leaves a stored but unsent notification unless the system has a retryable outbox or equivalent reconciliation. RabbitMQ publisher confirms, consumer acknowledgements and durable queues protect specific broker hops; none proves the browser received the message. If notifications matter after reconnect, use the database as history and replay by sequence/cursor. [Article](https://priyanshuguptaofficial.medium.com/scaling-websocket-server-e4323e031edf), [RabbitMQ reliability guide](https://www.rabbitmq.com/docs/reliability).
- Two queues per instance keep topology simple and cap binding count, which is helpful for broad public fanout. The cost is broker deliveries proportional to gateway count for *both* public and private events. The article has no throughput measurements, reconnect strategy, slow-client handling, broker failure recovery, or observability detail, so its title is stronger than its evidence. [Article](https://priyanshuguptaofficial.medium.com/scaling-websocket-server-e4323e031edf).

## Where to use it in the project

Build the article's `public.#`/`private.#` version as an intentionally simple broadcast baseline. Measure broker deliveries and gateway discard rate as node count grows. Then compare an interested-node binding or user-to-node registry for private notifications. A multi-device user should receive the same notification on every active device, while an unrelated gateway should consume none in the optimized case. Test a gateway crash, a revoked token, a publish failure after database commit, and reconnect replay.
