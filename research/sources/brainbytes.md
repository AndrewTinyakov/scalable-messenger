# Brain Bytes & Binary: WebSockets at scale

Source: [Sahil Sarwar, "WebSockets at Scale," 13 December 2025](https://brainbytesandbinary.substack.com/p/websockets-explained-from-http-upgrade). Useful for posing a routing question, but several categorical claims and the Kafka diagram need correction before they appear in our article.

## Useful concepts

- An HTTP/1.1 WebSocket handshake uses `GET`, `Upgrade: websocket`, and a client key; the server's `101` response includes `Sec-WebSocket-Accept`, calculated from the key and a fixed GUID. After that exchange, the connection carries WebSocket frames. This is enough protocol background to explain why a reverse proxy must support the upgrade and why the socket stays on a backend node. [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html). Do not describe *all* WebSockets as an HTTP/1.1 Upgrade: [RFC 8441](https://www.rfc-editor.org/rfc/rfc8441.html) defines bootstrapping over an HTTP/2 stream.
- A connection gateway can keep local `user -> connections` and room maps while business services validate, persist, and publish application events. The separation can reduce REST-driven connection churn and scale the socket layer independently. It does not require the gateway to be wholly "dumb": it still has to authenticate, authorize subscriptions and actions, enforce limits, handle heartbeats and backpressure, and coordinate reconnects. [Article](https://brainbytesandbinary.substack.com/p/websockets-explained-from-http-upgrade).
- A distributed directory of which nodes currently host a user is one way to avoid sending every event to every gateway. TTL/leases allow entries for a dead node to expire. It has costs: writes on connect/renew, stale reads, node-specific routing, cleanup races, and the need to record *multiple* connections or nodes for a user with several tabs/devices. Treat this as a design to compare with broker subscriptions by room or user; it is not required for horizontal scaling. [Article](https://brainbytesandbinary.substack.com/p/websockets-explained-from-http-upgrade).
- The best recovery idea in the article is to persist messages before the real-time push, give them stable IDs or per-chat sequence numbers, and let clients request missing data after reconnect. That makes stale directory entries tolerable *only if* the client actually detects gaps and syncs; a dropped push alone gives no eventual-delivery guarantee. Deduplicate replay by message ID. [Article](https://brainbytesandbinary.substack.com/p/websockets-explained-from-http-upgrade).

## Problems with the proposed implementation

- The Kafka partition example assigns GW1 and GW3 to partition 12, then says each gateway consumes only its own users' events and no other gateway reads the partition. In one consumer group, each partition has exactly one consumer, so both gateways cannot consume that partition. Sending both gateways the partition through separate groups would restore broadcast and filtering. A correct node-targeted Kafka design needs explicit, changing partition ownership or a separate router; keying by gateway ID alone does not make a partition belong to that gateway. Kafka guarantees order only *within a partition*. [Article](https://brainbytesandbinary.substack.com/p/websockets-explained-from-http-upgrade), [Kafka design](https://kafka.apache.org/40/design/design/), [Kafka partitioning](https://kafka.apache.org/40/design/protocol/).
- A single `user_id -> gateway` entry loses the user's other tabs or devices. The example writes a Redis hash with `HSET` and later reads it using `GET`, which would be a type error; it would need `HGET` or a string value. A 30-second TTL refreshed by a ping/pong cycle also creates a large, steady write workload and leaves stale routes until expiry. Connect/disconnect races need an instance ID or generation token so an old connection's cleanup cannot delete a newer route. [Article](https://brainbytesandbinary.substack.com/p/websockets-explained-from-http-upgrade).
- The claim that sending HTTP requests directly to gateway nodes "dies at 1M+ users" is unsupported. The backend would contact the number of *gateway nodes*, not one endpoint per user, and could reuse connections. Direct RPC has service-discovery, retry, and coupling tradeoffs, but no such universal threshold. The claim that Kafka partitions are the "only sane way" is likewise too broad; Redis 7 has [sharded Pub/Sub](https://redis.io/docs/latest/develop/pubsub/) and room/user subscriptions can route only to interested nodes.
- Masking is explained as if it prevented a browser from issuing a Redis `FLUSHDB` command after `new WebSocket('ws://...:6379')`. That example is misleading: the browser first sends an HTTP WebSocket handshake, and a non-WebSocket Redis endpoint would not return a valid `101`/`Sec-WebSocket-Accept`, so the browser would not enter the WebSocket send phase. The actual RFC rationale for unpredictable client masking is protecting deployed intermediaries, especially proxies, from maliciously chosen on-the-wire bytes and cache poisoning. Masking is neither encryption nor a replacement for authentication or network isolation. [RFC 6455 handshake and masking](https://www.rfc-editor.org/rfc/rfc6455.html).
- The article's 50,000–200,000 sockets per "strong machine" is a workload-dependent guess. Idle connection capacity says little about handshakes/sec, messages/sec, fanout, payload sizes, or slow clients. Benchmark those separately and show the tested machine and application configuration. [Article](https://brainbytesandbinary.substack.com/p/websockets-explained-from-http-upgrade).

## What to include in the project/article

Use the handshake and local socket ownership to explain the first scale boundary. Then compare two targeted fanout designs on the *same* chat workload: broker subscriptions for active rooms/users and a lease-backed node directory. Simulate multiple devices, node crash, stale routing, room fanout, and reconnect replay. If Kafka is used, show its consumer-group partition assignment explicitly; it is better suited to a durable application event pipeline than the article's proposed one-partition-per-dynamic-gateway routing. [Kafka design](https://kafka.apache.org/40/design/design/).
