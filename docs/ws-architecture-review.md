# Messenger WebSocket architecture review

Reviewed 2026-09-27 against the [broker decision](adr/0001-messenger-broker-split.md), [Messenger architecture](../research/messenger-architecture.md), [recovery research](../research/reliability-and-recovery.md), [Centrifugo comparison](../research/centrifugo-scale-and-positioning.md), [authorization research](../research/centrifugo-auth-and-revocation.md), and [hot-room routing analysis](../research/hot-room-routing.md). This is a code and design review, not a throughput benchmark.

## Verdict by workload

| Workload | Current assessment |
| --- | --- |
| Many moderate rooms and many mostly idle sockets | The architecture can add WS nodes without broadcasting every room to every node. Each node subscribes only to rooms with local listeners; one shared Redis Pub/Sub connection handles many local room channels per Redis primary. Per-socket output and per-room burst queues are bounded. Capacity is not measured yet. |
| One very large, busy group | Viewer fanout spreads across WS nodes, but each accepted message still touches one hot SQL chat row, one Redis room slot, every interested WS node, and every local viewer. Adding WS nodes does not remove those fixed hot spots. |
| Many messages in one chat | The client keeps at most 200 visible messages and pages by sequence in both directions. An explicit Jump resolves only the unseen prefix; the visible tail is applied separately. SQL history remains available on scroll back. The server's exact `received_message` acknowledgement prevents an unresolved historical gap from repeatedly closing an otherwise healthy socket. |
| Connection and Redis reconnection storms | Browser and room retries use jitter, and Redis room recovery replays a retained gap or signals SQL fallback. Redis leases cap each user at ten sockets across WS nodes; per-user handshake and subscription attempts, node in-flight handshakes, and group authorization calls are bounded. Fleet-wide reconnect capacity and SQL/gRPC pool budgets are still unmeasured. |

## What the implementation now covers

- The RabbitMQ command, SQL transaction, outbox, Redis live room, and SQL recovery responsibilities follow the selected [broker split](adr/0001-messenger-broker-split.md). A saved message has one chat sequence and a durable SQL history row. Broker publication can repeat, so clients deduplicate by message ID.
- [Socket admission](../ws/internal/socket/server.go) reserves node capacity before upgrading HTTP, closing the concurrent-upgrade race. [Redis leases](../ws/internal/redisroom/connection_leases.go) atomically cap a user at ten active sockets across nodes, renew every 30 seconds, and expire after 90 seconds if a node crashes. Per-user handshake and subscribe attempts and node in-flight handshakes/group authorization calls are bounded. Output queues have count and byte caps. The [ACK tracker](../ws/internal/socket/ack.go) distinguishes exact live-notification receipt, device application, and explicit dismissal, and bounds client-supplied per-chat position state.
- Logout removes the current SQL session and queues a `session_revoked` personal-room event in the same transaction. The WS node validates the session through gRPC once after joining that room and before exchanging application frames. Matching active sockets close on the event; ticket expiry closes a socket within one hour if the event never arrives. The [public NGINX proxy](../client/nginx.conf) limits login, registration, ticket, and upgrade requests per source IP in the Compose deployment.
- [Redis room subscriptions](../ws/internal/redisroom/subscriptions.go) use one inline event slot while idle, grow only to the existing 256-event burst limit, wait for a prior unsubscribe before rejoining, and wait for a closed shared feed to leave the hub before retrying.
- [Room feed restoration](../ws/internal/room/room_subscription.go) replays publications made during a Redis outage or sends a fresh `recovery_failed` signal. It no longer silently adopts the new tail. Quiet-room position checks can detect a missed final live event, within their configured check interval.
- [Client history](../client/src/app/useMessenger.ts) keeps a bounded visible window, supports `beforeSeq` and `afterSeq`, retains older SQL history after Jump, retries failed selected-chat catch-up with bounded jitter, and limits routine chat-list refresh to one page plus the selected chat.

## Remaining decisions and work

| Priority | Finding and concrete next step |
| --- | --- |
| Accepted revocation window | Group removal is asynchronous. Its transactional outbox event usually ejects live subscribers promptly. The selected group renews after eight minutes; a missed event can leave access until the ten-minute WS lease expires. This is the chosen bound without per-minute API calls. A strict promise that no post-removal group message reaches a former member requires recipient selection ordered with the save transaction and personal delivery, with work proportional to group size. Shared group-room publication cannot provide that strict promise. |
| Accepted revocation window | Logout revokes the current SQL session and closes matching sockets through a personal-room event. A missed event on a continuously open socket is bounded by the ticket's remaining one-hour lifetime, without periodic auth RPCs. Reconnect checks SQL. If that maximum becomes unacceptable, add periodic revalidation or a shorter ticket lifetime and measure the resulting load. |
| Browser credential storage | The browser still keeps its opaque 30-day bearer token in local storage. Server-side revocation now works with that token; moving the browser credential to an HttpOnly, Secure, SameSite cookie is a separate choice. It would reduce token theft through injected JavaScript but requires an explicit CSRF and trusted-origin design for state-changing HTTP requests. |
| Admission tuning | The ten-socket Redis cap and per-user handshake/subscribe limits are practical abuse controls, not strict invariants through asynchronous Redis failover. Redis lease renewals cost one script per socket per 30 seconds, about 33,000 scripts/second at one million sockets before distribution across Redis primaries. Compose's source-IP NGINX limits are local to its public proxy; configure them at the outermost trusted ingress in a different topology. Load-test handshake/group-auth limits and record accepted/rejected outcomes before raising defaults. |
| Scale test first | [Message saves](../api/messenger-command-processor/src/main/kotlin/com/andrewtinyakov/messenger/message/service/MessageSendService.kt) lock one chat row while checking membership, allocating a sequence, inserting the message/result, and enqueuing outbox rows. This preserves order but serializes a hot chat. Measure lock wait and transaction duration. Keep work inside the lock minimal; if the measured single-chat write target exceeds one row's capacity, introduce a chat owner or sequencer and a history layout that can partition writes while preserving the product's ordering contract. |
| Scale test first | A room's Redis Stream, epoch, and sharded Pub/Sub channel share one hash slot. Many rooms can distribute across Redis primaries, but one hot group cannot. Measure per-slot CPU, publish latency, and bytes. If a measured group saturates a slot, split delivery into viewer segments or a relay tier while keeping one authoritative SQL sequence and explicit segment recovery. |
| Scale test first | [Outbox publishing](../api/messenger-outbox-publisher/src/main/kotlin/com/andrewtinyakov/messenger/infrastructure/outbox/OutboxPublicationService.kt) claims up to 100 rows, publishes them sequentially, then batch-deletes successes under a fixed 30-second lease. Measure publish time against lease expiry and outbox age. Parallelize independent rooms with bounded per-room ordering lanes or renew claims; retain idempotent publication and completion. |
| Scale test first | Each quiet active room-node pair checks the Redis tail every 30 seconds using two Redis reads. Batch position checks by Redis owner and consider one atomically updated room-position value if command count or round trips dominate. Recovery after a saved event lost during Redis failover still depends on SQL catch-up; a continuously open socket has no strict SQL freshness deadline today. |
| Scale test first | [Socket enqueue](../ws/internal/socket/connection.go) marshals the same room event once per local recipient. Encode a room event once and share immutable bytes across local outbound queues, preserving per-recipient removal checks. This removes repeated JSON work but does not remove the required viewer × message socket writes. |
| Scale test first | The browser currently returns one exact `received_message` frame per live notification and may also send `applied`. Measure inbound frame and JSON decode cost in a busy group. If it dominates, batch exact `(chatId, sequence)` receipts under a short time and count limit. A single cumulative chat sequence is unsafe when room events reach the socket out of sequence. |
| Database budget | Bound the sum of SQL connection pools across API, command processors, outbox workers, and future auth validation replicas below PostgreSQL capacity. Bound client pending sends and replace one status SQL request per unresolved send with a batched status API if high outstanding send counts are a target workload. |

## Validation still needed

The unit, race, Redis integration, client, and contract checks verify behavior and races exercised by those tests. They do not establish a safe number of concurrent users or a claim of no security gaps. Run repeatable load tests for: many quiet room-node pairs; a single group with high viewer and message rates; many groups with rapid join/leave; full-fleet reconnect after Redis/API restart; slow browsers; and large SQL catch-up gaps. Record p95/p99 socket delivery lag, SQL lock wait and pool usage, outbox age, Redis slot CPU and position-check rate, WS queue bytes, ACK expiry, reconnect rate, and authorization latency. Set admission limits from those measurements.
