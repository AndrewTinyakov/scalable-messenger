# WebSocket scaling: project choices by communication shape

These are peer designs for different communication patterns at a comparable target scale. They are not stages in a startup's growth. The teaching goal is to show why the listener pattern changes placement and fanout, and to measure the cost of each choice under load.

The core question is how a WebSocket node reaches an event's recipients. A room is a logical recipient set, not a machine. A node may host many rooms, and one room may span nodes. For an event `e`, let `k(e)` be the number of WebSocket nodes holding its listeners. If `k(e) = 1`, one node can fan out locally. If `k(e) > 1`, the event must reach those `k(e)` nodes. The transport still writes one frame per receiving socket. Socket.IO documents local room membership and how a Redis adapter reaches other servers. [Socket.IO rooms](https://socket.io/docs/v4/rooms/), [Redis adapter](https://socket.io/docs/v4/redis-adapter/).

For one region, modest rooms, and a stable listener graph, the user's two cases are the main choices: co-locate everyone who communicates, or distribute connections and route events to the interested nodes. More project names do not create more routing architectures. Other cases become interesting when a room is too hot for one node, listeners belong to overlapping groups, memberships change rapidly, or a producer needs to reach one specific connected client.

## Three core projects

| Project | Tiny application | Placement | How events reach sockets |
| --- | --- | --- | --- |
| Messenger | Direct messages, group chats, multiple devices | Spread sockets with an L4 balancer; each socket may subscribe to a personal user room and bounded group rooms | RabbitMQ accepts send commands; SQL saves messages and outbox rows; Redis routes saved events to interested WS nodes; SQL catches up missed history |
| Kanban desks | One desk per tab, movable cards and columns, no personal channel | L7 consistent hash of desk ID sends viewers of each modest desk to one node | Backend commits an edit, sends it to that desk's node, and the node broadcasts locally |
| Twitch-like chats | Many streamer rooms of very different sizes; some have hundreds of thousands of readers and many writers | WS proxy balances by current connection and outbound capacity; compare elastic room-aware placement under the same load | API accepts a message, then sends it only to WS nodes that currently have clients in that room; control write rate and slow clients |

For messenger, L4 least connections is a sensible local experiment on a dedicated chat port. NGINX stream supports it; AWS Network Load Balancer instead uses a flow hash, so the exact policy depends on the product. L7 becomes useful for routing `/ws/chat` beside other services or applying HTTP handshake policies at the edge. L7 alone cannot co-locate users who may join many groups. [NGINX stream upstream](https://nginx.org/en/docs/stream/ngx_stream_upstream_module.html), [AWS load-balancing behavior](https://docs.aws.amazon.com/elasticloadbalancing/latest/userguide/how-elastic-load-balancing-works.html).

Messenger needs membership checks before joining group rooms and again when processing a queued send. A WS node publishes the command to a RabbitMQ quorum queue and reports `queued` after confirmation. The worker commits a message ULID, per-chat sequence, request result, and outbox rows in SQL; the outbox relay publishes to Redis. Redis Pub/Sub reaches interested gateways and short Redis Streams support replay. If short replay fails, the API uses the SQL sequence for exhaustive catch-up. The [Messenger architecture](messenger-architecture.md) and [broker decision](../docs/adr/0001-messenger-broker-split.md) are canonical for this example. [RabbitMQ confirms](https://www.rabbitmq.com/docs/confirms), [Redis Pub/Sub](https://redis.io/docs/latest/develop/pubsub/), [Debezium outbox](https://debezium.io/documentation/reference/transformations/outbox-event-router.html).

The subscription count for interested-node routing is the number of active **room-gateway pairs**, not the number of browser sockets. Each gateway refcounts its local members and creates one broker interest on the first join, removing it after the last leave. For example, 100,000 active rooms present on two gateways each imply roughly 200,000 room-gateway interests. Redis can multiplex channel subscriptions over gateway broker connections; RabbitMQ can use one queue per gateway with a binding for each local room. This avoids per-socket broker queues, but binding memory, routing work, and join/leave churn can still become expensive. Socket.IO's sharded Redis adapter exposes a static mode with few channels and dynamic modes with a channel per room, illustrating the tradeoff. [Socket.IO Redis adapter](https://socket.io/docs/v4/redis-adapter/), [RabbitMQ memory use](https://www.rabbitmq.com/docs/memory-use), [RabbitMQ cluster sizing](https://www.rabbitmq.com/blog/2020/06/18/cluster-sizing-and-other-considerations).

If exact room interests become expensive, compare them with a deterministic room coordinator and one inbox per gateway. The coordinator tracks which gateways have listeners and sends only to those gateways. This removes per-room broker bindings but keeps the same membership knowledge in coordinator memory, with register, lease, and recovery handling. Another option is a coarser hash bucket subscription, which reduces broker interest state but sends some events to gateways without listeners. Neither is automatically better than exact room interests; measure active room-gateway pairs, publish rate, and join/leave churn. Cluster-wide broadcast is not the intended Messenger design. [Ably platform scalability](https://ably.com/docs/platform/architecture/platform-scalability), [Socket.IO Redis adapter](https://socket.io/docs/v4/redis-adapter/).

For Kanban, route `/ws/desks/:deskId` by the normalized desk ID. The gateway still checks desk membership. If the REST backend stores a card move, it needs a path to the desk's node; local socket fanout does not remove that backend-to-node hop. New connections can map elsewhere when the hash ring changes while old sockets remain on their original node. Drain the old node or deliver to both during reassignment. One unusually large desk may require splitting viewers across nodes. [NGINX HTTP upstream hashing](https://nginx.org/en/docs/http/ngx_http_upstream_module.html), [NGINX WebSocket proxying](https://nginx.org/en/docs/http/websocket.html).

For Twitch-like chats, model many streamer rooms with skewed audience sizes. The reference WS proxy balances new connections against node capacity. A WS node subscribes to a room's live events only while it has local listeners, so the API does not broadcast to the whole fleet. Compare a room-aware variant in which the WS proxy chooses from an elastic eligible set for that room. Adding a node affects new connections; old connections stay put until they leave or drain. The eligible set is placement state, while active broker subscriptions represent the nodes that need each event. Room-aware placement pays off when a hot room can fit on substantially fewer WS nodes than the fleet and internal fanout is a measured bottleneck. A 400,000-viewer room may still need hundreds of WS nodes for outbound writes, even if it needs fewer for connection count. The hard limit is accepted messages times readers: placement does not remove those socket writes. Include publisher limits, moderation, outbound queues, slow-client handling, message history, and replay. A single ordered room message stream can also bottleneck at high publish rates; relays can spread fanout work. [Ably platform scalability](https://ably.com/docs/platform/architecture/platform-scalability), [Discord large guilds](https://discord.com/blog/maxjourney-pushing-discords-limits-with-a-million-plus-online-users-in-a-single-server). See [the architecture decision](twitch-architecture-decision.md) for diagrams, state, and a capacity example.

## Conditional projects with a different constraint

| Idea | When it warrants its own project | WS routing lesson |
| --- | --- | --- |
| Remote-control agent fleet | The backend must push a command to one specific connected agent and get a prompt reply | Spread agent sockets; keep an expiring `agent ID -> node` directory; route a command directly to the node, without room broadcast |
| Moving nearby map | Viewers follow overlapping, changing geographic cells | Connections remain spread; local subscriptions and broker interests churn as clients move; one location cannot place a client near every viewer |
| Synthetic market watchlist | Each client watches several symbols, and current prices replace old prices | Use interested-node fanout, but coalesce per-symbol updates for slow clients and recover the latest value rather than every price tick |
| Neighborhood community | Most activity stays inside a neighborhood, with occasional citywide rooms | Hash by neighborhood to make common traffic local; route citywide events to the interested nodes |

The room-aware subset is a peer experiment in this Twitch-like workload. Its advantage depends on a room fitting on fewer nodes than the cluster total and internal fanout being a limiting cost. Capacity-based connection balancing plus interested-node fanout is the reference design; Ably documents that approach, not the elastic room assignment. [Ably platform scalability](https://ably.com/docs/platform/architecture/platform-scalability).

The agent fleet can simulate devices rather than using real hardware. It differs from occasional telemetry uploads, which can use HTTP POST: the backend initiates commands over a persistent connection. A directory entry can be stale after a crash, so failed direct delivery must trigger a lookup or retry. An operator dashboard that watches many agents cannot necessarily be co-located with every agent.

The nearby map can be as simple as moving colored dots. It exercises overlapping subscriptions and membership churn, but its event routing is still a more demanding version of distributed interested-node delivery. Build it only if that extra behavior deserves measurement.

The market watchlist can use generated prices or match scores. It reuses Messenger-style interested-node delivery but changes the data rule: clients need the latest value for each watched key, while Messenger needs every accepted chat message. Coalesce obsolete price snapshots before slow clients build large queues; on reconnect, send current values per key. Do not apply latest-value coalescing to trades or accepted chat messages. [Centrifugo history and recovery](https://centrifugal.dev/docs/server/history_and_recovery).

Neighborhood routing is the useful middle case between perfect co-location and arbitrary placement. It reduces cross-node work for the common traffic without pretending that every event stays local. The same idea can be tested as a locality-heavy workload in the messenger rather than as a separate application.

## Games as examples, not new architecture categories

Tic-tac-toe, Pong, a typing race, and a small co-op game usually have one match per socket and a bounded number of players. Put one match on one node and broadcast locally, just as with one Kanban desk. Matchmaking or an authoritative game loop changes state handling, ordering, and update rate; it does not change the underlying listener-placement choice. If a match has more spectators than one node can handle, use multi-node fanout as in the giant chat. Colyseus uses room ownership and a reserve-seat-then-connect flow, but these are session management choices around that placement. [Colyseus scalability](https://docs.colyseus.io/scalability), [Colyseus state synchronization](https://docs.colyseus.io/state).

## What to measure

Use the same load generator for each project. Record per-node socket count, rooms or interests per node, nodes reached per event, inter-node copies per event, recipient writes, client-observed latency, CPU, memory, and reconnect rate. Compare many small desks, one oversized desk, sparse group chats, one hot group chat, and abrupt node loss. Separate message history and delivery guarantees from placement: a local Kanban desk may still need versioned snapshots, while a distributed chat needs durable per-chat replay.

The main comparison includes Messenger, Kanban, and Twitch-like chats with many rooms and a skewed audience. An agent fleet is the best fourth project if the lesson is reliable work dispatch and RabbitMQ: browser tabs can simulate agents, and the backend must send a command to one connected agent and await its application acknowledgement. A synthetic market watchlist is an optional fifth project for latest-value coalescing and snapshot recovery. The moving map exercises changing overlapping subscriptions but needs enough simulation and UI work to distract from the WS layer. Give each project its intended routing design at the target load, then compare the routing costs under controlled tests.
