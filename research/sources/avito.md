# Avito: scaling WebSocket connections in Go

Source: [AvitoTech conference write-up, 25 November 2020](https://habr.com/ru/companies/avito/articles/522744/). These are notes on the article, with current primary documentation used to check claims that matter for a project design. Its numbers describe Avito's system or a specific demo, not general capacity targets.

## Architecture and useful lessons

- Avito describes roughly 800,000 concurrent messenger WebSocket connections at the time. The transport nodes keep client connections and local subscriptions; Redis Pub/Sub routes publications to nodes with interested subscribers. Use one broker connection or a small pool per node, not one broker connection per browser connection. Personal channels permit delivery to a user's multiple devices. [Avito](https://habr.com/ru/companies/avito/articles/522744/), [Centrifugo engine design](https://centrifugal.dev/docs/server/engines).
- Their Redis choice followed a concrete workload: the earlier RabbitMQ design created a queue per connection and did frequent bind/unbind operations. The article reports about 70 CPU cores at 100,000 connections versus 0.3 core after replacing it with Redis. That is evidence against *that queue topology*, not a general RabbitMQ-versus-Redis benchmark. RabbitMQ's own [sizing guide](https://www.rabbitmq.com/blog/2020/06/18/cluster-sizing-and-other-considerations) warns that large queue counts and queue/binding churn cost resources.
- Fast live delivery is separate from catch-up. Avito atomically appended a numbered publication to a bounded Redis List and published it through Pub/Sub using a Lua script. A returning client reported its last sequence, allowing replay from the List. Server nodes checked sequence gaps and periodically checked positions; on a detected gap they closed the connection so the client could recover. [Avito](https://habr.com/ru/companies/avito/articles/522744/), [Redis Pub/Sub delivery semantics](https://redis.io/docs/latest/develop/pubsub/). This is a good pet-project experiment: deliberately drop a subscriber, then show the Pub/Sub loss and recovery path.
- The hot history absorbs a reconnect spike that would otherwise hit the application database. It is a bounded cache, so the main database must still supply initial state or a full reload when the gap exceeds retention or the cache is lost. Current Centrifugo expresses this explicitly with `epoch`, `offset`, and `recovered: false`. [Centrifugo history and recovery](https://centrifugal.dev/docs/server/history_and_recovery).
- Reconnect pressure includes authentication, subscriptions, and state restoration, not just TCP handshakes. The article proposes short-lived JWT validation on the WebSocket node, Redis pipelining, and batching subscription work. It also covers invalidating already-open connections by an account/session event or periodic checks. JWT expiration alone does not invalidate an existing long-lived socket; the design needs a refresh or revocation path. [Avito](https://habr.com/ru/companies/avito/articles/522744/).
- Redis sharding by channel name distributes broker work as channel counts and traffic grow. The article's demo used five Redis instances and jump consistent hashing. Current Centrifugo supports application-level channel sharding; adding shards can move ephemeral history and cause recovery to fail for some channels, which the client must handle. [Centrifugo engine design](https://centrifugal.dev/docs/server/engines), [Centrifugo design overview](https://centrifugal.dev/docs/getting-started/design).

## Bottlenecks and limits

- Capacity depends on file descriptors, memory per socket, CPU for messages and handshakes, TCP/conntrack limits, and the load balancer's outbound ports. The article notes ephemeral-port exhaustion between a proxy and WebSocket nodes. Do not turn its Linux tuning values into defaults; measure the actual connection path and reserve capacity for diagnostics. [Avito](https://habr.com/ru/companies/avito/articles/522744/).
- Go-specific memory work includes smaller Gorilla buffers, a pooled write buffer, and ending the HTTP handler after transferring ownership to connection goroutines so old request references can be collected. Gorilla's [own documentation](https://github.com/gorilla/websocket/blob/main/doc.go) confirms one concurrent reader and one concurrent writer, HTTP buffer reuse when upgrader sizes are zero, and write buffer pooling. The article's reported memory saving of up to 40% is workload-specific; benchmark it before adding low-level `epoll` or alternative WebSocket libraries.
- Redis Pub/Sub itself has **at-most-once** semantics. Sequence checks and short history can detect and repair brief loss, but neither proves that an application message was durably stored or read by a recipient. For durable messenger messages, persist first in the application database, publish an event after commit, use stable message IDs for deduplication, and fall back to database synchronization if history cannot bridge a gap. [Redis Pub/Sub](https://redis.io/docs/latest/develop/pubsub/), [Centrifugo design overview](https://centrifugal.dev/docs/getting-started/design), [Centrifugo history](https://centrifugal.dev/docs/server/history_and_recovery).
- The 2020 demo reached one million sockets, roughly 500,000 delivered messages per second and 200 ms p99 latency, using 20 server pods, 27 GB RAM, and five Redis instances. It included two subscriptions per connection and ~100-byte messages. The [first-party demo write-up](https://centrifugal.dev/blog/2020/02/10/million-connections-with-centrifugo) says **28 million** delivered messages/minute while the Avito transcript rounds this to **30 million**. Recovery/history doubled Redis CPU utilization in the same demo, from 32% to 64% per instance. It was a demonstration, not a saturation test, and says little about hot rooms, large payloads, or durability.

## Centrifugo as an implementation option

Centrifugo is a standalone real-time server with APIs for backend publication, channel subscriptions, broker fanout, presence, and optional short history/recovery. The app backend should validate and persist business actions, then publish. Its benefit for the project is a ready-made reference against a custom gateway, particularly for reconnect recovery and metrics. Its costs are a required client/server protocol and SDK integration, a Redis deployment for normal multi-node operation, additional broker network hops, and retained responsibility in the application for authorization, durable state, and failed recovery. [Centrifugo design overview](https://centrifugal.dev/docs/getting-started/design), [engine design](https://centrifugal.dev/docs/server/engines), [history](https://centrifugal.dev/docs/server/history_and_recovery).

Current Centrifugo can expose Prometheus metrics and a Grafana dashboard for connections, subscriptions, publications, recovery, Redis, and Go runtime. That is a useful observability baseline for the pet project. [Centrifugo observability](https://centrifugal.dev/docs/server/observability).

## Claims to update before citing the article as current advice

- The article says HTTP/2 WebSockets remained a draft. [RFC 8441](https://www.rfc-editor.org/info/rfc8441/) was published in 2018; support still depends on the client, proxy, and server.
- Its comparison of library, broker, and Centrifugo versions reflects 2020. Current Centrifugo documentation uses Redis Streams for history by default; Redis Lists remain a backward-compatibility option. [Current engine documentation](https://centrifugal.dev/docs/server/engines).
- The article suggests SockJS fallback and sticky sessions for its HTTP fallback implementation. Current Centrifugo has built-in WebSocket emulation over HTTP streaming/SSE; SockJS transport was removed in v6. [Centrifugo v6 migration](https://centrifugal.dev/docs/getting-started/migration_v6). Treat stickiness as transport and state-design dependent, not a universal WebSocket requirement.
