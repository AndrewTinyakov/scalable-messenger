# Young Gao: scaling WebSocket connections

Source: ["Scaling WebSocket Connections: From Single Server to Distributed Architecture" (2026)](https://dev.to/young_gao/scaling-websocket-connections-from-single-server-to-distributed-architecture-1men). Article accessible. This is a useful menu of design choices, but several code examples do not implement the guarantees claimed in the prose.

## Approaches worth demonstrating

1. **One gateway process.** Local map of sockets and room memberships, then a load test with connection count, message rate, payload size and fanout varied independently. Its broadcast loops over *all* clients and stringifies the same payload per recipient, so it makes a good deliberately simple baseline. The article's `20–50 KB` per connection and `50k–100k` per Node process are estimates without a cited workload or benchmark. Use measured capacity for this project instead. [Article](https://dev.to/young_gao/scaling-websocket-connections-from-single-server-to-distributed-architecture-1men).
2. **Several gateways plus room-aware Redis Pub/Sub.** Subscribe to a room channel only when the node has local members; publish room events, then deliver locally. This is a compact example of cross-node fanout and saves traffic to nodes that have no members. Pub/Sub is at-most-once: a disconnected subscriber misses the message and cannot ask Redis to replay it. The sample never unsubscribes on the last local departure and adds the room to its local subscription set *before* `SUBSCRIBE` succeeds, so subscription state can drift. [Article](https://dev.to/young_gao/scaling-websocket-connections-from-single-server-to-distributed-architecture-1men), [Redis Pub/Sub delivery semantics](https://redis.io/docs/latest/develop/pubsub/).
3. **Connection registry with expiry and targeted node channels.** `conn:<connectionId> -> serverId` with a TTL bounds stale records after a node crash. A `direct:<serverId>` Pub/Sub channel can send to one gateway when it knows where a connection lives. This is a useful alternative to broadcasting every direct message to every node, but a lookup followed by publish races disconnect or migration, and a successful `PUBLISH` does not prove client delivery. The sample's `server:<serverId>:clients` set has no TTL or cleanup after server death, so its count remains stale even after individual connection keys expire. [Article](https://dev.to/young_gao/scaling-websocket-connections-from-single-server-to-distributed-architecture-1men), [Redis expiry](https://redis.io/docs/latest/develop/using-commands/keyspace/), [Redis Pub/Sub](https://redis.io/docs/latest/develop/pubsub/).
4. **Heartbeat, reconnect, load balancing, metrics.** Server Ping/Pong and a reconnect delay with jitter address half-open sockets and reconnection surges. `ws` replies to Ping with Pong automatically; the application still needs to update liveness on Pong. Nginx's WebSocket mode tunnels the selected upstream after the upgrade, and idle timeouts matter. Track active connections, reconnect rate, broker lag, queue/backpressure, and *client-observed* delivery latency. [ws heartbeat example](https://github.com/websockets/ws/blob/master/README.md#how-to-detect-and-close-broken-connections), [Nginx WebSocket proxying](https://nginx.org/en/docs/http/websocket.html).

## Major corrections

- **The Redis Streams code does not broadcast across gateways.** All instances use one `ws-servers` consumer group. `XREADGROUP` delivers each new stream entry to one consumer in that group; other gateways with sockets in the room never receive it. Separate groups per gateway would copy every entry to every gateway, but then every node must filter every room and group lifecycle grows with nodes. Another design is durable per-room or per-user history plus Pub/Sub for live fanout. This is the main architectural error in the article. [Article code](https://dev.to/young_gao/scaling-websocket-connections-from-single-server-to-distributed-architecture-1men), [Redis Streams consumer groups](https://redis.io/docs/latest/develop/data-types/streams/), [XREADGROUP](https://redis.io/docs/latest/commands/xreadgroup/).
- **The stream example has no crash recovery.** Its `XREADGROUP ... >` reads only never-delivered entries; it never calls `XAUTOCLAIM` or reads pending history. On crash, pending entries remain pending. Creating a new group at `$` also starts after any existing history. It calls `handler(message)` without awaiting a possible asynchronous handler, then acknowledges; a WebSocket send cannot itself prove client receipt. Thus the prose's “no lost messages during deploys” is unsupported. [Redis Streams guide](https://redis.io/docs/latest/develop/data-types/streams/), [XGROUP CREATE](https://redis.io/docs/latest/commands/xgroup-create/).
- **The heartbeat/registry ordering can lie.** The sample refreshes a connection's Redis TTL when it *sends* Ping, before Pong comes back. A responsive server with a dead client can keep renewing the record until the timeout branch runs. Keep the lease tied to proven liveness and make timeout policy explicit. [Article code](https://dev.to/young_gao/scaling-websocket-connections-from-single-server-to-distributed-architecture-1men), [ws heartbeat example](https://github.com/websockets/ws/blob/master/README.md#how-to-detect-and-close-broken-connections).
- **Room affinity needs a workload rule.** Consistent hashing can put a room's connections on one node only if the connection can be routed by that room at handshake time. One socket subscribed to several rooms cannot reside on every room's owner. Hot rooms can also overload their owner, and adding/removing nodes changes ownership and requires reconnections or a forwarding path. The article's hash-ring code is only an assignment function, not the routing/migration protocol. [Article](https://dev.to/young_gao/scaling-websocket-connections-from-single-server-to-distributed-architecture-1men), [Envoy consistent-hash configuration](https://www.envoyproxy.io/docs/envoy/latest/api-v3/extensions/load_balancing_policies/common/v3/common.proto.html).
- **Some absolutes are too strong.** Round-robin can route each *new* WebSocket handshake; the connection then stays on its selected upstream. Least connections may give a better distribution when connections have different lifetimes, but neither solves cross-node delivery. L4 balancing can coexist with TLS termination at another proxy rather than requiring TLS on each backend. `ip_hash` is client-IP affinity, not room affinity. [Nginx WebSocket proxying](https://nginx.org/en/docs/http/websocket.html), [Nginx load balancing](https://nginx.org/en/docs/http/load_balancing.html).
- **The sample's measurement is not end-to-end delivery latency.** Its timer stops after local send and Redis `PUBLISH`; it does not observe remote gateway delivery or the receiving client. Use message IDs/timestamps and client acknowledgements to measure those stages. Treat the article's 100 ms p99 and 70–80% capacity thresholds as suggested starting hypotheses, not measured requirements. [Article instrumentation](https://dev.to/young_gao/scaling-websocket-connections-from-single-server-to-distributed-architecture-1men), [Prometheus histograms](https://prometheus.io/docs/practices/histograms/).
- **Reconnect needs durable protocol semantics.** `resumeId` alone does not restore memberships or replay; the server must implement both. The sample's outgoing queue is unbounded, and replaying buffered sends after reconnect can duplicate effects unless commands have IDs and deduplication. A finite queue and explicit retry policy are safer teaching examples. [Article code](https://dev.to/young_gao/scaling-websocket-connections-from-single-server-to-distributed-architecture-1men).

## Project experiments

- Compare local broadcast, Redis Pub/Sub for all nodes, and room-aware subscriptions while changing the fraction of nodes occupied by a room. Record broker traffic, discarded messages and subscription churn.
- Add a targeted-message registry; kill a gateway and show the difference between an expiring connection key and its stale node set. Test the lookup/publish race and multi-device users.
- Reproduce the single-group Streams bug with two gateway instances and one room spanning both. Fix the topology, then add pending-entry recovery and a durable per-room history. Separate broker ACK from client ACK.
- Simulate a deploy causing thousands of disconnects. Compare fixed-delay reconnects with jitter, capture peak handshakes and connection distribution. Measure delivery latency at the receiving client.
