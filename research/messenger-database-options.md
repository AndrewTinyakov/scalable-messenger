# Database choice for a billion-user messenger

Research note, 25 September 2026. This assumes a Telegram-like product with server-side, multi-device chat history. A WhatsApp-like product changes the storage problem: WhatsApp says it retains encrypted undelivered messages for up to 30 days, while Telegram says it stores cloud chats on its servers. Neither publishes enough current detail to establish its exact database engine from these statements. Do not claim that a named database is "what Telegram uses." [Telegram FAQ](https://www.telegram.org/faq), [Telegram privacy policy](https://telegram.org/privacy), [WhatsApp privacy policy](https://www.whatsapp.com/legal/privacy-policy-eea).

Discord provides a verified large chat deployment: its engineers say they moved a trillion-message history store from Cassandra to ScyllaDB in 2022, using channel and time-window partitions and sortable Snowflake IDs. They also added request coalescing and channel-based service routing because hot partitions remained a problem. In May 2026, Discord said ScyllaDB held messages, channels, servers, and most user data across dozens of clusters. These are Discord's results, not a proof of the same latency or node count for this workload. [Discord message storage](https://discord.com/blog/how-discord-stores-trillions-of-messages), [Discord cluster operations](https://discord.com/blog/how-discord-automates-scylladb-clusters-at-scale).

## Workload before product names

One billion **daily active** users sending 30 messages per day means 30 billion new messages daily, or 347,000 message writes per second on average. A 10x busy interval means 3.47 million writes per second. At an assumed 500 bytes of persisted message data, this is 15 TB of new logical data daily, 45 TB daily with three full copies, or about 5.5 PB of logical history yearly before indexes, edits, tombstones, metadata, or media. These are scenario calculations, not published Telegram or vendor measurements. One billion registered users would imply a very different load. The product must specify retention, active users, messages per active user, peak multiplier, median and p99 row size, group distribution, and regional placement before any credible node count or bill can be given.

Media belongs in object storage with message rows holding references. Durable history, unread state, presence, live fanout, search, and analytics have different access patterns; one database should not be expected to serve all of them. A broadcast channel with millions of followers is mostly a fanout and caching problem, while a conversation with thousands of concurrent senders can overload one storage partition or one order sequencer. Adding nodes does not split one hot key automatically.

## Candidate engines

| Option | Why it fits | Limit that affects this app |
| --- | --- | --- |
| **Vitess over MySQL** | Mature online resharding, query routing, and single-shard ACID transactions. A good choice when the core invariant is transactional message, conversation, membership, and outbox state colocated by conversation ID. | Cross-shard writes should be rare. Vitess's default multi-shard mode can partially commit; 2PC adds latency and atomicity but not full cross-shard isolation. A huge hot conversation remains on one shard unless the application changes its data layout. [Sharding guidelines](https://vitess.io/docs/24.0/user-guides/vschema-guide/sharding-guidelines/), [distributed transactions](https://vitess.io/docs/24.0/reference/features/distributed-transaction/). |
| **Citus over PostgreSQL** | Distributed PostgreSQL tables and efficient transactions/joins when related rows share the same distribution key. Keeps the project's current PostgreSQL model conceptually familiar. | Primary keys and unique constraints on distributed tables must include the distribution column. Citus cannot enforce arbitrary cross-worker uniqueness or foreign keys. A hot conversation grouped by `conversation_id` still hits one placement. [Citus DDL reference](https://docs.citusdata.com/en/v13.0/develop/reference_ddl.html), [table colocation](https://docs.citusdata.com/en/v6.1/sharding/colocation.html). |
| **ScyllaDB or Cassandra** | Natural fit for enormous append-heavy history read by conversation and time, with explicit partition keys, ordered clustering columns, horizontal capacity, replication across data centers, and selectable read/write consistency. | The application must design every query and duplicate some data. A partition needs a bounded bucket; a hot bucket may also need stripes. Conditional linearizable operations use Paxos/LWT and are a poor default for every message or global sequence. Atomic relational workflows across partitions need application coordination. [Scylla query design](https://docs.scylladb.com/stable/get-started/data-modeling/query-design.html), [Scylla LWT](https://docs.scylladb.com/manual/stable/features/lwt.html), [Cassandra architecture](https://cassandra.apache.org/doc/stable/cassandra/architecture/dynamo). |
| **DynamoDB** | Managed scaling removes much cluster operation work. Conditional writes, ordered sort keys inside a partition, TTL, streams, and global tables suit a key-based model. | A physical partition's write ceiling is 1,000 1-KB writes per second, so hot conversations require write sharding. Multi-Region eventual tables can expose partial replication of a transaction; multi-Region strong tables have higher WAN latency and do not support transaction APIs. Cost and vendor dependency need explicit modeling at this write volume. [Data modeling blocks](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/data-modeling-blocks.html), [global table design](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-global-table-design.html), [global table concepts](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/globaltables-CoreConcepts.html). |
| **Plain PostgreSQL plus app sharding** | Full PostgreSQL semantics inside each shard; the team controls shard routing. | PostgreSQL table partitioning alone does not provide Vitess- or Citus-like routing and online resharding across a cluster. The team owns placement, moves, global schema changes, and recovery. [PostgreSQL partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html). |

At this scale, my recommendation for a **Telegram-like history product** is ScyllaDB for message history plus a sharded transactional SQL store for account, conversation, and membership metadata. Vitess is the stronger SQL choice if the project wants to teach automated resharding and colocated transactions; Citus is defensible when retaining PostgreSQL matters. This is an architecture recommendation from the documented capabilities, not a vendor benchmark. ScyllaDB cannot make membership checks and history writes one ordinary relational transaction. A SQL outbox cannot atomically commit with a ScyllaDB write either, so delivery publication needs ScyllaDB CDC or a recoverable application-side workflow with replay and deduplication. ScyllaDB's CDC log has a configurable TTL, 24 hours by default, so a consumer that falls behind needs a history-based repair path. [ScyllaDB CDC](https://docs.scylladb.com/manual/stable/features/cdc/index.html), [CDC settings](https://docs.scylladb.com/manual/stable/cql/ddl.html). If the teaching project insists on one durable database, choose Vitess with a carefully chosen shard key and say clearly that large broadcast channels and hot conversations need special handling.

## Data layout and guarantees to teach

* Store history by `(conversation_id, time_bucket)` with an ordered message key. Bound bucket size by measured bytes, not just a calendar interval. A day bucket can still be hot during a viral event; stripe writes for outliers, then merge reads across stripes. Scylla documents bucketing specifically to prevent unbounded partitions. [Scylla query design](https://docs.scylladb.com/stable/get-started/data-modeling/query-design.html).
* Give every send a stable client request ID and a server message ID. Enforce deduplication at the authority for that conversation. A sortable distributed ID can establish a display order, but it is not a gapless, globally agreed conversation sequence. If strict per-conversation order is required, serialize acceptance through a conversation owner or sequencer; that owner becomes the hot conversation's throughput limit. This is a design inference, not a database feature claim.
* Define the acknowledgement precisely: a saved acknowledgement follows durable commit at the selected consistency level. Publish to WebSocket nodes after that commit through a same-database outbox, change stream, or replayable scanner. Live delivery may repeat; clients deduplicate by message ID. Do not equate broker publish with durable history or claim an atomic outbox across ScyllaDB and SQL.
* Pick a home region for each conversation if strict order and read-after-write matter. Replicate history outward for reads and recovery. Active-active writes to the same conversation introduce conflict and order policy. Scylla's `LOCAL_QUORUM` only coordinates within a data center; DynamoDB's global table modes make different latency and transaction tradeoffs. [Scylla consistency levels](https://docs.scylladb.com/manual/stable/cql/consistency.html), [DynamoDB global tables](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-global-table-design.html).
* Keep the choice conditional on product semantics. Telegram cloud chats and WhatsApp's encrypted delivery queue are materially different persistence obligations. Public Telegram material describes multi-data-center cloud storage but does not identify a database engine. [Telegram FAQ](https://www.telegram.org/faq), [Telegram privacy policy](https://telegram.org/privacy), [WhatsApp privacy policy](https://www.whatsapp.com/legal/privacy-policy-eea).
