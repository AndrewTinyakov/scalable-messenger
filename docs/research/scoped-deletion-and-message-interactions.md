# Scoped deletion and message interactions

Research date: 2026-11-04. This is an implementation guide, not an implementation or benchmark result. External behavior below is supported by primary sources. Sections marked recommendation describe this project's proposed contract, not Telegram's internals.

## Evidence and scope

Read the task brief, [CONTEXT](../../CONTEXT.md), [ADR0001](../adr/0001-messenger-broker-split.md), [ADR0002](../adr/0002-read-progress-and-mutable-history.md) and the [previous research](presence-read-receipts-and-history.md). These temporary reports contain repository paths and caller evidence; they are session artifacts, not permanent external references. No services, browser sessions, Git operations or benchmarks were run for this report.

The new brief supersedes the previous research's universal global-delete and tombstone recommendations. Preserve confirmed Rabbit acceptance, SQL request deduplication, membership enforcement, explicit transactions, ACK after commit and independent human reads. The audits establish current friction: message and change foreign keys prevent hard deletion; durable outbox and Redis replay copy bodies and quotes; history windows assume sequence adjacency; per-chat navigation resets the viewport. ## What Telegram establishes

| Topic | Documented fact or inspected first-party behavior | Implication here |
| --- | --- | --- |
| Direct messages/history | Telegram's FAQ permits either participant to delete sent or received messages for both sides, and clear history on both ends. It says deleted messages leave no mark. [FAQ](https://telegram.org/faq#q-can-i-delete-my-messages) | Adopt either-participant global deletion in direct chats. This does not prove Telegram uses SQL hard deletion or immediately erases backups. |
| Selected messages | `messages.deleteMessages` takes an ID vector and a `revoke` flag for all-participant deletion; forbidden message errors remain possible. [Method](https://core.telegram.org/method/messages.deleteMessages) | Use explicit scope and bounded IDs; check rights for every target. |
| History flags | `messages.deleteHistory` documents `just_clear` as current-user clearing, `revoke` as all-participant deletion, and `max_id` as the maximum message ID to delete. Date filters have non-user-peer restrictions. [Method](https://core.telegram.org/method/messages.deleteHistory) | Capture a server-side accepted prefix. Do not copy Telegram's numeric message IDs into this project's SQL-sequence contract. |
| Groups and moderation | Ordinary users delete their own group messages; admins can mass-delete with configured rights. [FAQ](https://telegram.org/faq#q-what-makes-telegram-groups-cool), [admin rights](https://core.telegram.org/constructor/chatAdminRights) | Group rights differ from direct rights. | Supergroup history | `channels.deleteHistory` has `for_everyone` and `max_id`, plus membership/admin errors. [Method](https://core.telegram.org/method/channels.deleteHistory) | Do not infer that every group member can clear shared history. Basic groups and supergroups have distinct methods. |
| First-party client | Web A's `deleteHistory` chooses channel or ordinary history methods, sets `revoke` or `just_clear` on the latter, and repeats while affected-history `offset` remains. [Implementation](https://github.com/Ajaxy/telegram-tt/blob/master/src/api/gramjs/methods/messages.ts#L1437) | Multi-step server work is compatible with the interaction. This mutable source is evidence of the inspected client, not a universal protocol guarantee. |

The method documentation does not fully specify empty-dialog retention or new-message sidebar resurfacing. Treat the requested Telegram-style lifecycle as a recommended project policy, not a verified universal Telegram guarantee. Do not equate a personal group hide with leaving membership, or equate clearing history with destroying the chat identity.

## Recommended scope, rights and lifecycle

These are project policy choices, using the brief and Telegram evidence above.

| Action | Self only | Everyone |
| --- | --- | --- |
| Message or selected batch | Any current member hides those messages for that account on all devices | Either direct participant; group author for own messages, creator for any message |
| Clear current history | Hide accepted prefix, keep empty sidebar entry | Either direct participant or group creator; hide prefix globally, preserve active chat |
| Delete chat | Hide accepted prefix and sidebar entry; retain membership | Either direct participant or group creator; close old chat identity, deny later writes and purge history |

Edits stay author-only. Reject a mixed unauthorized batch atomically, rather than silently deleting its authorized subset. Repeated deletion is idempotent without disclosing foreign-chat IDs. Default the scope chooser to self only, state whose history changes, and require an explicit everyone choice. Whole-chat global deletion remains distinct from clear history. A later direct conversation after global deletion has a fresh chat ID. A self-hidden chat reappears when a new saved message has sequence above its hide cutoff, including the account's own new send; an old edit, replay or receipt cannot resurface it.

## Recommended compact personal visibility

Keep authorization membership separate from visibility. Store per account/chat `clearedThrough`, nullable `hiddenThrough`, and a monotonic personal revision. Under the existing chat serialization point capture accepted high-watermark H, then update the account state. Self clear sets `clearedThrough=max(old,H)` and removes sidebar hiding. Self delete advances the clear cutoff and sets the hide cutoff. An empty chat needs nullable hiding state, because H can be zero. Directory visibility is `hiddenThrough IS NULL OR lastAcceptedSequence > hiddenThrough`. This avoids writes to every group member for each send. Account-room hints invalidate other devices; reconnect must reconcile authoritative account state even if hints vanished. This follows the audit's existing membership and user-room seams.

For arbitrary personal deletions, store bodyless, disjoint, merged sequence intervals above the cutoff, indexed by account/chat/start. Singletons are intervals. Merge overlaps and true numeric adjacency under the account/chat visibility lock; never merge across a surviving visible row merely because its neighbors were selected. Storage is proportional to disjoint exclusions, which can still grow with arbitrary user actions. Apply request/rate budgets and bounded compaction, and state this cost honestly. A prefix clear must not expand into per-message or per-recipient records. Prune exclusions subsumed by a later cutoff asynchronously.

An explicit ID batch can resolve at most 100 saved messages, an initial proposed selection/request cap. For a genuine range operation use explicit sequence bounds and scope, not a list of every interior ID. Authorize range semantics separately: a group author cannot globally erase another author's intervening rows. Do not turn a gesture across unfetched history into an unseen all-message range deletion. The UI default selects only loaded, encountered rows and stops at the shared cap.

## Recommended keyset queries and sparse recovery

PostgreSQL documents that large `OFFSET` still computes skipped rows, and that multicolumn B-tree equality on leading columns plus a range on the next column constrains the scan. These support sequence seeks, not a latency guarantee. [LIMIT/OFFSET](https://www.postgresql.org/docs/current/queries-limit.html), [multicolumn indexes](https://www.postgresql.org/docs/current/indexes-multicolumn.html).

Keep `(chat_id,sequence)` indexed. Start ascending history after `max(requestCursor,personalCutoff,globalCutoff)`. Find a containing hidden interval through an indexed predecessor lookup. Jump directly to its end. Otherwise read visible candidates only until the next interval's start or snapshot H. Repeat with bounded interval-transition and row budgets. Reverse this for older pages. A plain anti-join that filters a million hidden middle rows after scanning them is insufficient. If budgets expire, return an empty or short page with a progressed continuation and explicit incompleteness. A long run of alternating singleton exclusions must not monopolize a request. Verify the actual SQL plans; keyset syntax alone does not prove bounded scanning.

Every authoritative history page should carry captured H, global mutation revision, personal visibility revision, the examined interval and a continuation/completion indicator. In one consistent snapshot, a page certifies that all eligible rows inside its examined interval were returned or intentionally absent. Fetching limit+1 establishes another visible result, but does not justify claiming unexamined intervals when scan budgets expire. Reject malformed, overlapping or regressing coverage in strict decoders.

Example: after baseline 100, a page returns rows 103 and 108 and certifies coverage `(100,110]` at H=110. Recovery can finish through 110 after installing those rows. A live packet containing only 108 cannot prove what happened to 101–107 or 109–110. It needs authoritative recovery. Deleted-tail and entirely empty pages must advance certified coverage too. Around-anchor pages support navigation; their isolated coverage does not automatically advance the transport baseline across an earlier unexamined gap.

Deepen the existing ChatRecovery module to own coverage installation, removal, version/revision reconciliation and reset. Never infer recovery from every `+1` existing, the last visible row, or an out-of-order hint's highest revision. Keep mutation catch-up independent of creation sequences. Preserve `received_message`, applied/dismissed transport semantics and account human-read progress as separate interface concepts. Update ADR0002 and generated HTTP/AsyncAPI fixtures before relying on this changed guarantee. [Current contract](../../CONTEXT.md), [previous recovery analysis](presence-read-receipts-and-history.md).

## Recommended permanent purge and concurrency

Acceptance and physical completion are different states. Accept a large global clear in one short transaction that authorizes, captures H under the chat lock shared with sends/mutations, advances a global cutoff, appends a bodyless range mutation, and persists purge work plus outbox hints. New sends serialize before the clear and fall within H, or after it and receive a larger sequence. Global chat delete also closes the lifecycle and releases the active direct-pair identity. Later queued first-time sends to that old chat record rejection. Keep existing request-before-chat lock order consistent across relevant paths.

For bounded selected-message global deletion, delete actual rows in the transaction if measured lock work permits; broad clears use durable jobs. Claim a small number of jobs with a lease/fencing token or transaction-held row claim. PostgreSQL explicitly permits `SKIP LOCKED` for queue-like consumers and warns that it gives an inconsistent view. Use it to claim jobs, not to prove all message rows were purged. [SELECT locking](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE).

Within each job, delete an indexed chunk, initially 500–1000 rows, and persist progress in that same transaction. Bound wall time, retries and fleet concurrency, schedule fairly, and retry deadlock/serialization failures. Never advance a keyset cursor past a skipped locked message row. Crash before commit retries the chunk; crash after commit resumes from committed progress. Coalesce overlapping prefix jobs by maximum target and generation. An old lease owner cannot mark a newer target complete. Completion rechecks outstanding work and dependent application stores. A failed job stays durable and visible to operators; logical denial is not permission to leave bodies indefinitely.

The current same-chat reply FK and change-target FK need migration. PostgreSQL supports composite references and explicit referential actions, but cascading through every reply would make a popular-target deletion unbounded. [Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html). Recommended adaptation: retain bodyless reply target identity without a target-existence FK, enforce same-chat/visible-target validation on new writes under the existing transaction, and hydrate missing or personally hidden targets as unavailable. Keep dangling IDs as metadata; do not retain a message tombstone row per deleted message. Revalidate batch and single-send paths. No recursive quote snapshots.

Mutation changes should discriminate upsert, removed IDs and cleared-through range, with no bodies. Remove dependence on the target row's existence. Hydrating an old upsert whose row is now absent must produce removal/current authoritative state, not a null assertion or resurrection. Keep change-log floors and bounded-window reset below the floor. Purging a target must invalidate cached quotes, composer reply previews, pinned/latest/detached windows, pending snapshots and selection. Personal visibility applies to history, anchor lookup, quote resolution, reply validation, read details and directory previews, not just the main page query. These changes address the audit's actual FK and hydration failures.

Retain bodyless send-result dedup rows and their request fingerprint. A saved result remains evidence of original acceptance after its message is gone; retries must not recreate content or become a send in a fresh direct chat. SQL deletion of dedup state would defeat this guarantee. Derived fingerprints are retained metadata, not erased data. Preserve message/result/sequence/outbox atomicity and consumer ACK after commit. Rabbit confirms and consumer acknowledgements are independent mechanisms. [Rabbit acknowledgements](https://www.rabbitmq.com/docs/confirms).

### Content retention and publication choice

The audit found bodies in SQL messages, claimed outbox payloads, Redis Stream events and ephemeral socket frames; reply previews duplicate text in events. The following is a recommendation based on those concrete paths, not a claim about Telegram storage.

| Design | Purge consequences | Cost and recommendation |
| --- | --- | --- |
| Bodyless durable outbox references and Stream hints; full ephemeral room frames | SQL owns retained history content; purge does not search durable event JSON for every body/quote copy. Already hydrated/in-flight frames still exist temporarily. | Prefer this. Add bounded current-row/quote hydration to the existing SQL-capable publisher seam. Deduplicate references across direct user rooms. Hydrate once per batch, not per recipient. |
| Full durable payloads plus redaction/fencing | Need indexed message/chat/quote dependencies, claimed-publisher fencing, deletion/redaction of queued content, and replay continuity repair. A stale publisher cannot be allowed to repopulate a purged Stream. | Viable if body replay proves essential under measured reconnect load; substantially more failure states and distributed coordination. |

Keep the existing publisher's batch claim/publication pattern and add one bounded hydration operation. Its Lua adapter appends a bodyless hint and publishes the full ephemeral frame atomically. Hints contain event ID, chat, sequence/revision and bounded operation metadata, never body or quote text. Coalesce replay hints per chat before bounded SQL recovery; add jitter, cancellation, per-device concurrency and server rate budgets. Live room fanout stays shared across recipients. Pub/Sub remains at-most-once, so hints do not replace authoritative recovery. [Redis Pub/Sub](https://redis.io/docs/latest/develop/pubsub/).

Shared group frames cannot prove an individual viewer's personal visibility of an old edited message or reply target. Include target identity and omit unproven preview text; resolve unknown visible quotes in a bounded viewer-authorized batch. Suppress old upserts until visibility proof is available. Do not add SQL lookups for every recipient on each ordinary live send or retain every personal exclusion in browser memory.

Selective `XDEL` removes named Stream entries, not all copies of their text. It also cannot preserve this repository's replay proof across undetected internal holes. Redis notes that entry deletion does not necessarily immediately reclaim its allocated memory. [XDEL](https://redis.io/docs/latest/commands/xdel/). With payload retention, fence old publishers and reset affected replay epochs or implement explicit discontinuity proof. User-room resets affect unrelated direct chats and can cause recovery bursts. Prefer eliminating retained bodies instead. Migrating existing plaintext outbox/Streams still requires a bounded drain/redaction/reset plan and old-publisher retirement; a new schema does not clean existing data.

A publisher may hydrate immediately before a delete commits, then publish its old snapshot afterward. Revision guards prevent reinstalling it after the client learns the deletion, but cannot guarantee that a client learns deletion first. Treat this as an in-flight response with bounded queue lifetime. Stronger no-post-commit-publication semantics require a real publication fence coordinated with deletion; acknowledge its chat-lock/network delay before choosing it. Do not present revision comparison as a distributed erasure fence.

Define purge completion as permanent removal from application-authoritative message rows and all retained application content stores, after migration work, with no future retry able to recreate them. Report acceptance separately from completion. PostgreSQL MVCC dead tuples require vacuum and do not mean the application still retains live history rows. [Vacuum](https://www.postgresql.org/docs/current/routine-vacuuming.html). Operational WAL, snapshots, backups, Redis/Rabbit persistence, already delivered packets, downloaded exports and recipient memory need explicit retention/access policies. SQL `DELETE` cannot erase those copies retroactively.

In particular, an accepted Rabbit command contains original text and may remain unacknowledged after SQL commit or be redelivered after deletion. Dedup suppresses saving it again; normal successful consumption eventually ACKs it. A delayed duplicate or exhausted-command queue may retain plaintext longer. Application SQL-purge completion must not claim broker-wide erasure while those copies remain. Monitor bounded broker retention and drain operationally; do not purge shared queues or ACK before commit. A command encrypted with a per-message erasure key would change this stronger guarantee, but is a large redesign without necessity for the requested application purge. [Rabbit ACK/requeue semantics](https://www.rabbitmq.com/docs/confirms#consumer-acks-double-and-unknown-tags).

## Recommended interaction module

Use one message-list selection/action module, with the viewport as the geometry adapter. Its small interface accepts message action intents and pointer/keyboard gestures and returns selection, popup and reply intents. Hide gesture snapshots, cancellation and caps inside it. This gives depth and locality instead of per-row timers and competing menu handlers. Keep existing recovery ownership; UI selection never owns authoritative visibility.

The standards establish mechanisms, not this exact product behavior. Pointer Events supplies capture, `pointercancel`, capture loss and `touch-action`; capture keeps receiving movement beyond a bubble. [Pointer Events](https://www.w3.org/TR/pointerevents3/). UI Events specifies click/double-click ordering, so a double-click cannot be treated as an unrelated first activation. [UI Events](https://www.w3.org/TR/uievents/). The Selection API exposes document text selection. [Selection API](https://www.w3.org/TR/selection-api/). Web A disables container double-click reply in selection mode and stops content double-click propagation; its touch behavior differs from desktop. [First-party handlers](https://github.com/Ajaxy/telegram-tt/blob/master/src/components/middle/message/hooks/useOuterHandlers.ts#L97).

Recommended behavior:

- A stationary primary click opens a small anchored popup with applicable Reply, Edit, Select and Delete actions, plus eligible read information. Links, text selection, editor controls and native copy gestures retain their own behavior. Replace the three-dot trigger and separate reader modal. Clamp the popup to the viewport; close it on target removal, chat change or Escape.
- Outside selection mode, double-click replies only on an eligible noninteractive message area. Preserve double-click word selection inside text by default. Suppress popup opening after text-selection drags. Opening the first-click popup must not steal the second click's target; close/cancel it when double-click wins and avoid moving keyboard focus for pointer-only opening. There is no portable system double-click timeout to hard-code. Verify real browser sequences.
- In explicit selection mode, primary click toggles. On press-drag, freeze the initial selected set and choose select or deselect from the starting row's initial state. Apply that fixed intent to the inclusive vertical range from anchor row to current row; reverse movement recomputes from the initial set rather than toggling repeatedly. Determine rows from Y within the list's vertical row bounds, even with X outside bubbles. Separators are not targets.
- Capture only the active primary pointer. A single animation-frame loop measures rows and scrolls near viewport edges at bounded speed, recomputing the range after scrolling. Bound selected IDs and gesture work to the shared 100-item cap and retained rows. Stop rather than silently select an unbounded remote interval. Show the count/limit. Keep selected identities, not copied bodies; drop or explicitly disable selections lost by eviction.
- Pointer up commits. Escape, pointer cancellation, capture loss, blur/hidden state, chat change and unmount stop auto-scroll, release capture and revert the in-progress gesture to its initial selection. Suppress the trailing click after a drag. Touch preserves native vertical scrolling outside explicit selection mode; offer Select through the popup/long-press without requiring touch dragging. Scope `touch-action` changes to the selection interaction, not the entire chat.

Use keyboard-operable row action access, Space to toggle in selection mode, Shift plus navigation for bounded ranges, and Escape to exit. A context-menu key/Shift+F10 opens the same popup; destructive confirmation remains accessible. If using ARIA menu roles, implement arrow/Home/End focus, activation and focus return, rather than merely adding roles. Inline reader rows must not masquerade as menu actions. [WAI menu pattern](https://www.w3.org/WAI/ARIA/apg/patterns/menubar/).

## Recommended checks, inline reads, grouping and location

Telegram documents one check for cloud acceptance and two for reading, without device-delivery status. [Check meanings](https://telegram.org/faq#q-what-do-the-check-marks-mean). Here one check means committed saved, never merely Rabbit queued or device ACK. Two means the existing human read contract. Default group semantics should remain any other eligible member read, with an accessible "Read by at least one member" label; do not imply every member has read or introduce a new all-member scan. Confirm the existing summary contract before changing it.

Fetch inline timestamp details only while an eligible outgoing message popup is open, using one bounded reader page with inline Load more if needed. Cancel/ignore stale completions, expire cached details, show unavailable/loading/error explicitly, and reauthorize target visibility on the server. Keep existing strict 168-hour eligibility and server-first-acceptance times. Telegram's direct method has unread/age/privacy errors and its group method has configurable size/age limits; they do not establish a universal seven-day constant. [Direct read date](https://core.telegram.org/method/messages.getOutboxReadDate), [group readers](https://core.telegram.org/method/messages.getMessageReadParticipants).

Web A groups by sender/day and defines a 600-second interval, but its inspected comparison splits at greater than 600 seconds. [Grouping implementation](https://github.com/Ajaxy/telegram-tt/blob/master/src/components/middle/helpers/groupMessages.ts#L9). Follow the brief's stricter rule here: split at a gap of exactly ten minutes or more, on author/day changes, or an explicit structural divider. Use immutable creation times, not edit times; split on negative time gaps rather than assuming wall clocks follow sequence. Recommendation: incoming group avatar and tail on the last row of each visual run, sender label at its first row, reserve consistent avatar space. Compute runs over the bounded ordered window with a neighbor at paging seams when available. Recompute after deletion, prepend and layout changes without changing IDs or navigation coordinates. Exact avatar placement is a project visual choice, not inferred from the interval constant.

Store per-chat `{messageId,sequence,offsetPx,atLatest}` separately from message bodies, with an explicit metadata cache budget and session persistence if desired. Capture a stable visible row and its pixel offset before navigation. On return, load one indexed around-sequence window if evicted, using nearest surviving visible neighbor when the anchor disappeared. Do not walk intervening pages. Pin the latest bounded page independently. Default to 50 latest plus 200 detached saved references, as in earlier research, with byte limits and separate pending-send limits. Budget inactive chat keys as well; unlimited anchor keys are still unlimited memory. The audits identify ChatRecovery/navigation as the owner, with the DOM hook as adapter.

Restore after the correct request generation installs rows and layout measures them; then apply scroll offset before paint where necessary. Observe subsequent height changes, compensate relative to the same anchor, and stop restoration when the user intentionally scrolls. Do not fight native scroll anchoring with a second uncoordinated correction. React documents `useLayoutEffect` before repaint and warns it blocks painting; use it only for the bounded layout step. Cleanup must survive Strict Mode's extra setup/cleanup cycle and stale fetch completion. [useLayoutEffect](https://react.dev/reference/react/useLayoutEffect), [useEffect](https://react.dev/reference/react/useEffect).

## Recommended read-dwell ordering

HTML distinguishes document visibility and focus; neither alone proves row visibility. Intersection Observer notifications are asynchronous and Resize Observer reports size changes, not attention. [HTML focus/visibility](https://html.spec.whatwg.org/multipage/interaction.html), [Intersection Observer](https://www.w3.org/TR/intersection-observer/), [Resize Observer](https://www.w3.org/TR/resize-observer/).

Use one visibility scheduler that reevaluates on focus, visibility restoration, installed rows, anchor restoration, resize, grouping/quote height changes and scroll. Do not wait for an intersection threshold crossing after focus. Measure committed row geometry in a scheduled frame after layout; evaluate only the selected chat and actual viewport. Treat navigation restoration as settling before starting dwell. On blur/hidden state, cancel eligibility immediately. At the 700 ms deadline recheck focus, visibility, row existence, selection generation and geometry with a monotonic clock. A delayed background timer cannot carry hidden time into a successful dwell. Preserve timers for unchanged continuously visible rows when arrivals update the list; replace timers only when eligibility changes. Keep coalescing at at most one read request per second.

Do not force the highest sequence read on focus. Preserve the cumulative account frontier and recent first-read ranges from ADR0002, including their honest declaration semantics. Coverage through absent rows can complete transport recovery, but is never a human-read event. A detached reply jump does not declare the skipped prefix read. Test the exact production caller after background arrivals and focus, with no scroll/click; actual browser scheduling and variable geometry are essential evidence. Record any inability to produce genuine hidden-tab state rather than simulating it and claiming reproduction.

## Required invariants and evidence

These are proposed tests and measurements, not results. Use real PostgreSQL/Rabbit/Redis for transaction, broker and replay guarantees; test the existing module interfaces. Run Go race checks for changed concurrency. Generate models from source schemas/migrations/controllers, decode strictly and share sparse-page/deletion/replay fixtures across languages, as required by [repository rules](../../AGENTS.md).

| Failure or edge | Required invariant and check |
| --- | --- |
| Two devices clear/select/hide concurrently; lost invalidation | Monotonic cutoffs/revisions, merged exclusions, account-only effect and authoritative reconnect convergence; no membership removal |
| Clear versus send/edit/reply; overlapping clears | Accepted cutoff fixes scope; later sends survive; old edit/reply cannot expose hidden content; all transaction effects roll back together |
| Retry after purge, crash between commit and Rabbit ACK, old direct identity | Saved dedup result stays terminal; no body resurrection or routing into the fresh chat; ACK remains after commit |

| Stale claimed publication, quote deletion, old payload migration | Durable outbox/Streams contain no removed body/quote after completion; ephemeral race stated honestly; old publisher cannot recreate durable payloads |
| Huge hidden middle, alternating intervals, empty/deleted tail | Indexed jumps and scan budgets; empty page continuation progresses; recovery ends without requiring every `+1` |
| Old HTTP snapshot/live upsert after clear, changes below retention floor | Revisions prevent resurrection in latest/detached/pinned/quotes; reset replaces/removes, rather than only patching existing IDs |
| Foreign IDs, mixed-author group batch, missing/hidden reply target | Atomic denial without leaking content; prior replies show unavailable target; repeated authorized removal remains safe |
| Drag outside bubble, reverse drag, edge scroll, pointer loss | Fixed select/deselect intent, no double toggle/trailing action, cap enforced, no leaked frame loop/listeners, cancellation restores initial set |
| Click/double-click/text selection, keyboard/touch | Copy remains usable, reply occurs once, no destructive first-click effect, accessible focus and touch scrolling |
| A/B/A, evicted/deleted anchor, late response, quote resize | One around seek, generation-safe restoration, stable pixel offset, latest remains available, bodies and metadata bounded |
| Focus after background burst, blur at 699 ms, resize at deadline | Only continuously eligible actual rows satisfy 700 ms; no transport/read conflation; unchanged dwell survives arrivals |
| Time gap 599.999/600 seconds, day/page seam, target deleted | Deterministic grouping, correct avatar/tail after recomputation, anchor and read geometry remain valid |

## Architecture recommendation and staged implementation

Use a concrete deletion module whose interface accepts actor, target, scope and idempotency identity and returns cutoff/revisions plus accepted/completed operation state. Its persistence seam owns rights, lock order, visibility predicates and durable purge progress; jOOQ is the adapter. Put shared visible-history rules inside that implementation for locality across page/quote/read/reply queries. Depth comes from hiding those rules from controllers and workers, not adding generic pass-through repositories. Deepen the existing publisher module with batch hydration and distinct live/replay encoding. Deepen ChatRecovery rather than creating a second client cache. One navigation/location owner and one selection module give leverage across sidebar, reply jump, deletion and keyboard callers. These are scoped responses to the audits' demonstrated friction.

1. Update ADR0001/0002 and terms for scoped deletion, sparse certified coverage, bodyless durable hints and accepted versus completed purge. Define strict generated contracts and cross-language fixtures first. Preserve SQL dedup and ACK after commit.
