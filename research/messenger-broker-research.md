# Messenger broker research: room fanout and recovery

This note compares Kafka, RabbitMQ and Redis for a Messenger with multiple WS nodes, several devices per user, direct messages and bounded group chats. It revisits the earlier recommendation in [broker selection](broker-selection.md). The question is whether the broker can send one saved room event to every WS node that currently has interested sockets, while still allowing a client to recover a missed message. Broker behavior below comes from vendor documentation. Architecture choices are our inferences unless stated otherwise. The [selected architecture](messenger-architecture.md) now uses RabbitMQ for send commands and Redis for live room events; this note preserves the alternatives.

## First define the room

`user:<id>` and `group:<id>` can both be logical WS rooms. A WS node keeps a local `room -> sockets` map. A device may belong to several rooms, and the same user may have devices on several nodes. A broker subscription or RabbitMQ binding is **per interested WS node**, not per browser socket. Direct messages may target the two user rooms. A group publication may target its group room, provided every device that should receive it has joined that room. If we publish the same message through a group room and a user room, clients need to deduplicate by stable message ID.

That last requirement matters. Joining only the group currently open in the UI saves subscriptions, but other group messages then require user-room notification fanout or a later catch-up request. Joining *every* group for every connected device expands the number of active room-node subscriptions or bindings. Neither policy is free; choose it from the product delivery contract and measure its cost.

## The Kafka question

**Yes, every interested WS node can read a Kafka room event, but Kafka does not do this automatically for a shared consumer group.** Kafka assigns each partition to exactly one consumer within a group. If nodes A and B use the same consumer group and a `group:42` record lands on partition 7, one node receives it. If A and B use *different* consumer groups, both can receive the record. Kafka documents this group behavior and per-partition ordering. [Kafka design](https://kafka.apache.org/design/), [Kafka introduction](https://kafka.apache.org/0100/documentation.html).

There are three practical arrangements:

| Kafka arrangement | Does every interested node receive the group event? | Cost |
| --- | --- | --- |
| One group for all WS nodes, one shared topic keyed by room | No. One node owns the partition and would have to forward to the other interested nodes. | A separate node-routing hop or room-to-node directory. |
| One group per WS node, one shared topic keyed by room | Yes, but **every** WS node reads **every** event in that topic and discards events for rooms with no local sockets. | Broker read traffic and filtering scale with all WS nodes, not just interested nodes. |
| Independent node readers manually assigned the partitions containing local rooms | Yes. Each interested node reads those partitions and filters by room key. | Kafka has no key-level subscription. A node with rooms scattered across partitions soon reads many unrelated events. The application must maintain assignments and cursors as local rooms change. |
| A separate topic per room, independent node groups | Nodes can subscribe selectively. | Topic and partition counts grow with rooms; dynamic subscriptions and group state become a large control plane. This is a poor default for many user and group rooms. |

A further arrangement is a Kafka consumer tier that reads each partition once, looks up interested nodes, then routes to them via another transport. Kafka is the retained upstream log in that design; it is **not** doing room-aware fanout itself. The table is an inference from Kafka's consumer-group, topic and manual partition-assignment APIs. Kafka's own monitoring guide treats partition count as a resource to monitor. [Kafka design](https://kafka.apache.org/design/), [Kafka consumer API](https://kafka.apache.org/42/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html), [Kafka monitoring](https://kafka.apache.org/43/operations/monitoring/).

Kafka is strong when we need a retained, replicated event log at high aggregate rate, ordered processing *within each partition*, replay by offset, or independent consumers such as search indexing and analytics. Its batching improves throughput; the producer's `linger.ms` waits up to a configured interval for more records, and a larger consumer `fetch.min.bytes` can improve throughput at the cost of latency. Current Kafka producer docs show a 5 ms default linger, but that is one tunable delay, not a measured end-to-end delivery time. `acks=all` and an appropriate replication policy protect the Kafka write, not the client's WebSocket receipt. [Kafka design](https://kafka.apache.org/design/), [Kafka producer configuration](https://kafka.apache.org/43/generated/producer_config.html), [Kafka consumer configuration](https://kafka.apache.org/43/generated/consumer_config.html), [Kafka topic configuration](https://kafka.apache.org/43/generated/topic_config.html).

For *this* fanout shape, Kafka adds either broad reads or another routing tier. Keying a record by `group:42` preserves Kafka partition order for that key, but it does not subscribe other nodes to that key and can concentrate a hot room on one partition. A Kafka offset is an internal transport position. It does not by itself tell a reconnecting client which chat messages it has applied. These are design deductions from Kafka's partition model. [Kafka design](https://kafka.apache.org/design/).

## RabbitMQ: broker-side routing to nodes

A direct or topic exchange can route key `group.42` to one queue per **interested WS node**. Each node binds its queue on the first local socket joining a room and unbinds after the last leaves. RabbitMQ's exchange uses bindings to route a publication to the matching queues, so a group spanning nodes A and B gets one queued copy for A and one for B; each node then fans out locally. A direct exchange suffices for exact room IDs; use a topic exchange if wildcard routing is needed. RabbitMQ documents both exchange types and bindings. [RabbitMQ exchanges](https://www.rabbitmq.com/docs/exchanges).

This is a good match for sparse rooms, but it has operational costs:

- The number of queue bindings follows active `room x WS node` pairs. Joins, leaves, node restarts and broker reconnects change those bindings. The node must treat the binding as ready only after RabbitMQ confirms the bind; otherwise an event can be published while the first local client is already eligible but the queue is not yet bound. On reconnect the node must rebuild bindings from its local socket map. This race is an inference from the exchange and binding model. [RabbitMQ exchanges](https://www.rabbitmq.com/docs/exchanges).
- A queue per node is very different from a queue per connection. It caps queue count near WS-node count, while binding count may still be large. Queue type matters: quorum queues replicate and confirm durable writes but add consensus and disk work. RabbitMQ advises against quorum queues for temporary queues, lowest latency and large fanout; its docs even name instant messaging as a case that may benefit less from quorum queues. Classic queues avoid quorum replication but do not replicate the queue contents in current RabbitMQ. [RabbitMQ quorum queues](https://www.rabbitmq.com/docs/quorum-queues), [RabbitMQ classic queues](https://www.rabbitmq.com/docs/classic-queues).
- A publisher confirm is **not** proof that any WS node received a publication. RabbitMQ can confirm an unroutable publication; `mandatory` plus returns, or an alternate exchange, is needed if an empty route is an error. A consumer ACK proves only that the WS node told RabbitMQ it processed the delivery. It does not prove that each local client applied it. [RabbitMQ confirms](https://www.rabbitmq.com/docs/confirms), [RabbitMQ exchanges](https://www.rabbitmq.com/docs/exchanges).
- A durable queue per short-lived WS instance can retain events after all its sockets have moved elsewhere. An exclusive queue disappears with its connection and cannot provide that durability. Queue identity, deletion, backlog limits and reconnect behavior need an explicit policy. RabbitMQ heartbeats detect dead broker connections after a configured timeout; the documentation warns against very low timeouts because they cause false positives. [RabbitMQ queues](https://www.rabbitmq.com/docs/queues), [RabbitMQ heartbeats](https://www.rabbitmq.com/docs/heartbeats).

RabbitMQ is therefore a plausible **interested-node fanout** implementation, not an automatic end-to-end delivery guarantee. It deserves a measured comparison with Redis for this workload. It is also a natural candidate for the separate asynchronous send-command queue: a confirmed command can be `queued`, then an API worker validates and commits it before replying `saved`. [RabbitMQ confirms](https://www.rabbitmq.com/docs/confirms).

## Redis: Pub/Sub, Streams, and a hybrid

Redis Pub/Sub directly implements the room subscription shape. Each node subscribes to `user:<id>` or `group:<id>` only while it has local sockets. A publication goes to current subscribers. Redis 7 sharded Pub/Sub confines a shard publication to the relevant cluster shard and can spread channels across shards. It has little storage work on the live path, but Redis explicitly calls delivery **at most once**: a disconnected or stalled subscriber cannot replay from Pub/Sub. [Redis Pub/Sub](https://redis.io/docs/latest/develop/pubsub/).

Redis Streams offer two different read patterns. Independent `XREAD` readers can each read the same room stream from their own cursor, so this **can** fan out to all interested WS nodes. `XREADGROUP` with one shared consumer group divides entries among nodes, like a work queue; that topology does **not** broadcast. Separate groups per node also broadcast, but create group state and pending-entry handling. Per-room streams and independent readers make room selection possible, yet many active room-node readers, retained histories and cluster placement need measurement. A blocking `XREAD` can avoid fixed-interval polling, but its documented work to wake waiting readers grows with the number of blocked clients. [Redis Streams](https://redis.io/docs/latest/develop/data-types/streams/), [Redis XREAD](https://redis.io/docs/latest/commands/xread/), [Redis XREADGROUP](https://redis.io/docs/latest/commands/xreadgroup/).

A hybrid uses Pub/Sub for the immediate path and a bounded Stream for short recovery. The outbox relay performs one Redis script/function that appends the event and publishes its position, with room history keys in one Redis Cluster slot. Redis scripts are atomic from other clients' view and permit `PUBLISH`/`SPUBLISH`; this does **not** create a PostgreSQL-to-Redis transaction. Centrifugo's Redis broker uses Pub/Sub plus Redis Streams history and treats that history as an ephemeral recovery cache. [Redis scripting](https://redis.io/docs/latest/develop/programmability/eval-intro/), [Redis Lua API](https://redis.io/docs/latest/develop/programmability/lua-api/), [Redis Cluster slots](https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/), [Centrifugo engines](https://centrifugal.dev/docs/server/engines/).

A different Redis design has a retained Stream **per WS node**. One router consumes accepted events, looks up the nodes interested in each room, and `XADD`s the event to each destination stream. The WS node uses `XREADGROUP`, acknowledges after processing, and can reclaim pending entries after a consumer restart. This removes per-room Pub/Sub position checks because each node has one replayable feed. It adds an interest directory, one stream append per destination node, idempotent router retries, binding-change races, and a policy for streams belonging to dead nodes. Redis does not supply room-to-node routing for Streams; this entire arrangement is an application design inference from `XADD` and consumer-group semantics. Redis's asynchronous replication still leaves a failover loss window, so PostgreSQL catch-up remains necessary. [Redis Streams](https://redis.io/docs/latest/develop/data-types/streams/), [Redis XREADGROUP](https://redis.io/docs/latest/commands/xreadgroup/), [Redis replication](https://redis.io/docs/latest/manual/replication/).

This hybrid does **not** remove the user's objection to checks. A later publication with a skipped room offset exposes a gap. A missed **last** publication has no later offset to reveal it. Centrifugo uses periodic positioning against history to detect that condition. Without a position check, an independent durable feed to each node, or a client-driven sync rule, an otherwise healthy socket can remain silently stale. The position check can be batched or limited to active views, but its detection delay and cost remain product choices. Redis replication is asynchronous and acknowledged Redis history can be lost after some failovers, so PostgreSQL must remain the recovery source if accepted messages must survive them. [Centrifugo history and recovery](https://centrifugal.dev/docs/server/history_and_recovery), [Redis replication](https://redis.io/docs/latest/manual/replication/).

## What "guaranteed delivery" can mean here

Keep these acknowledgements separate:

1. `queued`: a RabbitMQ quorum queue confirmed the send command. A worker may later reject it.
2. `saved`: SQL committed the message, the idempotency key and an outbox event. This is the durable application promise.
3. `broker accepted`: Kafka, RabbitMQ or Redis accepted a publication under its configured durability rules.
4. `node processed`: the WS node consumed it and attempted local socket delivery.
5. `device applied`: the client applied the message and acknowledged its application cursor.

No broker ACK implies step 5. The client needs a stable message ID for deduplication and a database-backed cursor for exact catch-up, or an explicit recent-view refresh contract if exhaustive catch-up is unnecessary. For the strict version, a transactional per-chat sequence can provide `WHERE chat_id = ? AND sequence > ?` without relying on ULID creation time or a nontransactional SQL sequence. The ordering argument and PostgreSQL sources are in [Messenger recovery source checks](messenger-recovery-sources.md). RabbitMQ and Kafka both document broker-side acknowledgements independently of application processing. [RabbitMQ confirms](https://www.rabbitmq.com/docs/confirms), [Kafka design](https://kafka.apache.org/design/).

If a WS node receives a broker event and sends it to a device, the node can keep a bounded pending item until a client ACK or timeout. A timeout can trigger retry or forced reconnect and database sync. This catches a lost client frame **after the node knew about the event**. It cannot catch an event the node never learned existed. To detect that last case while a client remains connected, the architecture needs a durable delivery obligation to that node or device, or some periodic comparison with the source of truth. RabbitMQ's durable queue is one way to keep a node-level obligation after a binding exists; Redis positioning and client sync are other ways with different costs. These are deductions from the acknowledgement boundaries above.

## Earlier research in this repo

The earlier article reviews are useful as test cases, not performance proofs:

- [Avito](sources/avito.md) describes a move from **one RabbitMQ queue per connection** to Redis Pub/Sub with short history and positioning. That says the former topology was costly at Avito's workload. It does not measure one RabbitMQ queue per WS node. The first-party [Avito write-up](https://habr.com/ru/companies/avito/articles/522744/) and [Centrifugo recovery docs](https://centrifugal.dev/docs/server/history_and_recovery) support the distinction.
- [Taycode](sources/taycode.md) shows **one queue per node** with per-room RabbitMQ bindings, which matches the routing question. The sample omits a complete bind/reconnect race protocol and does not establish client delivery. The author's [article and sample](https://github.com/Taycode/distributed-socket-app) should be read alongside [RabbitMQ binding](https://www.rabbitmq.com/docs/exchanges) and [confirm](https://www.rabbitmq.com/docs/confirms) rules.
- [Brain Bytes & Binary](sources/brainbytes.md) sketches Kafka partition ownership in a way that would give two gateways the same partition in one group. Kafka explicitly assigns a partition to one consumer within a group, so a router or independent groups are required. [Kafka design](https://kafka.apache.org/design/).
- [Young Gao](sources/young_gao.md) uses one Redis Streams consumer group across WS nodes and labels the result broadcast. Redis documents that `XREADGROUP` shares entries; independent `XREAD` readers or independent groups are required for broadcast. [Redis Streams](https://redis.io/docs/latest/develop/data-types/streams/).
- [Priyanshu Gupta](sources/priyanshu.md) uses a broad `private.#` RabbitMQ binding on every gateway. It reaches multiple devices but sends all private events to every gateway for local filtering. Interested-node exact bindings trade that broker traffic for more control state. [RabbitMQ exchanges](https://www.rabbitmq.com/docs/exchanges).
- [Lichess's maintained WS repository](sources/lichess.md) uses Redis communication and local user/room maps, and has bounded in-process version history. It is a useful example of domain-specific WS nodes, but its short history is not a durable Messenger inbox. [Lichess WS source](https://github.com/lichess-org/lila-ws).

## What Telegram and WhatsApp actually disclose

Telegram's public API documents client update positions (`pts`, `seq`, channel positions), gap detection and `updates.getDifference` or `updates.getChannelDifference` recovery. It also documents a long-period sync trigger after 15 minutes without updates. That is evidence for client-side reconciliation, **not** evidence that Telegram uses Kafka, RabbitMQ or Redis for internal fanout. [Telegram updates](https://core.telegram.org/api/updates).

Meta's WhatsApp multi-device write-up says the sending client encrypts and transmits a separate copy to each sender and receiver device for one-to-one chats, and devices sync history and state. It does not identify the internal server message broker. Its end-to-end encrypted client fanout is also a different content-handling contract from this proposed server-readable Messenger. [WhatsApp multi-device](https://engineering.fb.com/2021/07/14/security/whatsapp-multi-device/).

## Selected split and alternatives to test

The selected architecture uses partitioned RabbitMQ quorum queues for commands. The WS node returns `queued` after publisher confirmation, an API worker later returns `saved` or `rejected`, and a stable `requestId` supports status lookup after reconnect. Rate limits run before enqueueing. Configure bounded queues with `reject-publish`, since RabbitMQ's default queue-length overflow can discard older entries. Partitioning is required because one queue replica has one CPU core on its hot path. More workers help until SQL or a hot chat becomes the limit. [RabbitMQ quorum queues](https://www.rabbitmq.com/docs/quorum-queues), [RabbitMQ confirms](https://www.rabbitmq.com/docs/confirms), [queue limits](https://www.rabbitmq.com/docs/maxlength), [queue scaling](https://www.rabbitmq.com/docs/queues).

Redis Streams with `XREADGROUP` and `XACK` could also process commands at scale if partitioned. We kept RabbitMQ because before SQL commit the command exists only in the ingress broker. Redis's default asynchronous replication can lose an acknowledged `XADD` during failover, whereas RabbitMQ documents a conditional majority-survival promise after a quorum publisher confirm. Redis Stream room history is written after SQL commit and can fall back to SQL. The split is about the meaning of `queued`, not an assertion that RabbitMQ has higher raw throughput. [Redis consumer groups](https://redis.io/docs/latest/commands/xreadgroup/), [Redis replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/), [RabbitMQ quorum queues](https://www.rabbitmq.com/docs/quorum-queues).

For this project, keep SQL messages, outbox and database catch-up as the correctness path. Redis sharded Pub/Sub with bounded Stream history is the selected **live** fanout design. Compare it under the same direct/group workload with RabbitMQ node queues if measured Redis routing or recovery cost is too high:

1. Redis sharded Pub/Sub with bounded Stream history has interested-node routing, but needs positioning or another sync policy for a silently missed final publication.
2. RabbitMQ direct exchange with one queue per WS node and exact bindings for active rooms puts routing and node-level redelivery in the broker, but binding churn, queue lifecycle and node/client ACK boundaries must be designed and measured.

Use Kafka if a separate retained event pipeline becomes a requirement. It could feed a router or independent processing services, while a room-aware transport performs live WS fanout. Measure send-to-client-ACK p50/p99, broker ingress and egress, active bindings/subscriptions, join/leave rate, time to detect a quiet lost event, reconnect catch-up time, and recovery after a WS node or broker failure. The result should choose the broker, not its reputation.

The decisive failure test is: keep a client's WebSocket open, interrupt only its WS node's broker feed, publish **one final message**, and send no later traffic. Record how each design detects the missing message and how long the client takes to apply it. Also test a first room join racing publication, a broker restart, a WS-node restart, and a reconnect surge. These tests expose delivery gaps that a normal throughput benchmark cannot.
