# Account read progress and mutable history

The client requires 700 ms of continuous foreground visibility, then coalesces progress to at most one request per second per selected chat. New arrivals preserve existing dwell timers. These timestamps record server acceptance of a cumulative prefix, including batching delay; they do not measure the exact instant each message was seen.

Human reads use a cumulative account-level frontier, separate from device recovery ACKs. Immutable timestamp ranges record the first accepted crossing of each new prefix, with one range per eligible UTC message-creation day. This avoids expanding a large prefix into per-message receipts, handles creation times that are not ordered by sequence, and permits bounded creation-based cleanup. The API expires details exactly 168 hours after message creation; daily bucket cleanup has up to one day of physical grace plus scheduler backlog. Short advances inspect at most 256 indexed sequences and write intervals only for eligible creation days present. Larger advances write at most eight ranges without scanning the skipped prefix. Retention and batching reduce storage without promising constant space for arbitrary traffic. See the [research](../research/presence-read-receipts-and-history.md).

Edits and deletions keep message creation sequences and use independent message versions and chat mutation revisions. A retained durable change log repairs old-message mutations after disconnects; clients below its floor refresh their bounded windows. Tombstones keep recovery contiguous and reply targets navigable. SQL mutations publish through the existing transactional outbox. Chat deletion is global, authorized for either direct participant or a group's creator, and a deleted direct pair can start a new conversation with a new identity.

Read invalidations use one SQL deduplication row per chat and two-second bucket. A nonblocking transaction advisory claim keeps independent readers from waiting on another reader's uncommitted notification row. Losing the claim coalesces only the invalidation, while each reader still commits its own durable progress and timestamps. A winner rollback can leave that bucket without a notification; the selected chat's jittered 12–15 second summary refresh repairs missed hints. The unique SQL key still enforces the emission limit across API replicas. Hash collisions can coalesce unrelated hints but cannot change progress or authorization. PostgreSQL releases transaction advisory locks automatically; see its [advisory lock functions](https://www.postgresql.org/docs/17/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS).
