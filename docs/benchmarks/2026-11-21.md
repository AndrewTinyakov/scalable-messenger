# Benchmark verification, 21 November 2026

The corrected driver completes the repeated 1,000-user workload with all sends saved and no correctness failures. All four stress ramps fail their pass criteria. The repeated pool runs vary too much to establish a reliable pool-size improvement or an exclusive server capacity limit.

Measured driver revision: `836dc7f84ea29a4c975fe23179821c93d3ca070c`. The later report commit changes documentation only. Application image digests match the `e56bc28` campaign because the benchmark repairs do not change server code. Replica routing was disabled. Sanitized results and 49 benchmark records, including the eight final runs, are in [2026-11-21.json](2026-11-21.json).

## Conditions

- Node 24.21.0, seed 1118, fresh accounts, fixtures and task volumes for every run.
- Shared Apple M3 Pro with 36 GiB RAM; Docker had 11 CPUs and 15.7 GiB RAM.
- Two-minute, 20-user smokes with one and two workers; two ten-minute, 1,000-user runs with one worker.
- Four 24-minute stress ramps with two workers: 1,000, 2,000, 3,000, 4,500, 6,000 and 8,000 users, four minutes per stage. Pool order was 10/20, 16/32, 16/32, 10/20, with the second 1,000-user run between the middle pair.
- Pool sizes mean Hikari connections per API instance / PgBouncer API connections. Images and generated plan hashes matched across repeats.

Every SQL `SAVED` delta matched the corresponding driver saved count. Every run had zero conflicting terminal results, durable mismatches, unverified durable rows and verification failures. Both 1,000-user runs checked 8,876 durable outcomes and 1,182 mutation views each. Their read-propagation checks passed 129/129 each.

"Not confirmed saved" includes actions that were never dispatched, explicit rejections and unresolved sends. It does not mean committed database rows disappeared. Failure observations include WebSocket errors, action failures and generator limits; several observations can describe one action. The launcher exited 0 because the campaign completed. Each stress collector exited 1, matching its failed report.

Two-worker missing-recipient checks cover recipients in the sender's shard. Interrupted device lifecycles are counted separately. Final resolve checks cover the actor and sampled peer views, not every offline cache or physical purge. Zero durable mismatches is evidence for those checks.

## What the stress runs establish

The larger pool produced the best repeat, saving 79,876/79,942 sends, but its other repeat saved 77,432. The smaller pool ranged from 68,212 to 78,705. Both settings missed the full-ramp criteria, so neither is demonstrated to sustain this 8,000-user workload. These samples do not justify changing the 16/32 default or claiming that it always outperforms 10/20.

Gateway `DEPENDENCY_UNAVAILABLE` and `RATE_LIMITED` frames accounted for 77–98% of traffic failures per run. Every ramp reached 64 active command workers per gateway; peak rolling command-queue p99 ranged from 4.8 to 17.6 seconds. Both API pools filled, with peak connection-acquisition p99 from 1.0 to 5.0 seconds. Sampled PostgreSQL commits waited on `WALWrite`, while the 15-second PgBouncer snapshots showed no waiting clients. Queueing and API connection acquisition are useful next investigation targets; the measurements do not establish a single initiating cause.

The 33 stress read misses remain measured scenario failures. The retained diagnostics lack the per-read event and state-fetch timeline needed to assign them to driver or server. Four occurred in B2 without local HTTP-capacity or cursor-limit faults.

The generator recorded 5,680 local `httpCapacity` failures and seven `catchUpCursorMissing` failures. All seven cursor failures were in `stress-a2`; they stopped recovery safely and remained failures in the report. `catchUpGap` was zero. Generator saturation limits a server-capacity interpretation.

Host conditions also varied. Median one-minute load ranged from 7.0 to 22.9 across stress runs. The PostgreSQL compute calibration ranged from 83.7 to 104.4 ms, and single-write `fdatasync` from 588 to 3,410 microseconds across the campaign. OrbStack did not expose the Docker VM pressure counters. Calibration and host load show unequal conditions; they do not identify the cause of every slow request.

## Progress and historical limits

The earliest 1,000-user baseline with an API estimate recorded 129,004 API requests. The final corrected repeats estimated 94,680 and 94,431, about 27% fewer. The old baseline revision was not pinned. Request mix, state recovery and WebSocket implementation changed between drivers, so this is an observed workload-history comparison, not a controlled code-performance improvement. The corrected repeats have ACK p99 upper bounds of 262.1 and 131.1 ms; there is no supported latency-improvement claim.

The old final-head 1,000-user reports marked a pass while retaining four read misses each. Earlier stress reports also mixed stale expected values, uncertain committed mutations and failed verifier authentication with possible application failures. Historical pass flags and mismatch totals remain provisional. Missing historical fields remain unknown. API totals are Prometheus increase estimates and include final verification for the 1,000-user runs. Workload latency and resource samples in corrected reports stop at the traffic cutoff.

The first corrected campaign on `1dcb801` passed its smokes and first 1,000-user run, then stalled one stress worker in a cursorless recovery loop. Its partial stress report is excluded from pool conclusions. The final driver reports that protected no-progress state explicitly, releases the worker and allows a later state check to repair it. When no replacement window needs protection, the original sync still repairs the cursor immediately. All eight final runs completed.
