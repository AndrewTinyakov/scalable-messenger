# Video summary audit: million WebSocket connections in Go

The local `video.txt` is a Gemini-generated article about [Eran Yanay's GopherCon Israel 2019 talk](https://www.youtube.com/watch?v=LI1YTFMi8W4), not a transcript. I could not fetch the video itself. Yanay published the [talk's code](https://github.com/eranyanay/1m-go-websockets) and [slides](https://speakerdeck.com/gopherconil/eran-yanay). His README calls the code a demonstration, explicitly **not production ready**. It reports over one million connections with less than 1 GB of RAM in that demonstration. This says little about delivery throughput, latency, auth, TLS, fanout, or resilience under a real workload.

## Useful ideas

- Idle connection density has a measurable cost in file descriptors, Go stacks, WebSocket buffers, kernel socket memory, and optional conntrack entries. Yanay's examples progress from a simple server through higher file limits, fewer persistent goroutines, and reusable WebSocket buffers. Compare each step with identical traffic and a full memory breakdown. [Talk repository](https://github.com/eranyanay/1m-go-websockets)
- The relevant test is not simply "how many sockets stay open?" Add messages per second, recipients per message, payload size, slow readers, reconnect bursts, and TLS. The summary correctly points to these as separate bottlenecks, but provides no credible comparative measurements.
- Backpressure and bounded queues are worth showing. A slow client must have a defined policy: drop ephemeral events, disconnect it, or preserve durable events for replay. A bounded worker pool alone can still fill its input queue or leave kernel buffers saturated; its existence is no delivery guarantee.

## Claims to reject or qualify

- The summary says ordinary Go uses a blocking OS thread per connection and must switch to epoll. [Go's runtime already has an integrated network poller](https://go.dev/src/runtime/netpoll.go), using [epoll on Linux](https://go.dev/src/runtime/netpoll_epoll.go). Parked goroutines still consume memory, so a custom event loop may reduce memory at very high idle connection counts, but it is a tradeoff to benchmark, not the first fix.
- Its detailed RAM totals, `100–500 ms` GC pauses, `2.8–4.5 GB` optimized RAM, `sub-millisecond` dispatch, and "easily" one million active sockets have no reproducible workload attached. Do not repeat them as facts. The speaker's own demo claims **less than 1 GB** for its particular workload, already inconsistent with the summary's table. [Demo README](https://github.com/eranyanay/1m-go-websockets)
- The summary's low-level server is not the speaker's published implementation. Its `conn.File()` approach duplicates the descriptor, and the caller must close that duplicate; [Go documents this explicitly](https://pkg.go.dev/net#TCPConn.File). Its one-call write does not handle partial writes or `EAGAIN`; its edge-triggered read needs to drain until `EAGAIN`. The [published demo](https://github.com/eranyanay/1m-go-websockets/blob/master/4_optimize_gobwas/epoll.go) instead uses level-triggered polling and reflection to find the descriptor, and its [server](https://github.com/eranyanay/1m-go-websockets/blob/master/4_optimize_gobwas/server.go) still uses `net/http` for upgrades. It has no broker, rooms, durable delivery, or broadcast benchmark.
- The summary treats TCP `rmem/wmem` defaults as fully allocated RAM for every idle socket and claims a precise 100 GB to 4 GB saving. [Linux documents these values as minimum, initial and maximum buffer settings](https://docs.kernel.org/5.10/networking/ip-sysctl.html), with receive autotuning. Actual memory depends on traffic and kernel state. Measure `/proc/net/sockstat` before changing them. Likewise, `tcp_tw_reuse` concerns outgoing connections and does not remove the server's one-million-accepted-socket limit; port exhaustion is mainly a load-generator concern.
- `sync.Pool` may discard entries at any time, so it cannot hold required per-connection state or guarantee zero allocations. [Go's `sync.Pool` docs](https://pkg.go.dev/sync#Pool). The summary's slab allocator, zero-copy claims, 90% GC reduction, sharded hub, and fixed worker counts are unverified additions. Treat them as hypotheses, not results of the talk.
- Conntrack bypass with `NOTRACK` is a topology-specific firewall choice, not a general preferred setting. The demo simply [raises `nf_conntrack_max`](https://github.com/eranyanay/1m-go-websockets/blob/master/4_optimize_gobwas/increase_conntrack_table). A pet project should not recommend globally changing kernel or firewall settings without showing the actual limit and traffic path.

## Good experiment for the project

Keep this as an optional **connection-density lab**, separate from the main routing and reliability examples. Run the same idle and active workload against a simple Go server and the event-loop demo. Record client and server CPU, RSS/heap, goroutines, file descriptors, socket memory, established connections, connects per second, outbound messages per second, p99 client-observed delivery latency, and disconnects. Show how an apparent one-million-socket success changes when each client receives events, reconnects, or reads slowly. Do not reuse the demo as production code.
