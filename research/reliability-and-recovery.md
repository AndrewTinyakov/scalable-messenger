# Reliability and recovery for the WebSocket projects

These are transport and recovery findings for the teaching projects, based on primary documentation. The [Messenger architecture](messenger-architecture.md) is the current Messenger decision: RabbitMQ quorum queues accept send commands, SQL stores saved messages and exact conversation sequence, and Redis handles live room delivery plus short replay. Distinguish a WS node losing its broker connection while clients remain connected from a client losing its WebSocket connection. Both can create a gap.

## If a WS node loses Redis Pub/Sub

Redis Pub/Sub has at-most-once delivery. A WS node that misses a publication will never receive that publication from Pub/Sub later. Its browser clients may remain connected, so waiting for a WebSocket reconnect is insufficient. The WS node must detect loss and either catch up or force affected clients to resubscribe and recover. [Redis Pub/Sub](https://redis.io/docs/latest/develop/pubsub/), [Centrifugo history and positioning](https://centrifugal.dev/docs/server/history_and_recovery).

For accepted events, use a durable database row and outbox row in one transaction. The outbox relay retries publication after a Redis outage. This protects the database-to-broker hop, but does not ensure that an already-connected WS node receives a Pub/Sub event. Give each message a stable ULID, independent of any delivery position. Keep bounded recent publication history alongside live Pub/Sub. A reconnecting WS node reestablishes subscriptions and checks the broker history position for each active room. If the complete gap is in recent history, it replays it. If it is not, it signals clients to refresh from the API. A periodic position check detects a lost final event when no later event arrives. Centrifugo uses positioning and forces reconnect with an insufficient-state code when it detects a possible gap. [Debezium outbox](https://debezium.io/documentation/reference/transformations/outbox-event-router.html), [Centrifugo history and positioning](https://centrifugal.dev/docs/server/history_and_recovery).

The fast path should record a publication in bounded history and publish its live notification as one broker operation, as Centrifuge's Redis broker does with Lua. Separate append and publish operations create an extra gap if the process crashes between them. Idempotent event IDs are still needed because an outbox relay may retry. [Centrifuge broker discussion](https://centrifugal.dev/blog/2021/01/15/centrifuge-intro), [Centrifugo Redis engine](https://centrifugal.dev/docs/server/engines).

## If the live path uses Kafka or Redis Streams

Kafka and Redis Streams retain records, so a consumer can resume from its committed offset or saved stream ID while records remain. This helps recover a WS-node-to-broker interruption. Neither gives every WS node a copy merely because WS nodes share a consumer group: members of a group divide records. Broadcasting to all interested WS nodes requires independent readers, per-node groups, or a separate interested-node fanout layer. Large numbers of per-node groups and per-room streams add state and replay work. A retained accepted-event processing log can use Kafka or Streams where needed; Messenger instead uses RabbitMQ for pre-SQL commands and a short Redis Stream only for post-commit room recovery. [Kafka design](https://kafka.apache.org/43/design/design/), [Redis Streams](https://redis.io/docs/latest/develop/data-types/streams/).

An offset commit proves only that an internal consumer advanced. It does not prove a WebSocket frame reached a client, or that the client applied it. Product delivery semantics still need application event IDs, client gap detection, and recovery. Broker retention can expire and consumer lag can exceed it. Kafka durability depends on replication and acknowledgement settings. Redis Stream durability depends on Redis persistence and replication settings; the default asynchronous replication can lose recent writes on a failover. [Kafka design](https://kafka.apache.org/43/design/design/), [Kafka topic configuration](https://kafka.apache.org/43/generated/topic_config.html), [Redis Streams](https://redis.io/docs/latest/develop/data-types/streams/), [Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/), [Redis replication](https://redis.io/docs/latest/manual/replication/).

## If a client disconnects

There are two recovery paths, which can be combined:

| Path | How it works | Good use | Limit |
| --- | --- | --- | --- |
| API and database | Client reconnects, resubscribes, sends its last application cursor, then fetches missing accepted events or a snapshot from the API. | Authoritative history, first load, long offline periods, cache misses. | A simultaneous reconnect of many clients can spike API and database reads. |
| Broker-backed short history | On reconnect, client sends the last stream epoch and offset. WS node reads missed publications from a bounded per-channel stream and returns them with the subscribe response. If the epoch changed or the entire gap is not present, it reports recovery failure and the client calls the API. | Brief disconnects and reconnect storms. | Extra broker memory and write work; retention can be exceeded or lost. It is a cache, not authoritative history. |

Centrifugo uses Redis Pub/Sub for live delivery and, when history is enabled, Redis Streams for bounded channel history. Each publication gets an offset and each stream an epoch. It reports `recovered: true` only when the epoch matches and the whole missed interval is present; otherwise `recovered: false`, so the application reloads from its source of truth. Centrifugo's Redis history survives a WS-node restart but inherits Redis persistence limits. It also has a cache recovery mode that returns only the latest publication, suitable for complete state snapshots rather than chat events. [Centrifugo recovery](https://centrifugal.dev/docs/server/history_and_recovery), [Centrifugo engine](https://centrifugal.dev/docs/server/engines).

The API may use ULIDs as message identities without a synchronized database counter. Centrifugo nevertheless gives each publication a *per-channel broker offset* and each history stream an epoch. This is broker metadata, not the database primary key. It coordinates publications within one channel; channels can still be distributed across Redis shards. An implementation can instead use Redis Stream IDs as short-history cursors and query entries after the last seen ID, but those IDs are not contiguous, so an ID comparison by itself cannot reveal every missed live event. Check the retained range and its earliest/latest IDs, or use an explicit broker position as Centrifugo does. [Centrifugo recovery](https://centrifugal.dev/docs/server/history_and_recovery), [Redis Streams](https://redis.io/docs/latest/develop/data-types/streams/).

A ULID is also a poor *strict* database catch-up watermark. The ULID specification says ordinary ULIDs generated within the same millisecond have no guaranteed sort order, and monotonic generation is local to a generator. Clocks and transaction commit order can differ across API instances. Therefore `WHERE id > last_seen_ulid` can miss a message that commits late with a smaller ULID. For an application that only needs a refreshed recent view, fetch a recent database page or snapshot and merge it with buffered live events by ULID. For a hard guarantee that every long-offline message can be read exactly after a position, the database needs some commit-consistent ordering mechanism or a serialized per-room writer. That is a product requirement and storage-design choice, not a requirement that message IDs be sequential. [ULID specification](https://github.com/ulid/spec).

This mechanism also resolves the subscribe/replay race: install the live subscription and recover against a known stream position as one coordinated operation, buffer live publications arriving during replay, then deduplicate and deliver in position order. A naive `GET history; SUBSCRIBE` has a hole between the two calls. A naive `SUBSCRIBE; GET history` can return duplicates; IDs and ordering are required. This race analysis is an inference from the documented epoch/offset recovery protocol and Redis Pub/Sub semantics, not a claim about Centrifugo's internal code. [Centrifugo recovery](https://centrifugal.dev/docs/server/history_and_recovery), [Redis Pub/Sub](https://redis.io/docs/latest/develop/pubsub/).

## Suggested project policies

- **Messenger:** Every accepted message has a ULID and durable database row. The client uses short broker history for a brief gap. If recovery fails, it reloads an authoritative recent page or snapshot from the API and merges by ULID. A strict long-offline catch-up API needs a separate commit-consistent database cursor; a ULID alone does not provide one. A personal room may carry message references rather than its own ordered history.
- **Kanban:** Cards have a desk version. On a gap, load a versioned snapshot and apply only later edits. A short stream can save API reads for brief disconnects, but a snapshot may be cheaper than replaying many edits.
- **Twitch-like chats:** Store bounded recent chat history per streamer. A short broker stream can absorb reconnect bursts, but cap replay volume and use API fallback or a fresh recent-history page if the gap is too large. The product must decide whether it promises every missed chat line or just recent context. At hundreds of thousands of reconnecting clients, the replay traffic itself is substantial.

For each project, measure broker outage duration, longest recoverable gap, recovery success rate, API fallback rate, duplicate rate, and client-observed time to a correct state.
