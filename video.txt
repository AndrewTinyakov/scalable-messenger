Introduction: The Challenge of High-Concurrency Real-Time Systems
In modern distributed systems and web platforms, providing real-time responsiveness to millions of connected clients has evolved from a niche requirement into an operational standard. Traditional web architectures were predominantly request-response driven: a client issued an HTTP request, the server processed it synchronously or asynchronously, returned a payload, and closed the connection.

However, live notifications, real-time collaboration tools, financial ticker streams, and instant messaging demand persistent, low-latency bi-directional channels.

The standard protocol for achieving bi-directional communication over TCP is WebSocket (RFC 6455). While establishing a single WebSocket connection is straightforward, maintaining one million or more concurrent, long-lived WebSocket connections on a single server machine introduces severe challenges across multiple layers of the system stack:

Memory Allocation Overheads: Persistent connections consume system resources even when idle. Standard application runtimes allocate fixed-size buffers, goroutines, or threads per connection, which rapidly exhausts system RAM when scaled to 10 
6
  concurrent sessions.

Operating System Limits: The Linux kernel enforces strict limits on open file descriptors, epoll event limits, network socket buffer allocations, and connection tracking tables (conntrack).

Runtime Scheduling and Garbage Collection (GC) Pressure: High-concurrency runtimes like Go rely on lightweight user-space threads (goroutines) and automatic heap management. Millions of active heap objects lead to prolonged GC pauses, high CPU overhead, and runtime scheduling lock contention.

This article provides an end-to-end deep dive into engineering a high-performance Go-based WebSocket infrastructure capable of serving 1,000,000+ simultaneous connections on a single server node.

1. The Real-World Motivation: Moving Beyond Polling
To understand why extreme WebSocket optimization is required, consider a large-scale real-time notification engine (such as the architecture deployed at Mail.Ru or similar high-throughput web platforms).

The Problem with Polling
Before moving to an event-driven pub/sub architecture, platforms frequently rely on periodic client polling over HTTP:

[ Client Browser ] --- HTTP GET /api/v1/notifications ---> [ API Gateway ]
[ Client Browser ] <--- 200 OK / 304 Not Modified -------- [ API Gateway ]
At scale, if tens of millions of active users poll the system every few seconds:

The system handles 50,000+ HTTP requests per second (RPS) just to check state changes.

Over 60% to 70% of these requests return 304 Not Modified, wasting network bandwidth, TLS handshake/session verification overhead, and backend CPU cycles.

Latency is non-deterministic: A user receives an event only on their next polling cycle, introducing a delay bounded by the polling frequency.

The Real-Time Event Bus Architecture
To eliminate polling overhead, the architecture transitions to a push-based publisher-subscriber event model:

When a backend service updates state (e.g., a new email arrives or a notification is triggered), it pushes an event to a central broker (e.g., NATS, Kafka, or Redis). The WebSocket Gateway receives the event and pushes it immediately down the open persistent socket to the targeted user.

While this drastically reduces system-wide RPS and delivers sub-millisecond event dispatching, it shifts the operational bottleneck entirely onto connection density and RAM usage at the gateway layer.

2. The Idiomatic Go Approach and Its Resource Bottlenecks
Go is widely praised for its concurrency model. The runtime scheduler manages M OS threads across N virtual CPU cores using P processor contexts, scheduling G goroutines effortlessly.

The standard, idiomatic way to implement a WebSocket server in Go (using standard libraries or high-level packages like gorilla/websocket) uses a two-goroutine-per-connection pattern.

Go
// Standard Idiomatic Connection Handler
type Channel struct {
    conn *websocket.Conn
    send chan []byte
}

func NewChannel(conn *websocket.Conn) *Channel {
    ch := &Channel{
        conn: conn,
        send: make(chan []byte, 256),
    }
    go ch.readerLoop()
    go ch.writerLoop()
    return ch
}

func (c *Channel) readerLoop() {
    defer c.conn.Close()
    for {
        _, message, err := c.conn.ReadMessage()
        if err != nil {
            break
        }
        c.handleMessage(message)
    }
}

func (c *Channel) writerLoop() {
    for msg := range c.send {
        err := c.conn.WriteMessage(websocket.TextMessage, msg)
        if err != nil {
            break
        }
    }
}
Deconstructing the Resource Footprint
While this model is simple, readable, and perfectly fine for tens of thousands of connections, it fails when targeting 1,000,000 concurrent sockets due to cumulative memory overheads:

1. Goroutine Stack Memory
Each Go goroutine starts with a dynamic stack allocation (typically 2 KB to 8 KB depending on Go version and runtime state).

Goroutines per connection=2 (1 reader + 1 writer)
For 1,000,000 connections=2,000,000 goroutines
2,000,000×4 KB average stack=8 GB RAM
2. I/O Buffers (bufio.Reader and bufio.Writer)
High-level packages allocate buffered readers and writers to minimize system call overhead during socket reads and writes. Standard buffer sizes defaults are often 4 KB for reading and 4 KB for writing.

I/O Buffers per connection=4 KB (read)+4 KB (write)=8 KB
For 1,000,000 connections=8 GB RAM
3. Channel Overhead and In-Memory Data Structures
A Go channel (chan []byte) with a capacity buffer of 256 elements allocates internal ring-buffer queue data structures in the heap. Coupled with the struct metadata, socket file descriptor state, and TLS session contexts (if terminating TLS at the application layer), each connection incurs an additional 4 KB to 8 KB of runtime allocations.

3. Four Core Optimizations to Reach 1 Million Connections
To scale beyond these limits, we must redesign how the Go runtime interacts with socket file descriptors, moving away from "goroutine-per-connection" to zero-copy, event-driven I/O.

Optimization 1: Netpoll / epoll Instead of Blocking Goroutines
In a typical real-time system, connections are 99% idle. A client connects, receives an initial handshake, and sits quietly waiting for push events from the server. Holding two active blocking goroutines (one waiting on sys_read and one waiting on channel receives) for an idle connection is a massive waste of resources.

Instead of assigning a blocking goroutine to every socket, we use the Linux kernel's epoll (or BSD kqueue) subsystem via Go's internal netpoll or a custom OS event loop.

 Idiomatic Pattern (Thread-per-Connection)
+--------------+    +-------------------+
| Connection 1 | -> | Reader Goroutine  | (Blocking Read)
+--------------+    +-------------------+
| Connection 2 | -> | Reader Goroutine  | (Blocking Read)
+--------------+    +-------------------+

 Optimized Event-Driven Pattern (epoll Loop)
+--------------+
| Connection 1 | \
+--------------+  \    +---------------------+    +----------------------+
| Connection 2 | -> | epoll Wait Loop     | -> | Fixed Worker Pool    |
+--------------+  /    | (Single Goroutine)  |    | (e.g., 128 Workers)  |
| Connection N | /     +---------------------+    +----------------------+
+--------------+
Sockets are registered with epoll in edge-triggered (EPOLLET) or level-triggered modes.

A single (or small fixed pool of) background reactor goroutine calls epoll_wait.

Only when the Linux kernel signals that data has arrived on a specific file descriptor (EPOLLIN) does the reactor fetch a worker from a bounded pool to read and process the incoming frame.

Memory Savings: Eliminates 1,000,000 idle reader goroutines (Saves ~4 to 8 GB RAM).

Optimization 2: On-Demand Writer Goroutines and Buffer Reuse
Just as reader goroutines block waiting for incoming network bytes, writer goroutines block waiting on channel reads (<-c.send).

To eliminate persistent writer goroutines:

When the server needs to push a message to a client, it directly schedules a temporary task or acquires a transient worker from a pool.

Instead of allocating dedicated bufio.Writer instances per socket, buffers are managed via sync.Pool.

When writing finishes, the write buffer is returned to the sync.Pool for immediate reuse by other connections.

Go
var writeBufferPool = sync.Pool{
    New: func() interface{} {
        return make([]byte, 4096)
    },
}

func SendMessage(fd int, payload []byte) error {
    buf := writeBufferPool.Get().([]byte)
    defer writeBufferPool.Put(buf)
    
    // Construct WebSocket Frame into shared buffer
    n := frameWriter.Construct(buf, payload)
    
    // Perform non-blocking syscall write
    _, err := syscall.Write(fd, buf[:n])
    return err

Memory Savings: Eliminates 1,000,000 idle writer goroutines and persistent 4 KB write buffers (Saves ~8 GB RAM).

Optimization 3: Low-Level WebSocket Protocol (Zero-Copy Upgrades)
Standard HTTP router abstractions (net/http) allocate substantial memory during the HTTP Upgrade handshake. A standard Go http.Request and http.ResponseWriter lifecycle performs multiple heap allocations (~8 KB per upgrade).

By bypassing heavy net/http abstractions and operating directly on raw TCP net connections (net.Conn or raw File Descriptors fd) using lightweight libraries like gobwas/ws:

Zero-copy Upgrades: Headers are parsed directly from read slices without converting headers to http.Header maps (map[string][]string).

Header Framing Optimization: WebSocket frame headers (2 to 10 bytes) are decoded on the stack or via reusable byte buffers.

Memory Savings: Reduces memory churn during connection bursts, keeping heap allocations near zero during connection setup.

Optimization 4: Bounded Worker Pools for Resource Protection
When hundreds of thousands of clients reconnect simultaneously (e.g., after a network blip or deployment), a naive server that spawns a goroutine per incoming packet will suffer severe CPU thrashing and memory exhaustion (self-inflicted DDoS).

By routing network events from epoll into a bounded worker pool (e.g., 128 to 1,024 dedicated goroutines):

Go
type WorkerPool struct {
    workChan chan int // File descriptors ready for I/O
}

func (p *WorkerPool) Start(numWorkers int) {
    for i := 0; i < numWorkers; i++ {
        go func() {
            for fd := range p.workChan {
                processSocketIO(fd)
            }
        }()
    }
}
Controlled CPU Utilization: Core processing remains locked to available hardware threads, keeping context switches low.

Backpressure Support: If the system is overloaded, incoming events queue up deterministically rather than crashing the process via Out-Of-Memory (OOM) errors.

4. Kernel and OS Tuning for 1 Million Open Sockets
Software optimizations in Go are only half the battle. Out of the box, standard Linux distributions are tuned for general-purpose workloads, not extreme connection density. Attempting to open 1,000,000 TCP sockets on a default Linux installation will fail almost immediately due to operating system safety limits, socket buffer exhaustion, and local port constraints.

To host 1,000,000 simultaneous TCP connections on a single instance, the Linux kernel must be explicitly configured via /etc/sysctl.conf and system resource limits.

1. File Descriptor Limits (nofile)
In Unix-like systems, "everything is a file." Every active TCP socket consumes a file descriptor (fd). By default, Linux limits a single process to 1,024 open file descriptors.

To allow a single Go binary to hold over 1,000,000 file descriptors:

Bash
# /etc/security/limits.conf
*    soft    nofile    1200000
*    hard    nofile    1200000
root soft    nofile    1200000
root hard    nofile    1200000
System-wide limits must also be adjusted in kernel variables:

Bash
# Increase system-wide file descriptor maximum
sysctl -w fs.file-max=2000000
2. Tuning Network Memory Sockets (rmem & wmem)
By default, the Linux kernel allocates default read and write memory buffers for every open TCP socket to support high-throughput TCP window scaling:

Default tcp_rmem: 4096 87380 6291456 bytes (4 KB min, 87 KB default, 6 MB max)

Default tcp_wmem: 4096 16384 6291456 bytes (4 KB min, 16 KB default, 6 MB max)

If every connection allocates an 87 KB read buffer and a 16 KB write buffer by default:

1,000,000×(87 KB+16 KB)≈103 GB RAM
Since WebSocket connections are mostly idle and transport small control/notification payloads, we must drastically reduce the minimum and default TCP buffer allocations in /etc/sysctl.conf:

Ini, TOML
# Reduce TCP socket read buffer space (min, default, max in bytes)
net.ipv4.tcp_rmem = 1024 4096 2097152

# Reduce TCP socket write buffer space (min, default, max in bytes)
net.ipv4.tcp_wmem = 1024 4096 2097152

# Adjust total memory allocated for all TCP buffers (measured in 4KB pages)
# min / pressure / max
net.ipv4.tcp_mem = 786432 1048576 2097152
With a 4 KB default read/write buffer, kernel-level memory for 1,000,000 sockets drops from ~100 GB down to ~4 GB RAM.

5. Architectural Deep Dive: Implementing Epoll with Go
To completely bypass the standard runtime network poller overhead and remove blocking net.Conn goroutines, we directly interface with the Linux kernel's epoll system calls using Go's golang.org/x/sys/unix package.

Epoll Core Mechanics: Edge-Triggered vs. Level-Triggered
Level-Triggered (Default): epoll_wait continuously notifies the application as long as a socket's read buffer contains unread data.

Edge-Triggered (EPOLLET): epoll_wait notifies the application only once when state transitions from having no data to having new data. This minimizes context switching in high-concurrency systems.

                     +---------------------------+
                     | Kernel Socket Buffer (FD) |
                     +-------------+-------------+
                                   | New Data Arrives
                                   v
                     +---------------------------+
                     |    epoll_wait Event       |
                     +-------------+-------------+
                                   |
                +------------------+------------------+
                |                                     |
                v                                     v
     [ Edge-Triggered (EPOLLET) ]         [ Level-Triggered ]
     Triggers ONCE on state change        Triggers CONTINUOUSLY until
     Requires reading until EAGAIN        socket buffer is completely empty
Step-by-Step Epoll Server Implementation
Below is a low-level event loop implementation that registers incoming TCP sockets into an epoll selector without spawning dedicated goroutines per socket.

Step 1: Initialize Epoll Loop Structure
Go
package main

import (
	"fmt"
	"net"
	"sync"
	"syscall"
	"golang.org/x/sys/unix"
)

type EpollLoop struct {
	fd          int
	connections map[int]net.Conn
	mu          sync.RWMutex
}

func NewEpollLoop() (*EpollLoop, error) {
	// Create an epoll file descriptor using epoll_create1
	fd, err := unix.EpollCreate1(0)
	if err != nil {
		return nil, err
	}
	return &EpollLoop{
		fd:          fd,
		connections: make(map[int]net.Conn),
	}, nil
}
Step 2: Socket Registration (EpollCtlAdd)
When a new TCP client completes the handshake, its file descriptor is extracted and added to the epoll interest list with EPOLLIN (readable) and EPOLLET (edge-triggered) flags.

Go
func (e *EpollLoop) Add(conn net.Conn) error {
	// Extract raw file descriptor from network connection
	rawConn, err := conn.(interface{ File() (*os.File, error) }).File()
	if err != nil {
		return err
	}
	fd := int(rawConn.Fd())

	// Set file descriptor to non-blocking mode
	err = unix.SetNonblock(fd, true)
	if err != nil {
		return err
	}

	// Define epoll event structure
	event := &unix.EpollEvent{
		Events: unix.EPOLLIN | unix.EPOLLET | unix.EPOLLHUP | unix.EPOLLERR,
		Fd:     int32(fd),
	}

	e.mu.Lock()
	e.connections[fd] = conn
	e.mu.Unlock()

	// Register file descriptor with epoll kernel instance
	return unix.EpollCtl(e.fd, unix.EPOLL_CTL_ADD, fd, event)
}
Step 3: Event Loop Wait Routine
A dedicated background goroutine runs the event loop, continuously monitoring ready file descriptors and passing read events to a worker processing pool.

Go
func (e *EpollLoop) Wait(workQueue chan<- int) error {
	events := make([]unix.EpollEvent, 128) // Batch event retrieval
	for {
		// epoll_wait blocks until kernel reports socket activity
		n, err := unix.EpollWait(e.fd, events, -1)
		if err != nil {
			if err == unix.EINTR {
				continue // Interrupted by system signal, retry
			}
			return err
		}

		for i := 0; i < n; i++ {
			fd := int(events[i].Fd)
			ev := events[i].Events

			// Check for connection close or errors
			if ev&(unix.EPOLLHUP|unix.EPOLLERR) != 0 {
				e.Remove(fd)
				continue
			}

			// Socket is ready for reading
			if ev&unix.EPOLLIN != 0 {
				workQueue <- fd // Hand off file descriptor to worker pool
			}
		}
	}
}
By decoupling connection storage from blocking runtime loops, this model maintains 1,000,000 connections using a single background epoll goroutine and a fixed worker pool, drastically cutting runtime stack allocation and thread overhead.

6. Advanced Go Memory Management: Eliminating GC Overhead
In high-concurrency systems running on automatic heap-managed runtimes, memory allocation behavior directly dictates throughput and tail latency (p

When managing 1,000,000 connections, naive code creates millions of dynamic heap allocations per second (e.g., temporary slice buffers for frame parsing, short-lived string representations of headers, or metadata objects). This triggers frequent Garbage Collection (GC) Stop-The-World (STW) mark-and-sweep cycles, leading to severe CPU starvation and socket write timeouts.

Understanding the Go GC Bottleneck
The Go collector is a concurrent tri-color mark-and-sweep collector. Its execution cost scales with:

The total number of objects on the heap (scanning millions of micro-objects to determine liveness).

The rate of new heap allocations (triggering GC execution early via GOGC threshold limits).

To achieve predictable performance under massive scale, our goal is simple: Zero allocations on the hot path during active frame reads and writes.

Step 1: Reusable Buffer Pools via sync.Pool
sync.Pool provides thread-safe, lock-free local storage for temporary object reuse, relieving GC pressure by preventing allocations from reaching the heap during steady-state operations.

Go
package main

import (
	"sync"
)

// Global pool of fixed-size byte buffers (4KB per buffer)
var readBufferPool = sync.Pool{
	New: func() interface{} {
		// Pre-allocate byte slice to avoid slice header re-allocations
		b := make([]byte, 4096)
		return &b
	},
}

func ProcessSocketRead(fd int) {
	// Acquire buffer from pool (Lockless Thread-Local Cache hit)
	bufPtr := readBufferPool.Get().(*[]byte)
	buf := *bufPtr

	// Perform non-blocking syscall read directly into pooled memory
	n, err := readSyscall(fd, buf)
	if err == nil && n > 0 {
		// Parse frame and handle business logic using buf[:n]
		handleFramePayload(buf[:n])
	}

	// Reset buffer state and return to pool
	readBufferPool.Put(bufPtr)
}

Instead of allocating thousands of small arrays individually:

Allocate a single contiguous Slab Block (e.g., 64 MB of RAM).

Carve out uniform chunks (e.g., 1 KB slots) sequentially for active connection buffers.

Keep track of free slots using a bitmask or lockless freelist.

7. Real-Time Architecture: Scaling the Pub/Sub Engine
Managing 1,000,000 connections on a single node is only half the battle; the server must also route broadcasts efficiently.

If a system needs to push a global system notification to all 1,000,000 clients:

Naive channel-based iteration over 1,000,000 items creates lock contention and CPU bottlenecks.

If each socket write blocks or runs slowly, client write queues back up, leading to memory bloat.

The Fan-Out Bottleneck & Lock Contention
A common pattern uses a central mutex protecting a client map:

Go
type Hub struct {
	mu      sync.Mutex
	clients map[int]*Client // 1,000,000 entries
}

func (h *Hub) Broadcast(msg []byte) {
	h.mu.Lock()
	defer h.mu.Unlock()
	for _, client := range h.clients {
		client.sendChan <- msg // Severe contention + blocked locks
	}
}
Locking a single mutex while iterating over 1,000,000 map entries causes total thread blockages across multi-core systems.

Architectural Solution: Sharded Hubs and Ring Buffers
To remove lock bottlenecks, divide client storage into sharded partitions based on connection ID hash rings or socket file descriptors.

           +-------------------------+-------------------------+
           |                         |                         |

   +---------------+         +---------------+         +---------------+
   | Hub Partition |         | Hub Partition |         | Hub Partition |
   |    Shard 0    |         |    Shard 1    |         |   Shard 31    |
   +-------+-------+         +-------+-------+         +-------+-------+

Implementation Pattern:
Divide connection management across N shards (where N=32 or 64, matching available CPU core layout).

Each shard maintains its own sync.RWMutex and map slice.

Broadcasting dispatches work across shards concurrently using parallel goroutines.

Go
type ShardedHub struct {
	shards []*HubShard
}

type HubShard struct {
	mu      sync.RWMutex
	clients map[int]*Client
}

func NewShardedHub(numShards int) *ShardedHub {
	h := &ShardedHub{
		shards: make([]*HubShard, numShards),
	}
	for i := 0; i < numShards; i++ {
		h.shards[i] = &HubShard{
			clients: make(map[int]*Client),
		}
	}
	return h
}

func (h *ShardedHub) GetShard(fd int) *HubShard {
	// Bitwise AND for fast modulo routing (requires power-of-two shards)
	return h.shards[fd&(len(h.shards)-1)]
}
