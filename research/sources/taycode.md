# Taycode: distributed WebSocket chat

Source: [Abdulmateen Tairu, "Websockets: Scaling Over a Distributed System" (2025)](https://medium.com/@taycode/websockets-scaling-over-a-distributed-system-ea567d8372e5). The author also links a [sample project](https://github.com/Taycode/distributed-socket-app). The article was accessible.

## What it proposes

Three WebSocket nodes sit behind Nginx. Each keeps its own socket objects and has a distinct RabbitMQ queue. On the first local join to room `r`, the node binds its queue to `room.r` on a topic exchange. On the last local leave, it unbinds. Publishing to `room.r` sends one copy to each *interested node*, which fans out to its local sockets. A Redis set of user IDs per room supplies a global presence count. The sample uses Nginx `ip_hash` for reconnect affinity. [Article](https://medium.com/@taycode/websockets-scaling-over-a-distributed-system-ea567d8372e5), [RabbitMQ exchange semantics](https://www.rabbitmq.com/docs/exchanges), [sample Nginx config](https://github.com/Taycode/distributed-socket-app/blob/master/nginx.conf).

## What to keep

- The distinction between local sockets and cross-node delivery is clear and teachable. A topic exchange with one queue **per node** reduces broker deliveries when a room occupies only a small fraction of nodes. RabbitMQ routes by binding key to queues, and an exact `room.r` binding is enough here; a direct exchange would also work if wildcard routing is not needed. [RabbitMQ exchanges](https://www.rabbitmq.com/docs/exchanges).
- The bind-on-first-join and unbind-on-last-leave transitions provide a concrete example of dynamic subscriptions. They also reveal the extra control traffic and state that this optimization costs.
- Global presence should be treated separately from socket routing. A room count is an observability or product concern; the broker binding already determines which nodes need a broadcast.

## Limits and failure cases

- The article's `10`-node versus `2`-node example shows an 80% reduction in **node deliveries** (`10,000` to `2,000` per second at `1,000` publishes per second). It does not establish an 80% reduction in CPU. Brokers still route every publish, and bound nodes still fan out to their sockets. This optimization pays most when rooms are sparse across nodes. [Article](https://medium.com/@taycode/websockets-scaling-over-a-distributed-system-ea567d8372e5), [RabbitMQ exchanges](https://www.rabbitmq.com/docs/exchanges).
- The earlier Kafka broadcast sends every event to every node only if each node consumes as a separate consumer group. Kafka can partition messages by room key, but then one consumer receives a partition and must know how to reach sockets on other nodes. The article's result is a property of its consumer topology, not a general Kafka limitation. [Kafka consumer groups](https://kafka.apache.org/documentation/#intro_consumers).
- Redis `SADD room:r:users user_id` and `SREM ... user_id` do not model connection instances. Two devices for one user count as one set member, and disconnecting either removes the user even while the other remains. If a WebSocket node dies, its cleanup handler cannot run, so its IDs remain indefinitely in this design. Redis persistence preserves such stale entries; it does not prove that users are online. Model connections or per-node presence with leases and expiry, then define whether the metric counts users, devices, or sockets. [Article code](https://medium.com/@taycode/websockets-scaling-over-a-distributed-system-ea567d8372e5), [Redis sets](https://redis.io/docs/latest/develop/data-types/sets/), [Redis key expiration](https://redis.io/docs/latest/develop/using-commands/keyspace/).
- Bind and unbind are asynchronous broker operations. A local user can become eligible before the binding exists, and a broker outage can leave local room state and binding state different. Recovery needs explicit re-declaration and re-binding from local connections. The article does not show this. This is an inference from the proposed sequence and RabbitMQ's binding model. [Article](https://medium.com/@taycode/websockets-scaling-over-a-distributed-system-ea567d8372e5), [RabbitMQ exchanges](https://www.rabbitmq.com/docs/exchanges).
- A RabbitMQ publish does not mean a client saw a message. An unroutable publish can still receive a broker confirm; use `mandatory`/returns if routing matters. Publisher confirms, consumer acknowledgements, persistent messages and durable queues cover different hops, while client ACK plus durable history is needed for end-to-end delivery/replay. [RabbitMQ confirms](https://www.rabbitmq.com/docs/confirms), [RabbitMQ reliability](https://www.rabbitmq.com/docs/reliability).
- Nginx selects an upstream for the opening handshake and then tunnels the upgraded connection. `ip_hash` only affects future handshakes; it cannot move an established socket or guarantee a reconnect to the same node if that node is gone. It hashes client IP, so users behind the same NAT may be concentrated. It does not co-locate members of a room. Sticky routing is not required for the RabbitMQ design because every node can accept a reconnect. [Nginx WebSocket proxying](https://nginx.org/en/docs/http/websocket.html), [Nginx `ip_hash`](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#ip_hash).
- The article's sample uses `redis.Redis` synchronous commands inside `async def`; those calls can block that Python event loop while waiting on Redis. It also shows `client_id` and room ID taken from the WebSocket path without any shown identity or room authorization checks. These are limitations of the shown code, not necessarily the full repository. [Article code](https://medium.com/@taycode/websockets-scaling-over-a-distributed-system-ea567d8372e5).

## Where it fits in the project

Use this as the **room-aware broker routing** stage after a simpler all-nodes fanout baseline. Compare broker deliveries, local discard rate, binding count/churn, delivery latency and failure recovery as room occupancy changes. Add crash and multi-device tests to expose why a plain Redis user set is not authoritative presence. Keep message history in a durable store so reconnecting clients can replay missed messages.
