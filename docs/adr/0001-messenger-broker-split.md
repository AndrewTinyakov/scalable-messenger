# Use RabbitMQ for send commands and Redis for live rooms

Status: accepted for the Messenger architecture example.

The WS node publishes send requests to partitioned RabbitMQ quorum queues and reports `queued` only after a publisher confirm. Messenger command processors validate and save them, then acknowledge the consumed commands. This makes `queued` a meaningful acceptance promise even if the sender goes offline before SQL commit, subject to the quorum queue's documented failure assumptions. The Compose cluster has three persistent nodes and three members per queue; a majority must remain available. Clients can connect to all three node addresses. SQL stores the message, request result, chat sequence, and outbox event in one transaction. An outbox publisher publishes saved events through Redis sharded Pub/Sub and keeps short Redis Stream history for recovery. SQL remains the authority for complete catch-up.

Redis Streams could also queue send requests with `XREADGROUP`, `XACK`, and pending-entry recovery. We chose RabbitMQ because a Redis primary can acknowledge `XADD` before its asynchronous replica receives the command; a failover could then erase the only server-side copy of a request that the sender believes is queued. Redis Streams have a different role after SQL commit: losing that short history falls back to SQL. This is a durability decision, not a claim that RabbitMQ has greater raw throughput. [RabbitMQ quorum queues](https://www.rabbitmq.com/docs/quorum-queues), [Redis replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/), [Redis consumer groups](https://redis.io/docs/latest/commands/xreadgroup/).

The extra broker and command hop add latency and operational work. Neither queueing nor Redis publication proves device application. The design uses a fixed set of command queues keyed by chat ID for existing chats and by the sorted user pair for a first direct send, consumer prefetch, a bounded backlog that rejects new publishes when full, request-id deduplication, client application acknowledgements, and SQL catch-up. A single RabbitMQ queue or Redis Stream would concentrate work on one leader or shard. Worker scaling stops helping when SQL or one hot chat becomes the bottleneck. [RabbitMQ queue scaling](https://www.rabbitmq.com/docs/queues), [queue limits](https://www.rabbitmq.com/docs/maxlength), [Redis Cluster](https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/).

The Compose prototype uses one six-node Redis Cluster with three primaries and three replicas for sharded Pub/Sub and bounded Streams. A shared room hash tag puts the Stream, epoch, and channel in one slot. The publisher appends to the Stream and publishes to the room channel in one Redis script. Separate Pub/Sub and Stream clusters would lose that atomic handoff and require another reconciliation protocol. Redis Cluster distributes rooms, but one hot room is still limited by its primary. SQL remains the authority when Redis history is unavailable. One million daily active users alone does not specify peak send rate, connected sockets, or room fanout; capacity needs a load test against those measurements. [Redis Cluster](https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/), [sharded Pub/Sub](https://redis.io/docs/latest/develop/pubsub/).

The outbox insert fires a transaction-bound PostgreSQL `NOTIFY` without carrying event data. The publisher listens on a dedicated connection, then claims and publishes batches of up to 100 rows until no immediately claimable rows remain. It deletes successfully published rows by ID in one SQL transaction per batch, so completed events do not accumulate in the outbox table. A one-second scan also catches missed notifications and leases that expire after a crash. Claim and completion transactions do not include Redis I/O. More publisher processes can claim disjoint batches with `SKIP LOCKED`; event IDs and SQL chat sequences handle retries and publication reordering. [PostgreSQL NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html), [SKIP LOCKED](https://www.postgresql.org/docs/current/sql-select.html).
