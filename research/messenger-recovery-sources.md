# Messenger recovery: source checks

This note checks source claims and records alternatives considered during Messenger design. The [selected architecture](messenger-architecture.md) now uses RabbitMQ quorum queues for send requests, SQL message history with a per-chat sequence, an outbox, Redis Pub/Sub for live fanout, and bounded Redis Stream history for short gaps. Some sections below explain earlier alternatives rather than the selected path. Vendor behavior and our design inferences are kept separate.

## What the components guarantee

| Component | Supported claim | Boundary |
| --- | --- | --- |
| Redis Pub/Sub | A published message reaches clients currently subscribed to its channel, in publication order. Delivery is at most once. A subscriber disconnected at publish time cannot replay the message from Pub/Sub. [Redis Pub/Sub](https://redis.io/docs/latest/develop/pubsub/) | A healthy browser socket says nothing about its WS node's separate Redis subscription connection. This is an inference from the two connections and Pub/Sub's delivery semantics. |
| Redis Stream history | `XADD` can append while trimming by `MAXLEN`, including approximate trimming. This gives a bounded count of recent publications. [Redis XADD](https://redis.io/docs/latest/commands/xadd/) | Redis history inherits Redis persistence and replication behavior; it is not the Messenger database. Centrifugo explicitly treats stream history as an ephemeral cache. [Centrifugo history](https://centrifugal.dev/docs/server/history_and_recovery), [Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/), [Redis replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/) |
| Centrifugo-style recovery | Each channel publication receives a monotonically increasing offset within an epoch. The reconnecting client sends its last epoch and offset. Recovery succeeds only when the epoch matches and the complete gap remains in history; otherwise the server returns `recovered: false` and the application reloads from its database. [Centrifugo history](https://centrifugal.dev/docs/server/history_and_recovery) | The offset is a Redis publication position, separate from the message's durable ID and from a database catch-up cursor. This separation is a design inference from the documented protocol. |
| Live position checks | Centrifugo periodically checks a connected client's position against the stream top. On a possible gap it disconnects the client with code `3010`, causing reconnect and recovery. [Centrifugo history](https://centrifugal.dev/docs/server/history_and_recovery) | Our own WS nodes would need an equivalent check or would need to force resubscription after losing their Redis subscription. Waiting for the browser WebSocket to close would miss the case where only Redis failed. |
| Database outbox | Saving the message and outbox event in one database transaction avoids the gap between committing a message and recording that it needs publication. An asynchronous relay sends the outbox event later. The event needs a stable ID for duplicate detection. [Debezium outbox pattern](https://debezium.io/blog/2019/02/19/reliable-microservices-data-exchange-with-the-outbox-pattern/), [Debezium outbox router](https://debezium.io/documentation/reference/transformations/outbox-event-router.html) | The outbox does not prove that a WS node or browser received the publication. Relay retries can yield duplicates, so consumers must deduplicate by event or message ID. |

## Publication and replay details

The Redis operation that records a broker position, appends the publication to short history, and publishes the live notification should be one server-side operation. Redis guarantees atomic execution of a Lua script or Function; `PUBLISH` is allowed as a write command in scripts. Centrifuge's Redis engine uses Lua scripts and Redis Streams for history. This closes the process-crash gap between separate `XADD` and `PUBLISH` calls. It does **not** create a transaction spanning PostgreSQL and Redis, and it does not make the publication survive every Redis failover. [Redis scripting](https://redis.io/docs/latest/develop/programmability/eval-intro/), [Redis Lua API](https://redis.io/docs/latest/develop/programmability/lua-api/), [Centrifuge implementation overview](https://centrifugal.dev/blog/2021/01/15/centrifuge-intro), [Redis replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

Implementation detail: Redis atomic execution means other clients cannot observe half the script. It is not SQL-style rollback on every runtime error. Validate key types and arguments before writes, and check command errors. Redis explicitly has no transaction rollback. [Redis transactions](https://redis.io/docs/latest/develop/using-commands/transactions/), [Redis scripting](https://redis.io/docs/latest/develop/programmability/eval-intro/)

Outbox relay retries need idempotent Redis publication. If a relay publishes and then crashes before marking the outbox row complete, an ordinary retry can assign a *second* broker offset to the same durable message. Dedupe at the client by stable `message_id` prevents duplicate display, but it does not preserve a one-publication-per-message stream. For that stronger property, keep a bounded Redis mapping from `event_id` to assigned position and check/write it inside the same publication script, with a lifetime at least as long as the outbox retry window. The need for this mapping is a design inference from outbox at-least-once behavior and the epoch/offset protocol. Redis 8.6 also documents stream producer idempotency options, but relying on them would make the design version-dependent. [Debezium outbox pattern](https://debezium.io/blog/2019/02/19/reliable-microservices-data-exchange-with-the-outbox-pattern/), [Centrifugo history](https://centrifugal.dev/docs/server/history_and_recovery), [Redis XADD](https://redis.io/docs/latest/commands/xadd/)

Subscription and history recovery must be coordinated. `GET history; SUBSCRIBE` permits a publication between those steps to disappear from the client's view. `SUBSCRIBE; GET history` avoids that hole if live events are buffered, but may duplicate events. The node should establish the broker subscription, buffer live publications, obtain/replay a complete history interval, deduplicate by event ID, and then drain the buffer in broker-position order. This is a design inference from Pub/Sub's at-most-once semantics and Centrifugo's documented position protocol. Centrifugo explicitly warns that loading database state and subscribing in separate steps has a race; its example captures the stream position first, then loads state, then subscribes from that position. [Redis Pub/Sub](https://redis.io/docs/latest/develop/pubsub/), [Centrifugo history](https://centrifugal.dev/docs/server/history_and_recovery)

If Redis history is lost or trimmed, return an explicit recovery failure. Do not return the retained tail as if it were the complete gap. Centrifugo uses this rule, bounds history by size and age, caps the number of publications in one recovery, and calls the application database the source of truth. [Centrifugo history](https://centrifugal.dev/docs/server/history_and_recovery)

## Identity and the long-offline contract

A ULID is suitable as a stable message identity. It does not establish database commit order across API instances. The ULID specification says IDs generated within one millisecond have no guaranteed order unless a monotonic generator is used, and even that generator only increments its own random component. PostgreSQL sequences also allocate before transaction commit and do not roll back. PostgreSQL `now()` records the transaction start time. Therefore `WHERE ulid > last_seen_ulid`, `WHERE serial_id > last_seen_id`, or `WHERE created_at > last_seen_time` can each skip a row that commits late behind a cursor already advanced by a faster transaction. The skip scenario is an inference from these documented behaviors. [ULID specification](https://github.com/ulid/spec), [PostgreSQL sequences](https://www.postgresql.org/docs/current/functions-sequence.html), [PostgreSQL date/time](https://www.postgresql.org/docs/current/functions-datetime.html)

Two product contracts lead to different database designs:

1. **Recent-view refresh.** After broker recovery fails, fetch an authoritative recent page for the chat and merge it with buffered live events by `message_id`. Older messages remain available through normal backward pagination. This restores a current chat view, but it does not promise an exhaustive enumeration of everything missed during a long absence. A late commit can land outside a finite recent page, so the UI needs pagination or periodic reconciliation if that matters. This is a proposed product policy, not a property of Redis or ULIDs.
2. **Every-message catch-up.** Give each chat a database cursor whose assignment is serialized through commit. One workable design locks the chat row, increments a transactional per-chat counter, inserts the message and outbox row, then commits before another writer can assign the next number. PostgreSQL row locks block conflicting writers until transaction end; unlike `nextval`, this counter update participates in the transaction. This gives a query such as `WHERE chat_id = ? AND sequence > ?` a commit-consistent boundary, assuming every writer uses that path. The guarantee is an inference from PostgreSQL's lock and transaction rules. [PostgreSQL row locks](https://www.postgresql.org/docs/current/explicit-locking.html), [PostgreSQL sequences](https://www.postgresql.org/docs/current/functions-sequence.html)

Even with a database sequence, a relay that processes outbox rows concurrently can publish later chat events first. If client display order must equal database order, serialize publication per chat or reorder by database sequence. The Redis broker offset records *publication* order, not necessarily *commit* order. This is a design inference from the independent outbox relay and Redis publication stages.

## Current recovery decision

Use ULIDs for message identity, a transactional per-chat database sequence for exact saved-message catch-up, outbox publication, Redis Pub/Sub for interested WS nodes, and a bounded Redis Stream per room for short recovery. If Redis cannot prove the whole published gap, fetch SQL rows after the last applied chat sequence. Redis history is a speed optimization and can disappear; the SQL query is the correctness path. A Redis-tail check cannot expose a saved publication lost by Redis failover after the relay marked its outbox row complete, so reconnect and chat-open SQL catch-up remain required. A strict deadline for a continuously open socket needs database-backed reconciliation or a durable delivery ledger. [Redis replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/), [Centrifugo history](https://centrifugal.dev/docs/server/history_and_recovery).

## Follow-up: keeping the outbox fast

The outbox is a durable record, not a required polling interval. Three ways to wake its relay are available:

| Method | Latency path | Recovery rule |
| --- | --- | --- |
| PostgreSQL `NOTIFY` in the message transaction | PostgreSQL delivers the notification only after commit. The relay reads the outbox row and publishes it. PostgreSQL recommends treating the notification as a signal to inspect a table. [PostgreSQL NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html) | A listener may be absent, and `LISTEN` startup has a race. Establish and commit `LISTEN`, scan outstanding outbox rows, react to notifications, and keep a periodic scan. The outbox row, not the notification, carries the retry obligation. [PostgreSQL LISTEN](https://www.postgresql.org/docs/current/sql-listen.html), [PostgreSQL NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html) |
| Publish immediately after commit | The request process can call the same idempotent Redis publication operation as a relay, then return the saved response. If it crashes or Redis fails, the independent relay later sees the outbox row. If it returns before publication, sender latency is lower but live delivery may lag. | Publish only after commit; otherwise clients could see an uncommitted message. The immediate path and relay must coordinate by stable event ID because either can race or retry. These are design deductions from the database/Redis dual-write problem. [Debezium outbox pattern](https://debezium.io/blog/2019/02/19/reliable-microservices-data-exchange-with-the-outbox-pattern/) |
| Change data capture | Debezium tails committed PostgreSQL changes and can emit outbox events without a timed table scan. Its connector resumes from a retained WAL position after restart. It is a fit when CDC is already operated or the outbox volume justifies it. [Debezium PostgreSQL connector](https://debezium.io/documentation/reference/stable/connectors/postgresql.html), [Debezium outbox router](https://debezium.io/documentation/reference/transformations/outbox-event-router.html) | CDC adds replication-slot and connector operations. A stalled slot retains WAL, so monitor lag and disk usage. It has no fixed zero-latency guarantee. [Debezium PostgreSQL connector](https://debezium.io/documentation/reference/stable/connectors/postgresql.html) |

For a PostgreSQL implementation, use a dedicated relay woken by `NOTIFY` plus a periodic outbox scan. For MySQL or Vitess, use a poller or committed-change stream instead. Send the `saved` result only after database commit, then publish it to the sender's room; the sender can query status after reconnect. Measure commit-to-publish latency and outbox age before deciding whether an immediate post-commit publish path is worth its coordination cost. This is an architecture recommendation, not a PostgreSQL guarantee.

## Follow-up: selected durable ingress queue

If an API first publishes `SendMessage` to a durable RabbitMQ queue, a publisher confirm says RabbitMQ accepted the command. It does not say a worker validated membership, committed the message, or delivered a WebSocket frame. Consumer acknowledgement is a separate signal from worker to broker, not from a browser to the application. RabbitMQ documents these as independent mechanisms. For broker crash safety, the queue and message must be durable/persistent and the publisher must use confirms. Redelivery after failures still requires idempotent processing. [RabbitMQ confirms and acknowledgements](https://www.rabbitmq.com/docs/confirms), [RabbitMQ reliability](https://www.rabbitmq.com/docs/reliability), [RabbitMQ queues](https://www.rabbitmq.com/docs/queues)

The selected architecture accepts the extra broker and worker hop because `queued` means the server has taken responsibility even if the sender goes offline before SQL commit. `queued` is still not `saved`. The client waits for a later result or queries by request ID; the worker validates and commits before reporting `saved`; retries resolve to one database message. Redis Streams could run the same worker pattern, but Redis's default asynchronous replication gives a weaker pre-SQL `queued` promise under failover. The broker choice is recorded in the [ADR](../docs/adr/0001-messenger-broker-split.md). [Redis replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/), [RabbitMQ quorum queues](https://www.rabbitmq.com/docs/quorum-queues).

## Follow-up: Redis topology and live checks

Centrifuge's broker interface combines `Publish` and `History`; its author explicitly calls for atomic saving of history and publication with the generated offset. Its Redis engine uses Lua and Redis Streams. In Redis Cluster, all keys touched by one Lua script must share a hash slot. Put a chat's history, epoch/offset metadata, and any event-ID deduplication key in one slot, for example keys tagged `{chat_id}`. Redis 7 sharded Pub/Sub also routes a shard channel by hash slot; conventional cluster Pub/Sub has different cluster-wide propagation behavior. Validate the chosen `PUBLISH` or `SPUBLISH` command with the deployed Redis topology. [Centrifuge broker overview](https://centrifugal.dev/blog/2021/01/15/centrifuge-intro), [Redis Cluster key slots](https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/), [Redis sharded Pub/Sub](https://redis.io/docs/latest/develop/pubsub/)

Centrifugo's `force_recovery` enables positioning. Positioning periodically compares a connected client's channel position with the stream top and disconnects on suspected loss with code `3010`. It needs channel history. This handles a client that stays connected while a publication is missed. It does not mean every message reaches every client in real time: detection happens later, and recovery can fail when history expires. [Centrifugo recovery and positioning](https://centrifugal.dev/docs/server/history_and_recovery), [Centrifugo channels](https://centrifugal.dev/docs/server/channels)

Centrifugo separately sends client pings every 25 seconds by default and waits 8 seconds for a pong. Those are connection liveness settings, not a check that the WS node saw every Redis publication. The public recovery documentation says position checks are periodic but does not specify a fixed check interval or worst-case detection bound; do not infer one from the ping interval. For our own node, detect Redis subscription disconnect, stop claiming continuity, resubscribe, and compare active chat positions. A periodic top-position check catches a lost final event even when no later publication exposes the gap. [Centrifugo configuration](https://centrifugal.dev/docs/server/configuration), [Centrifugo recovery and positioning](https://centrifugal.dev/docs/server/history_and_recovery)

## Follow-up: a strict cursor while retaining ULIDs

If the product promises every missed message, keep `message_id` as a ULID and add `chat_sequence` to the message row, with `UNIQUE (chat_id, chat_sequence)`. Give the chat row a transactional `last_sequence` counter. In one PostgreSQL transaction: lock the chat row with `SELECT ... FOR UPDATE`; validate membership and the idempotency key; increment `last_sequence`; insert the message and its outbox event; commit. A second writer for the same chat waits for the first to commit or roll back before it can assign the next value. Then `WHERE chat_id = $1 AND chat_sequence > $2 ORDER BY chat_sequence` is a strict catch-up query, provided all writers use this transaction path and sequence rows are retained. PostgreSQL documents row-lock blocking until transaction end and the nontransactional behavior of ordinary SQL sequences; the cursor guarantee is an inference from those rules. [PostgreSQL explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html), [PostgreSQL sequences](https://www.postgresql.org/docs/current/functions-sequence.html)

The lock serializes sends within one chat, so a very hot chat can become a write bottleneck. That cost is tied to the stronger order guarantee. A global `BIGSERIAL`, `created_at`, or ULID avoids the row lock but does not fix commit-order ambiguity. A WAL/CDC position could encode commit order, but making it a stable, queryable, per-chat client cursor is a different storage design. Preserve the ULID either way as identity and deduplication key. [PostgreSQL sequences](https://www.postgresql.org/docs/current/functions-sequence.html), [PostgreSQL date/time functions](https://www.postgresql.org/docs/current/functions-datetime.html), [Debezium PostgreSQL connector](https://debezium.io/documentation/reference/stable/connectors/postgresql.html), [ULID specification](https://github.com/ulid/spec)
